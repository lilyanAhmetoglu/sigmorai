## Goal

After this lesson you can:

- Explain MCP to a non-technical colleague: what it is, and what the host, client and server do.
- Sort a feature into a prompt, a resource or a tool by asking who decides when it is used.
- Spot the safety jobs that belong to the AI app, and check what a vendor's MCP support really covers.

## The problem

A hotel group with 9 hotels wants its guest-services assistant to reach three systems: room bookings, the housekeeping schedule, and a spreadsheet of local partner offers that lives on a manager's laptop.

The project lead writes a requirements list after a vendor meeting:

- "We buy MCP from our AI vendor."
- "One connector inside our AI app talks to all three systems."
- "Each system gets the full guest chat, so its answers are better."
- "MCP makes sure the guest agrees before anything happens."
- "The vendor's API connector supports MCP, so the laptop spreadsheet works too."

Each line sounds fine in a meeting. Most are wrong. This lesson gives you the plain facts to fix them. The guidance below is from the MCP spec and each vendor's docs (October 2026).

## The idea

**What MCP is.** The [MCP spec](https://modelcontextprotocol.io/specification/2026-07-28) calls the Model Context Protocol "an open protocol". A **protocol** is a shared set of rules for how two programs talk. MCP is not a product you buy from one vendor. It connects AI apps to outside data and tools in a standard way. The spec says MCP took "some inspiration" from the Language Server Protocol, which did the same job for programming languages in code editors.

The spec has dated versions. The one this course cites is 2026-07-28.

Our example: MCP is like the standard shape of a power socket. Any plug that fits the standard works in any socket, whoever made the lamp.

**Three roles.** The spec names three parts:

- **Host:** the AI app the user works in, such as a chat app or a coding tool. The spec says hosts are the apps "that initiate connections".
- **Client:** a connector inside the host. The host creates it.
- **Server:** a service that gives the host data and actions, for example for a booking system.

```text
host (the AI app)
 |-- client 1 ---- server: bookings     (remote)
 |-- client 2 ---- server: housekeeping (remote)
 |-- client 3 ---- server: offers sheet (local)
```

The [architecture page](https://modelcontextprotocol.io/specification/2026-07-28/architecture) says one host can run many clients. Each client "communicates with exactly one server", a 1:1 link. Every server is reached through its own client. This is true for local and remote servers alike. A **local** server runs on the user's own computer; a **remote** one runs on the internet. The architecture page allows both kinds.

**The host has the big jobs.** On the architecture page, the host:

- creates and manages the clients;
- decides which connections are allowed;
- sets the security rules and the consent rules;
- handles the user's authorization decisions (who may do what);
- coordinates the AI model.

So when you buy an AI app, much of your safety depends on the host, not only on the servers.

**Servers see only what they need.** One design principle in the architecture page matters for privacy: servers "should not be able to read the whole conversation, nor 'see into' other servers". In plain words:

- Each server receives just the context its job needs.
- The host keeps the whole chat.
- If data must move from one server to another, the host controls it.

The principle does not change for local or remote servers, or for servers on your own network.

**What a server can offer.** The [server features page](https://modelcontextprotocol.io/specification/2026-07-28/server) lists three building blocks. Each has a different "who decides" rule:

| Building block | Who controls it | Spec's examples                 |
| -------------- | --------------- | ------------------------------- |
| Prompts        | The user        | Slash commands, menu options    |
| Resources      | The application | File contents, git history      |
| Tools          | The model       | API POST requests, file writing |

All three can put text in front of the model. What differs is **who decides when**. A person picks a prompt. The app attaches a resource. The model chooses to call a tool.

Features can also go the other way. **Elicitation** is one such client feature in the spec: with it, a server can ask the user for more information.

**Consent is the host's job.** The spec's security principles include these:

- "Hosts must obtain explicit user consent before exposing user data to servers".
- "Tools represent arbitrary code execution and must be treated with appropriate caution." (Arbitrary code means any code at all.)
- "Hosts must obtain explicit user consent before invoking any tool".

Then the key line: "MCP itself cannot enforce these security principles at the protocol level". No rule in the protocol stops a tool call. The app's builders must add the consent screens. Our reading: a line in the system prompt asks the model; it does not make a consent screen.

**Support is not the same everywhere.** Many products speak MCP, but each one supports a different part:

- The [Claude MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector) reaches remote servers from the API "without a separate MCP client". It has two limits. Of the MCP feature set, "only tool calls are currently supported", so resources and prompts need another route. And "The server must be publicly exposed through HTTP"; a local server can't be connected directly.
- The [OpenAI MCP guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) connects to a remote server with a `server_url` field. A private server needs a tunnel (chapter 3 covers tunnels).
- The [Gemini function calling page](https://ai.google.dev/gemini-api/docs/function-calling) says its Interactions API can connect to remote MCP servers, but "Remote MCP only works with Streamable HTTP servers". Servers that use the older SSE type are not supported.
- The [Claude Code docs](https://code.claude.com/docs/en/mcp) show coding tools using MCP for tasks such as building a feature from an issue tracker or querying a database.

## Worked example

### Step 1: the weak list

The five lines from the hotel group's requirements list (see The problem).

### Step 2: fix what MCP is and the roles

```text
- MCP is an open protocol. We don't buy it; we choose an
  AI app (the host) and servers that speak it.
- The host runs one client per system: three clients for
  three servers.
```

### Step 3: fix the context

```text
- The host keeps the guest chat. The bookings server gets
  only the booking request, for example "free rooms on
  12 May at the harbour hotel".
- If housekeeping needs a booking date, the host passes it on.
  Servers never read each other directly.
```

### Step 4: sort the features

The team plans three features:

- **A:** staff pick "/late-checkout-reply" from a menu. A person decides when: a **prompt**.
- **B:** the app adds the hotel's house rules to every chat. The app decides: a **resource**.
- **C:** the assistant books a room when it thinks the guest wants one. The model decides: a **tool**.

**The hard case is B.** The house rules change the model's answers, so they feel like a tool. But nobody asks the model to call them; the app attaches them. Ask "who decides when?", not "does the model see it?". The answer is the app, so B is a resource.

### Step 5: fix consent and the vendor's support

```text
- The host shows staff a confirm screen before each room
  booking (tool C). The protocol can't do this for us.
- Our vendor is Anthropic's API connector: tool calls only,
  public HTTP servers only.
  -> A and B need our own MCP client, or another route.
  -> The laptop spreadsheet is not public. Move the offers
     to a server we run, or use a host that supports
     local servers.
```

### Step 6: why it is better

- **Right words.** MCP is an open standard we use, not something we buy; one client per server.
- **Private by design.** Each server gets small pieces of context, and the host keeps the chat.
- **Right building block.** Each feature is sorted by who decides when.
- **Real consent.** A screen in the host, not a hope in the protocol.
- **Fits the vendor.** The plan checks what the chosen connector supports.

## Common mistakes

1. **Calling MCP a vendor's product.** It is an open protocol, so one server can serve apps from several vendors. Fix: ask which host and which servers, not "which MCP".
2. **Sorting by what the model sees.** Prompts, resources and tools can all reach the model. Fix: sort by who decides when it is used.
3. **"Supports MCP" means "supports all of MCP".** Products support different parts and server types. Fix: ask which building blocks and which server types work, before you design.

## Try it

Not graded. Write your answer down before you read the answer.

A law firm sets up MCP for its staff assistant. Find three problems.

```text
- The document server and the billing server both
  receive the full chat, so they "stay in sync".
- The billing server reads case files straight from
  the document server.
- Feature: "/weekly-summary", which a lawyer starts
  from a menu. The team built it as a tool.
```

### Answer

1. **Full chat to servers.** The host keeps the chat. Each server gets only what one request needs.
2. **One server reads another.** Servers should not see into other servers. If data must move, the host passes it on.
3. **Wrong building block.** A lawyer picks "/weekly-summary" from a menu, so a person decides when. That is a prompt, not a tool.

## Recap

- MCP is an open protocol. The AI app is the host; it runs one client for each server, and each server offers data and actions.
- A person picks prompts, the app attaches resources, the model calls tools. Servers see small pieces of context, never the whole chat.
- Consent is the host's job, because the protocol cannot enforce it. Check which parts of MCP each vendor supports.

## Goal

After this lesson you can:

- Find the hidden tokens an integration adds to every request, and price one finished task.
- Use caching and batch discounts, and say when each one does not apply.
- Build a cost view that covers building, running, upkeep and checking, for both build and buy.

## The problem

An energy supplier has a billing helpdesk. Its AI assistant uses 25 tools to look up meter readings, tariffs and payment plans. The demo cost a few dollars. Three months after launch, the monthly bill is many times what the project plan said, and the finance director wants to know why.

The team had priced the assistant like this: "average question 300 tokens, average answer 400 tokens, times the price per million tokens." That sum leaves out most of the bill. This lesson shows what it missed. The guidance below is from each vendor's docs (October 2026). Prices change often, so always read them from the vendor's live page.

## The idea

**Everything is tokens.** Both vendors bill by **tokens**, small pieces of text (a token is often part of a word). Input and output have separate prices. The [Claude pricing page](https://platform.claude.com/docs/en/about-claude/pricing) gives prices per "MTok" (a million tokens). The [OpenAI pricing page](https://developers.openai.com/api/docs/pricing) says "Prices per 1M tokens", with columns for input, cached input and output.

Our example: a token bill is like a phone bill that charges for every word, including the words the app says before you speak.

**The hidden tokens.** An integration adds text you never see on screen:

- **Tool definitions.** Each tool has a name, a description and a **schema** (the list of inputs it takes). The Claude pricing page says tool requests are priced on all input tokens, "including in the `tools` parameter". The [OpenAI function calling guide](https://developers.openai.com/api/docs/guides/function-calling) says function definitions "count against the model's context limit and are billed as input tokens."
- **Tool calls and results.** The Claude pricing page counts the `tool_use` and `tool_result` blocks too. A tool that returns a whole document costs as much as a long question.
- **A tool system prompt.** When you send tools, the Claude API adds its own instructions. The [Claude tool use page](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) lists the size per model, for example "496 tokens" for Claude Haiku 4.5 (with `tool_choice` auto or none).
- **Tool fees.** Some server tools charge per use. The Claude pricing page lists web search at "$10 per 1,000 searches", plus tokens. For MCP, the [OpenAI MCP guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) says you "only pay for tokens" when importing tool definitions or making tool calls: "No additional fees apply per tool call."

**Fewer tools, smaller bill.** The OpenAI function calling guide suggests you "Aim for fewer than 20 functions available at the start of a turn", and calls this "just a soft suggestion". The OpenAI MCP guide adds that many tools "can result in high cost and latency" (latency means waiting time). Its `allowed_tools` setting, and the allowlist in the [Claude MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector), switch off tools you don't need. It is the same control as in the security chapter; here it also saves money.

**Same text, more tokens.** The Claude pricing page says Claude 4.7 and later models use a newer tokenizer (the part that cuts text into tokens). It "produces approximately 30% more tokens for the same text". The page adds: "The exact increase depends on the content and workload shape." Older models, up to Claude Sonnet 4.6, keep the old one. So a model change can raise the bill even when the price per token stays the same.

**Discount 1: caching.** **Prompt caching** reuses an unchanged start of the prompt at a lower price. Tool definitions can be part of that cached start; the Claude caching page lists them first in the order it caches.

- On the Claude pricing page, a cache read costs "0.1x base input price" on most models (a few models are lower). A 5-minute cache write (storing the start so it can be reused) costs "1.25x base input price".
- The [OpenAI caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) says that for GPT-5.6 and later, writes cost "1.25×" the input rate and reads "0.1×" on most of these models. Earlier models use a cached-input price set per model, with "No additional cache-write charge".

The catch: the cached start must stay the same. The [Claude caching page](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) says "Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache". The OpenAI guide lists changes to tool "names, descriptions, schemas, ordering" as changes that affect the cached prefix. One small edit to one tool, and every request pays full price again until the cache is rebuilt.

**Discount 2: batch.** A **Batch API** runs requests later, not live.

- The Claude page lists "a 50% discount on both input and output tokens". The [Claude batch page](https://platform.claude.com/docs/en/build-with-claude/batch-processing) says most batches finish "in less than 1 hour".
- The [OpenAI batch guide](https://developers.openai.com/api/docs/guides/batch) lists a "50% cost discount compared to synchronous APIs", and says "Each batch completes within 24 hours".

Batch fits work nobody waits for: overnight reports, test runs. It does not fit a live chat. The Claude pricing page says batch and caching discounts "can be combined".

**The rest of the bill.** The vendor's page covers model usage only. This four-line view is our own framework:

1. **Build:** engineer time to connect, test and secure the integration.
2. **Run:** model usage per task, times the volume.
3. **Maintain:** hours spent keeping tools, prompts and tests up to date. Vendors retire models (chapter 6).
4. **Review and support:** people who check outputs and handle errors.

**Build or buy?** Buying moves lines 1 and 3 to a supplier, but adds a licence fee and a dependency. Building costs more at the start and gives control. Our advice: compare all four lines for both options over two or three years.

## Worked example

Prices are Claude Haiku 4.5 from the Claude pricing page, checked October 2026: $1 per MTok input, $5 per MTok output, $0.10 per MTok cache hit. The workload is our own made-up example.

### Step 1: the weak estimate

```text
150,000 requests a month
question  300 tokens -> 45M tokens x $1 = $45
answer    400 tokens -> 60M tokens x $5 = $300
Estimate: $345 a month
```

What goes wrong: the 25 tool definitions are missing. They take 4,000 tokens and go out with every request.

### Step 2: the honest sum

```text
tool definitions  4,000 tokens -> 600M tokens x $1 = $600
question            300 tokens ->  45M tokens x $1 =  $45
answer              400 tokens ->  60M tokens x $5 = $300
Total: $945 a month (before tool results and the tool system prompt)
```

The definitions are the biggest line, and the user typed none of it.

### Step 3: cut and cache

- Load only the 12 tools the helpdesk needs. Definitions fall to about 2,000 tokens: 300M tokens, or $300.
- Cache them. At the cache-hit price, 300M tokens cost about $30 (we ignore the write cost to keep it simple).
- New total: $30 + $45 + $300 = **about $375**, down from $945.
- Freeze tool edits into one planned release a month, so the cache is not broken every few days.

### Step 4: the hard case

**The hard case: IT wants to move to a newer Claude model, with no change to the price per token.** It looks free. But a 4.7-or-later model uses the newer tokenizer: about 30% more tokens for identical text. On the input lines above, $75 of input becomes about $98. Output tokens are counted with the new tokenizer too. The real rise varies with your text, so run a week of real requests through both models and compare the token counts before you sign off.

### Step 5: move the night job

The helpdesk also writes summaries of 40,000 closed calls every Sunday night for the Monday team meeting. Nobody reads them before 10 am. Through a Batch API, that job costs half.

### Step 6: why it is better

- **Priced per task**, with the biggest hidden line included and the rest named.
- **Discounts used where they fit**, and their conditions named.
- **Model changes tested**, not assumed to cost the same.

## Common mistakes

1. **Pricing only questions and answers.** Tool definitions, calls and results are input tokens on every request. Fix: count them in the per-task price.
2. **Editing tools whenever someone has an idea.** Each change breaks the cache. Fix: group tool changes into planned releases.
3. **Comparing only the licence fee with the model bill.** Build, upkeep and review time are real costs. Fix: use the four-line view for both build and buy.

## Try it

Not graded. Write your answer down before you read the answer.

A team runs 50,000 requests a month. Tool definitions are 2,000 tokens. Use made-up prices: $2 per MTok input, $0.20 per MTok cache read. Answer three questions.

```text
1. What do the definitions cost a month, uncached?
2. About what do they cost if read from cache
   (ignore writes)?
3. A weekly report job runs at 3 am; results are read
   at noon. Which discount fits?
```

### Answer

1. 2,000 × 50,000 = 100M tokens. At $2 per MTok, that is **$200**.
2. 100M tokens at $0.20 per MTok is **$20**, if the definitions don't change.
3. **Batch.** Nobody waits for the result, and both vendors list 50% off.

## Recap

- Tool definitions, calls and results all count as input tokens in each request. Price one finished task, not a million tokens.
- Caching and batch can each cut the bill, but caching needs stable tools and batch needs work nobody waits for.
- A model change can change the token count. Count building, running, upkeep and checking costs over several years.

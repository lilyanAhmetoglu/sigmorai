## Why it matters

In realm 0 you learned habits for one person: use the approved tool, share the minimum, never paste secrets. A company of 2,000 people can't run on habits alone. It needs an **AI policy**: written rules that say who may use which AI tools, with which data, and who checks the results.

A policy only works if the tools back it up. This chapter shows how vendor settings turn a rule on paper into a rule that the system enforces.

## Five parts of a policy

This list is a tool for this course, not a legal template. A useful AI policy answers five questions:

1. **Tools and accounts.** Which AI tools and accounts are approved?
2. **Data.** Which kinds of data may go into which tool?
3. **Review.** When must a person check the output before it is used?
4. **Access.** Who may create keys, change settings and see usage?
5. **Reporting.** How do staff and customers report a problem, and who answers?

Example: a furniture retailer writes "staff may use AI for marketing drafts". That covers part 1 only. It says nothing about customer data, review, access or reporting.

## Part 1 and 2: tie data rules to settings

The data terms depend on the account and its settings, so a policy should name them.

- **Retention settings can differ inside one company.** OpenAI's data controls page says approved customers can set Zero Data Retention or Modified Abuse Monitoring for the whole organization. Each project can inherit that setting, pick its own, or select "None" to turn the controls off for that project.
- **Anthropic sets zero data retention (ZDR) per organization.** Its docs say each new organization needs ZDR enabled separately, and it doesn't automatically extend to other organizations under the same account.
- **Not every product or model is covered.** Anthropic's docs list the Console and its playground as not covered by ZDR. They also list some models, called Covered Models, that require 30-day data retention.

So "we have zero data retention" is not a complete rule. Example: the retailer's data team opens a new project for a pilot. If nobody checks its retention setting, it may not match the company rule. A better rule: "Customer data goes only into projects where the approved retention setting is on. IT checks this before a project goes live."

## Part 3: say when a person reviews

OpenAI's safety guide recommends that, wherever possible, a human reviews outputs before they are used. It says this is especially critical in high-stakes domains. It adds that reviewers should know the system's limits and have the information they need to check the output, such as the original notes behind a summary.

A policy turns this into a rule per use. Example: "Marketing drafts: the author reviews. Replies about refunds: a support lead approves before sending." The next chapter, Risk tiers, shows how to sort uses into levels.

## Part 4: control access and keys

An API key is like a door key to your AI account. Policy should say who holds keys and how long they live.

- OpenAI's production guide strongly recommends an expiration date on project API keys and a regular rotation process. It says administrators can enforce a maximum key lifetime, and restrict which types of keys can be created.
- Anthropic's Admin API page lists five organization roles. A developer can manage API keys; the admin role can also manage users. Its best practices include auditing member roles regularly and rotating keys periodically.
- Anthropic's workspaces page says workspaces can separate teams or projects, each with its own members, API keys and limits.

Example: at the retailer, every developer is an admin "to save time". A policy rule fixes this: give each person the smallest role they need, and review roles every quarter.

## Part 5: let people report problems

OpenAI's safety guide says users should have an easy way to report problems, such as an email address or a ticket form. A human should monitor it and respond. The same guide tells you to understand and communicate the system's limits, so users' expectations match what it can do.

Example: the retailer's chat assistant gets a "Report a problem" link. The reports go to a named team, not to a shared inbox that nobody reads.

## Write rules people can follow

A long policy that nobody reads doesn't protect anyone. Keep each rule short and testable: "IT checks the retention setting before go-live" can be checked. "Use AI responsibly" can't.

## Key points

- An AI policy covers tools, data, review, access and reporting (a tool for this course).
- Data rules should name the settings behind them: retention controls can differ per project or organization.
- Vendor docs list products and models that a retention option doesn't cover; check before you promise.
- Human review is recommended wherever possible, especially for high-stakes uses.
- Give the smallest role needed, set key expiry and rotation, and audit roles regularly.
- Give users a monitored way to report problems.

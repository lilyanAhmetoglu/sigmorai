## Goal

After this lesson you can:

- Run an AI incident in five steps: spot, contain, investigate, tell, learn.
- Choose the smallest action that ends the harm, and know which steps can't be undone.
- Write the first message to the people affected, with only the facts you have checked.

## The problem

An online grocery company has 1,100 staff. Its app has an AI helper for order questions, and its warehouse team uses an AI tool to plan delivery routes. Both call the Claude API.

On a Sunday, a developer copies the order helper's API key into a public code page by mistake. By Monday morning, the AI bill for the weekend is many times a normal weekend. The key sits in the company's Default Workspace, next to the route tool's key.

On Monday nobody knows who leads. One person wants to shut down every AI tool in the company. Another wants to email all customers that "no data was affected", before anyone has checked.

Every one of these ideas is fast. None of them is a plan. The vendor facts in this lesson come from each vendor's docs (October 2026).

## The idea

Controls lower risk; they do not remove it. An **incident** is any event that harms people, data or money: a wrong answer to a customer, a leaked key, or a bill that runs out of control overnight.

No vendor publishes an incident plan for your company. Our advice is a five-step plan:

```text
1 Spot  ->  2 Contain  ->  3 Investigate  ->  4 Tell  ->  5 Learn
```

Name one **incident owner** for each AI use before anything goes wrong. A plan with no named person is a plan that waits. Think of a fire drill: the exits, the meeting point and the person who counts heads are set before the fire.

**Step 1: Spot.** Simple signals catch most problems, but only if a person reads them.

- **A report channel.** The [OpenAI safety guide](https://developers.openai.com/api/docs/guides/safety-best-practices) says users should have an easy way to report problems, and that "This method should be monitored by a human and responded to as appropriate."
- **Spend alerts.** The [OpenAI production guide](https://developers.openai.com/api/docs/guides/production-best-practices) says to set spend alerts "to send notifications when usage exceeds a certain dollar amount." The [Claude workspaces page](https://platform.claude.com/docs/en/manage-claude/workspaces) lets you cap monthly spend per workspace and "configure alerts when spending reaches certain thresholds."
- **Output checks.** The [Claude jailbreak guide](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks) says: "Regularly analyze outputs for signs of successful injection." It adds that what you learn should improve your prompts, filters and input checks.
- **Per-user identifiers.** These tie each request to one end user, so you can find one bad actor fast. The OpenAI safety guide recommends a `safety_identifier` for products where individual users talk to a model. It says this can help your team "respond to abuse faster". The [Claude Messages API reference](https://platform.claude.com/docs/en/api/messages/create) has a similar field, `metadata.user_id`. It says: "Anthropic may use this id to help detect abuse."

**Step 2: Contain.** Stop the damage first; fix the cause later. Our advice: choose the smallest action that ends the harm, and one you can reverse.

- **Turn off one key.** The [Claude Admin API page](https://platform.claude.com/docs/en/manage-claude/admin-api) says the API "can only read, rename, and change the status of existing keys". Its example sets a key's status to `inactive`. The OpenAI safety guide says that if a key may be exposed, "revoke it promptly and replace it with a new key."
- **Lower the limits.** Claude workspace spend and rate limits can be set lower than the organization's.
- **Deal with one user.** The Claude jailbreak guide suggests "throttling or banning users who repeatedly attempt to circumvent your application's guardrails."

Two steps look strong but can fail or go too far:

- **Removing a person.** On the Claude Admin API page, a personal key ends when its user leaves the organization, but "Workspace API keys continue to work." There is one exception: "In the Claude Code workspace, each key is bound to the member who created it and stops working when that member is removed."
- **Archiving a workspace.** The Claude workspaces page says this archives every API key created for that workspace, and it "Cannot be undone".

**Step 3: Investigate.** Logs answer "who changed what, and when".

- The [OpenAI Admin APIs page](https://developers.openai.com/api/docs/guides/admin-apis) has an Audit Logs endpoint for "recent user actions and configuration changes for the organization."
- The [Claude Activity Feed page](https://platform.claude.com/docs/en/manage-claude/compliance-activity-feed) says recording "begins when the Compliance API is first enabled for your organization". Logs help only if they were on before the incident.

**Step 4: Tell.** This step is our own advice, not a vendor rule. Before any incident, decide who tells legal and the data protection lead, who writes to the people affected, and who talks to the vendor. In a first message, write only what you have checked. "We found a problem, we are checking it, and we will write again by Thursday" is true. "No data was affected" may not be. Your legal team sets the deadlines that apply to you.

**Step 5: Learn.** Our advice: add the real case to your tests, fix the control that failed, and fix the policy rule behind it. The OpenAI safety guide recommends "red-teaming": testing with normal inputs and with inputs from someone trying to break the app. The Claude jailbreak guide says to red-team your agent "Before deploying". Write the review about the system, never about one person. When people fear blame, they hide the next problem.

## Worked example

### Step 1: the weak plan

```text
AI incident plan v1
If something goes wrong with AI, call IT.
```

What goes wrong:

- **Spot:** nobody looked at spend until Monday.
- **Contain:** "call IT" gives no first step, so people grab the biggest switch.
- **Tell:** nobody owns the message, so a guess almost went to every customer.

### Step 2: one owner and one first step per step

Our example plan for the grocery company:

```text
Owner        Head of platform (deputy: lead developer)
1 Spot       Spend alerts go to the on-call phone, read 24/7.
             App report form goes to support, answered same day.
2 Contain    Leaked key: set it to inactive and make a new one.
             After that, move each tool to its own workspace
             with its own spend limit.
3 Investigate  Audit logs on since launch. Owner pulls them.
4 Tell       Legal and data protection lead within 1 hour.
             Customer message only after legal checks the facts.
5 Learn      Write-up in 5 days. Add the case to tests.
             Fix the rule that failed.
```

The 1 hour and the 5 days are our own choices, not vendor numbers.

### Step 3: run Monday with the plan

- **Contain:** the owner sets the leaked key to inactive and makes a new one for the order helper. The route tool keeps working.
- **Investigate:** the owner checks the audit log to see if any settings changed over the weekend. Until that check is done, it is a question, not a fact to announce.
- **Tell:** legal decides whether anyone outside must be told. Any message says what is known and when the next update comes.

### Step 4: the hard case

**The hard case is the Default Workspace.** Someone says "lower the workspace spend limit". But the leaked key and both tools are in the Default Workspace, and the Claude workspaces page says: "You cannot set limits on the Default Workspace". The same page says the Default Workspace "cannot be renamed, archived, or deleted."

The fix: contain by the key. Set it to inactive and make a new one. Then, as a Learn action with an owner, move each tool to its own workspace, so the next incident can be capped there.

### Step 5: why it is better

- **Fast and small.** One key off, one new key on. Nothing else stops.
- **Reversible.** The [Claude update API key reference](https://platform.claude.com/docs/en/api/admin/api_keys/update) lists `active` as a status you can set, so a key can be turned on again. An archived workspace can't come back.
- **Honest.** No message goes out with a guess in it.

## Common mistakes

1. **No owner named before the incident.** On the day, people argue about who leads. Fix: name an owner and a deputy for each AI use now.
2. **One shared key for every tool.** When it leaks, turning it off stops everything. Fix: one key per tool, so you can turn off just one.
3. **Testing the plan for the first time in a real incident.** Gaps show up when it costs most. Fix: walk through it once a year with a made-up case, like a fire drill.

## Try it

Not graded. Write your answer down before you read the answer.

A team will add a per-user identifier to every request. Which of these values follow both vendors' docs?

```text
1. The customer's email address
2. A hash of the customer's account number
3. A session ID for a guest who is not signed in
```

### Answer

1. **No.** The Claude reference says: "Do not include any identifying information such as name, email address, or phone number." The OpenAI guide says to hash the username or email.
2. **Yes.** The Claude reference asks for "a uuid, hash value, or other opaque identifier". A hash hides who the person is.
3. **Yes, for OpenAI.** The OpenAI guide says: "If you offer a preview of your product to non-logged in users, you can send a session ID instead." Our reading: the Claude reference names no session rule, but an opaque session ID fits its wording.

## Recap

- Use five steps: spot, contain, investigate, tell, learn (our list). Name an owner and make sure a person reads every alert and report.
- Contain with the smallest step that can be undone, such as setting one key to inactive. Removing a person may not stop a workspace key; archiving a workspace can't be undone.
- Logs help only if they were on before. Tell only checked facts, and learn by adding the case to your tests and fixing the rule that failed.

## Why it matters

A pilot with 60 volunteers is not a company. In realm 2 you learned to run a pilot with a go, change or stop rule. In realm 7 you learned controlled rollouts, champions and adoption. This chapter joins them into a **rollout plan**: how a proven pilot grows to the whole company without breaking things.

The plan has four parts: waves, environments, limits and a way back.

## Part 1: Roll out in waves

A **wave** is a bigger group that gets access at the same time. This wave model is ours, not a vendor standard. A simple version has four waves: the pilot, one department, several departments, then everyone.

OpenAI's guide on ChatGPT Work usage and cost describes the same idea for a controlled rollout. Pick a limited group and a workflow you can evaluate. Compare usage with the baseline. Review outcomes and the real billing impact before you expand.

Give each wave:

- **an entry gate:** what must be true before it starts,
- **a stop rule:** what makes you pause or go back,
- **an owner:** one named person.

Example: a logistics firm has 3,000 staff. Its waves are 60, then 300, then 1,000, then everyone. Wave 2 starts only when the pilot's go rule is met and support tickets are under control.

## Part 2: Verify controls before each wave

Settings that are not tested are only hopes.

- Anthropic's Claude Code admin guide says that after you configure managed settings, a developer runs `/status` and checks that the setting source shows the enterprise managed settings.
- OpenAI's ChatGPT Enterprise rollout guide, in its step on verifying local and cloud execution policies, says to test an action the policy should allow and an action it should block. If a restriction does not work as expected, resolve the issue before users rely on it.

Make this a gate item. Example: before wave 2, an IT lead tries to do one allowed task and one blocked task with a wave 2 account, and writes down the result.

## Part 3: Separate environments

Do not test on the system your staff use.

- Anthropic's workspaces page suggests separate workspaces for development, staging and production. Development gets lower rate limits, and production gets full limits with monitoring.
- OpenAI's production guide says that as you scale, you may want separate projects for staging and production.

Example: the logistics firm lets testers use a staging workspace with a small monthly cap. A test script gone wrong cannot use up the production budget.

## Part 4: Set limits before volume arrives

Limits protect your budget and your service.

- Anthropic's workspaces page says workspace spend and rate limits can be set lower than, but not higher than, the organization's limits. Organization-wide limits always apply.
- It also says the Claude Code workspace is the only workspace that supports per-user monthly spend limits.
- OpenAI's rate limits page says limits are defined at the organization and project level, not at user level.
- OpenAI's production guide says to set spend alerts.

Example: finance sets a monthly cap per wave, with an alert at a set share of the cap. If wave 2 uses the budget in a week, you find out in week 1.

## Part 5: Ramp traffic gradually

Rate limits are not only about size. OpenAI's rate limits page says a `slow_down` error means your request rate increased too quickly. Its rule of thumb: once traffic reaches 1 million input tokens per minute, increase it by no more than 50% every 15 minutes. The exact point varies by model and traffic. It also says a 429 error is a rate limit error, while overload is a different error (503).

A business reader does not need the maths. The lesson is this: do not switch on 2,000 people in the same minute if the tool calls an API. Start teams in steps and watch the error rates. (This advice is OpenAI's. Check your own vendor's page for its rules.)

## Part 6: Plan the way back

A rollback plan answers three questions:

1. **Trigger:** what exact event means "go back"? (For example, a serious incident from chapter 4, or a wrong answer in a high-tier use.)
2. **Action:** how do we stop it, and who may press the button? (For example, turn off a key or lower the limits.)
3. **Fallback:** what do staff do meanwhile? (For example, the old manual process.)

Keep the old process alive until the new one has passed a few review cycles. Example: the logistics firm keeps its manual checklist for six weeks after wave 4.

## Part 7: Help people through each wave

Realm 7 covered training, champions and adoption. For each wave, plan the same three things: a short training, a named champion per team, and a place to ask questions. Measure use per team, not only in total.

## Key points

- Grow in waves, each with an entry gate, a stop rule and an owner (a tool for this course).
- Test that controls work before each wave, with one allowed and one blocked action.
- Use separate environments; keep testing away from production.
- Set spend and rate limits first; workspace limits can only be at or below the organization's.
- Ramp traffic in steps; OpenAI warns that fast growth triggers `slow_down` even inside the limits.
- Write the rollback plan before the launch: trigger, action, fallback.

## Goal

After this lesson you can:

- Place an option on the scale from "we build it" to "the vendor runs it".
- Pick the lightest option that covers your mapped steps, your data rules and your team's skills.
- Ask the questions that find hidden data-access and upkeep risks.

## The problem

The marketing team of a retail chain wants a weekly brief on competitor promotions. It should read public websites and the chain's own sales notes, then write a two-page summary every Monday. Later, the team wants the AI to suggest promotions and add them to the chain's own promotions system.

One manager says, "Just buy a tool." An engineer says, "We should build it ourselves." Both are partly right. This lesson shows the options in between and how to choose. The guidance below is from each vendor's docs (October 2026).

## The idea

**Build vs buy is a scale.** The [Claude docs](https://platform.claude.com/docs/en/about-claude/use-case-guides/overview) describe three paths that "differ in how much control you keep and how much of the implementation you offload to Anthropic":

- **Messages API:** the most control. You write the loop yourself and run your own tools and servers. The **agent loop** is the code that lets the model use a tool, read the result and decide the next step.
- **Claude Agent SDK** (SDK = a software kit for developers): in the middle. It gives you the loop and runs the tools, but you operate the process.
- **Claude Managed Agents:** you hand over the most. Anthropic hosts "the agent loop", "tool execution", and "runtime" for you.

The [OpenAI docs](https://developers.openai.com/api/docs/guides/agents) offer a similar set and rate the "Agent integration effort" for each:

```text
Option          Where the agent runs                    Effort
Agents API      "OpenAI runs a managed Codex harness"   Low
Agents SDK      inside your own application             Medium
Responses API   your application                        High
```

A **harness** here is the vendor's own setup that runs the agent for you. The OpenAI docs say the Agents API is for "Long-running tasks", and that OpenAI "manages the agent" and "saves its progress".

The Responses API is for "Calling models directly or building an agent from scratch". The same page points to ChatKit to "Add an embedded chat experience".

**Ready-made products sit at the "buy" end.** An [OpenAI cookbook](https://developers.openai.com/cookbook/articles/chatgpt-agents-sales-meeting-prep) builds a ChatGPT **workspace agent** through a "conversational builder": you describe the agent in plain words. It says these agents are "Currently available in research preview for ChatGPT Business, Enterprise, and Edu customers". You can start "from pre-built agent templates".

**Ready-made still needs owners.** Before you build, the cookbook asks the workspace admin to confirm settings, such as "Agents are enabled for your workspace" and "The apps you need are enabled". It also shows a data risk. A connected app can use each user's own login, or one **agent-owned account** shared by the agent. With the shared account, "anyone we share the agent with will be able to access the SharePoint resources". Admins can limit an agent to "read actions, but not write actions".

**Build only as much as you need.** The [Anthropic post on agents](https://www.anthropic.com/engineering/building-effective-agents) recommends "finding the simplest solution possible". It warns that frameworks add layers that "obscure" the prompts and replies underneath, which makes problems "harder to debug". They can also make it "tempting to add complexity when a simpler setup would suffice". Wrong ideas about what a framework does inside are, it says, "a common source of customer error".

**Expect change.** The same post now carries a note: "Much of the tooling landscape described in this post has changed since December 2024." So keep your own map, success criteria and test examples. They stay useful when you switch tools.

Our example: dinner for guests. You can cook from raw ingredients (most control), use a meal kit (the recipe and steps come in the box, you cook at home), or book a restaurant (least work, least control over what goes in).

## Worked example

### Step 1: the weak choice

```text
Plan: build our own agent from zero on a raw model API.
Reason: "We want full control."
```

What goes wrong: the chain has one part-time developer. Phase 1 needs no custom system. They would spend months on an agent loop that a product already offers.

### Step 2: check the steps against the options

```text
Phase 1 steps                        Needs custom code?
Read public competitor web pages     no (web search)
Read sales notes in shared docs      no (connected app)
Write a 2-page brief each Monday     no (schedule + template)
```

All phase 1 steps fit a ready-made workspace agent the chain already pays for.

### Step 3: set up access (the hard case)

The first draft connects the shared-docs app with one agent-owned account. This account is also able to open the finance folder with supplier margins. The plan is to share the agent with all 120 store managers.

**This is the hard case.** Every store manager could reach supplier margins through the agent. The fix:

```text
- Connect the docs app with each user's own login, or
- give the agent account access to the sales-notes folder only.
- Allow read actions only. The brief is saved by a person.
- Share with the marketing team of 8 first, not all 120.
```

### Step 4: plan phase 2

Phase 2 must write suggested promotions into the chain's own promotions system. IT wants that data to stay in the chain's own setup and does not want to write an agent loop. That points to the middle of the scale: an **agent SDK**, such as the Claude Agent SDK or the OpenAI Agents SDK. The SDK handles the loop and calls the tools, and the chain runs it itself. Before agreeing to any framework, ask: "Show me the prompts and calls it really makes."

### Step 5: why it is better

- **Fast start.** Phase 1 runs on a product the chain already has.
- **Safe data.** Access is checked before sharing, not after.
- **Right amount of build.** Code only where the product can't reach (phase 2).
- **Easy to switch.** The map, criteria and test briefs belong to the chain.

## Common mistakes

1. **Building from scratch by default.** It costs months when a product covers the steps. Fix: check each mapped step against the lightest option first.
2. **Trusting the demo.** Demos skip data access and admin setup. Fix: ask who can see which data through the agent, and who keeps it up to date.
3. **Adding a framework nobody can explain.** Hidden prompts make problems hard to debug. Fix: ask to see the real prompts and calls before you agree.

## Try it

Not graded. Write your answer down before you read the answer.

For each team, choose a point on the scale: ready-made workspace agent, agent SDK, vendor-hosted agent, or direct model API. Give one reason.

```text
1. A small legal team wants a weekly digest of new court rulings.
   No developers. The firm already pays for an AI workspace.
2. A bank's engineers need an agent that writes into their own
   loan system. Data must stay in the bank's own setup. They
   would rather not code the loop themselves.
```

### Answer

1. **Ready-made workspace agent.** No developers, and the workspace covers reading, summarizing and scheduling. Check what data each connected app can reach before sharing.
2. **Agent SDK.** The SDK handles the loop and the tool calls, while the bank runs it itself. A vendor-hosted agent breaks the data rule, and a direct API means writing the loop.

## Recap

- Build vs buy is a scale. Anthropic and OpenAI both offer a direct API, an SDK and a vendor-hosted option. Ready-made products, such as ChatGPT workspace agents, sit at the "buy" end.
- Pick the lightest option that covers your mapped steps, data rules and skills. Check data access and owners before you share.
- Build only as much as you need, ask to see what a framework really does, and keep your own map, criteria and tests so you can switch.

## Goal

After this lesson you can:

- Spot a hallucination, even when it sounds sure.
- Rewrite a prompt with four simple techniques that lower the risk.
- Decide how much human checking a task needs, based on what a mistake costs.

## The problem

A procurement lead must compare two software vendors by Friday. Vendor A sent a 60-page proposal. She asks an AI assistant: "Summarize this proposal and its main terms."

The summary is clear and well written. One line says: "Includes free data export when the contract ends." She almost copies it into her recommendation. Then she searches the proposal. It says nothing about data export.

The sentence sounds normal, and that is why it is dangerous. This lesson shows how to make this rarer, and how to catch it when it happens. The techniques below come from the vendors' docs (October 2026).

## The idea

A **hallucination** is text that sounds right but is not. The [Claude docs](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations) describe it as text that is "factually incorrect or inconsistent with the given context". They add that "even the most advanced language models" can do this.

Two kinds matter at work:

- **Wrong facts.** A date, a number or a rule that is not true.
- **Not in your document.** The model "quotes" or summarizes something your file does not say.

**Confident is not the same as correct.** The [Claude glossary](https://platform.claude.com/docs/en/about-claude/glossary) says LLMs "generate human-like text". Fluent text sounds sure, but the tone tells you nothing about the facts.

Our example: a hallucination is like a colleague who fills a gap in a meeting with a guess, in the same calm voice they use for facts.

**Four techniques you can use in any chat.** All come from the Claude guide:

1. **Allow "I don't know."** Give the model permission to say it is unsure. The guide says this "can drastically reduce false information".
2. **Quotes first.** For long documents (the guide says over 20k tokens), ask for "word-for-word quotes first", then do the task from those quotes.
3. **Cite and check.** Ask for a supporting quote for each claim. "If it can't find a quote, it must retract the claim."
4. **Only your documents.** Tell the model to use only the documents you gave it, "not its general knowledge".

The guide also lists **best-of-N**: run the same prompt several times and compare. "Inconsistencies across outputs could indicate hallucinations."

Two warnings:

- **Send the right documents, not all of them.** The [OpenAI accuracy guide](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy) says too much irrelevant context "drowns out the real information and causes hallucinations".
- **The risk gets lower, not zero.** The Claude guide says the techniques "don't eliminate them entirely" and adds: "Always validate critical information, especially for high-stakes decisions."

So match the checking to the cost of a mistake. In one example in the OpenAI guide, "where the cost of failure was very high", the team decided "the human would drive and the AI would function as an assistant."

## Worked example

### Step 1: the first prompt

```text
Summarize this proposal and its main terms.

[vendor-a-proposal.pdf, 60 pages]
```

What goes wrong:

- Nothing allows the answer "the proposal doesn't say".
- Nothing ties each line to the text, so a made-up term looks the same as a real one.
- Nothing stops the model from filling gaps with what proposals "usually" include.

### Step 2: the better prompt

```text
I am comparing software vendors. Use ONLY the attached proposal.
Do not use general knowledge about typical contracts.

Step 1: Copy, word for word, every sentence about price, contract
length, support hours, data export and ending the contract.
Number each quote.

Step 2: Using only those quotes, fill in this table:
Term | What the proposal says | Quote number

Step 3: Check each row. If no quote supports it, delete the row
and write "removed: no quote".

If the proposal says nothing about a term, write
"Not in the proposal". Do not guess.

[vendor-a-proposal.pdf, 60 pages]
```

### Step 3: the hard case

Data export is the hard case. The proposal is silent on it, so the first prompt invented a friendly answer. With the new prompt, the row reads "Not in the proposal". **That gap is useful.** It becomes a question for the vendor before she signs.

### Step 4: why it is better

- **"I don't know" is allowed**, so a gap shows up as a gap.
- **Quotes first** keeps the summary tied to the real text of a long document.
- **Cite and check** makes every row easy to verify: she opens quote 7 and reads it.
- **Only your documents** stops "typical contract" guesses.

### Step 5: set the checking level

Our advice: decide the review step by what a mistake would cost.

```text
Internal notes from the vendor call   -> AI drafts, she skims
Comparison table for the decision     -> she checks every quote in the PDF
Final choice and contract signature   -> people decide; AI only prepares
```

## Common mistakes

1. **Trusting the tone.** A calm, detailed answer is not proof. Fix: treat every number, name, date and quote as something to check.
2. **Asking for "more detail" to fix it.** Longer answers give more room for unsupported claims. Fix: ask for quotes and allow "not in the document".
3. **Skipping review because the prompt is better.** The techniques lower the risk but don't remove it. Fix: keep a human check wherever a mistake is costly.

## Try it

Not graded. A marketing manager uses this prompt for a customer newsletter. The draft says the new version is "40% faster". The product notes give no speed figure. Name the problem and rewrite the prompt.

```text
Write an exciting newsletter about our new product version.
Make it sound impressive.

[product-notes.docx]
```

### Answer

The problem is a **hallucination**: a claim that is not in the given notes. "Make it sound impressive" also pushes the model to add claims. A better prompt:

```text
Write a newsletter about our new product version.
Use only facts from the attached product notes.
After the draft, check each claim. If no sentence in the notes
supports it, remove it and mark the place with [ ].
If the notes don't cover something, leave it out.

[product-notes.docx]
```

A person still checks every number before it goes to customers, because public claims are costly to get wrong.

## Recap

- A hallucination is false or unsupported text, often said with confidence.
- Four prompt techniques lower the risk: allow "I don't know", quotes first, cite and check, only your documents. Running a prompt more than once can expose a guess.
- No technique makes the risk zero. Match the human checking to the cost of a mistake.

## Why it matters

Once AI tools reach a team, three questions come up fast. Who may use what? Who owns each workflow and each shared prompt or skill? What can people do that they could not do before?

If nobody answers, the answers appear by accident. The most eager person becomes an admin. Shared tools have no owner. This chapter gives you a simple way to answer all three.

## Access: seat, admin role, custom role

OpenAI's guide on roles and workspace permissions separates three things in ChatGPT Enterprise:

- A **seat** decides which product surfaces a member can use.
- A **built-in role** decides administrative power. Owner manages workspace-wide settings, Admin manages supported operations and groups, Member has no admin rights, and Analytics Viewer can open workspace analytics.
- A **custom role** decides which supported features a member can use. It does not replace the seat, and it does not grant rights in a connected system.

The rollout guide adds a short rule: keep built-in administration roles limited to the people who administer the workspace.

Anthropic's Claude Code analytics page also splits setup by role. Admins and Owners can view the dashboard. Only an Owner can turn on contribution metrics, and a GitHub admin must install the GitHub app.

Example: a pilot lawyer needs to try the tool every day. She needs a seat and a feature role. She does not need the Admin role.

## Access stops at the next system

OpenAI's page lists six control boundaries: the workspace, local clients, Codex cloud (hosted coding tasks), the API platform, plugins and connected systems. It says a request must pass every boundary that applies. Workspace access can make a plugin available, but the connected service still decides what the signed-in account can read.

So a new AI role does not open the filing system. The filing system's own permissions still apply. Check them as a separate item in your rollout plan.

## Name an owner for every part

OpenAI's rollout guide starts by assigning an owner for each part: workspace access, local runtime policy, Codex cloud (hosted coding tasks), connected systems, and reporting and compliance.

Anthropic's Claude Code guide frames setup as a series of decisions: where the tool signs in, how settings reach devices, what to enforce, how to track usage, and how to handle data.

For a business team, here is a simple role map. It is our own tool for this course, not a vendor standard:

| Role           | Question it answers                                            |
| -------------- | -------------------------------------------------------------- |
| Sponsor        | Why are we doing this, and who funds it?                       |
| Workflow owner | Is this workflow working, and does it still need to exist?     |
| Builder        | Who made the prompt, skill or agent?                           |
| Reviewer       | Is it safe and correct? (A different person from the builder.) |
| Users          | Who does the daily work with it?                               |

One person can hold more than one role, with one limit: the builder should not be the only reviewer.

## Skills are shared assets

A **skill** is a packaged set of instructions, and sometimes scripts, that an AI tool loads when a task needs it. Think of it as a written procedure, like an onboarding guide for a new colleague. Anthropic and OpenAI both support skills, so the management questions are the same.

Anthropic's "Skills for enterprise" page describes a lifecycle: plan, create and review, test, deploy, monitor, then iterate or deprecate. Three of its rules matter to managers:

1. **Separate duties.** Skill authors should not be their own reviewers.
2. **Keep a registry.** For each skill, record purpose, owner, version, dependencies and evaluation status.
3. **Start narrow.** Begin with specific, workflow-level skills. Merge them into a broader one only when the evaluations show equal performance.

The same page lists risk signs to check before approval. Scripts that run code and calls to outside web addresses are rated high concern. So are instructions that name connected tools.

OpenAI's rollout guide asks for similar facts before a plugin or skill joins the rollout. Confirm its source, accountable owner, intended audience and review date. Test it with non-sensitive data and the least access it needs. Record who owns re-review and retirement.

Example: a finance analyst builds a skill that formats the monthly report. It runs a script and has no owner after she changes jobs. Under these rules it needs a named owner, a reviewer who is not the analyst, and a review date.

## Skills people need

Roles also change what people must be good at. This list is ours, not a vendor's:

- **Briefing:** write a clear task with a goal, a format, sources and limits (chapter 1).
- **Checking:** compare output with the source before it goes out (chapter 2 sets the review points).
- **Escalating:** know when to hand a case to a person.

Plan time to teach these three, not only how to open the tool.

## Key points

- A seat, an admin role and a custom role are three different things.
- Keep admin roles for people who administer; give everyone else the feature role they need.
- Access in an AI tool does not open other systems; those systems keep their own rules.
- Give every part of the rollout, and every shared skill, a named owner.
- Authors should not be their own reviewers; keep a registry and review dates.

## Goal

After this lesson you can:

- Give each person the right kind of access: a seat, a built-in role or a custom role.
- Explain why access in an AI tool does not open the other systems it connects to.
- Run shared skills like company assets: a named owner, a separate reviewer, a registry and a review date.

## The problem

An engineering consultancy with 350 staff ran a one-year AI pilot. It went well. Now the bid team, the marketing team and two project teams use the assistant every day. They also built 22 shared **skills**. A skill is a packaged set of instructions, and sometimes scripts, that the AI tool loads when a task needs it. Think of it as a written procedure for a new colleague.

Nobody planned roles. Ten people hold the Admin role "so they can try things". The finance controller wants monthly usage reports, so the controller got Admin too. One skill sends draft bids to an outside translation website. Nobody knows who built it. A bid manager asks: "My AI seat is new. Can the assistant now read every project folder on the file server?"

The chief operating officer wants this in order before the tool opens to all staff. The guidance below comes from the OpenAI ChatGPT Enterprise docs and the Claude docs (October 2026).

## The idea

**Three kinds of access.** The OpenAI page [Roles and workspace permissions](https://learn.chatgpt.com/docs/enterprise/roles-and-workspace-permissions) separates three things in ChatGPT Enterprise:

- A **seat** decides which parts of the product a person can reach. The page calls them "product surfaces".
- A **built-in role** decides administrative power. The page lists four:
  - **Owner**: "manages workspace-wide settings".
  - **Admin**: "manages supported operations and groups".
  - **Member**: "doesn't have administrative rights".
  - **Analytics Viewer**: "can access workspace analytics".
- A **custom role** sets the features a person may use. It does not replace the seat. It does not give rights in a connected system.

The page adds: "Only workspace owners can configure role-based access control (RBAC) and create custom roles." The [OpenAI admin rollout guide](https://learn.chatgpt.com/docs/enterprise/admin-setup) gives a short rule: "Keep built-in administration roles limited to the people who administer the workspace." Our comparison: a seat is a ticket to the building, a custom role is a key to some rooms, and Admin is the master key.

The Claude Code side splits roles too. The [Claude Code analytics page](https://code.claude.com/docs/en/analytics) says Admins and Owners can view the dashboard. Configuring the analytics settings needs the Owner role. A GitHub admin must install the GitHub app.

**Access stops at the next system.** The OpenAI roles page lists six control boundaries:

- the ChatGPT workspace,
- local clients (the desktop app and coding tools),
- Codex cloud (hosted coding tasks),
- the Platform API,
- plugins,
- connected systems.

It says: "A request must pass every boundary that applies to it." Workspace access can make a plugin available. But the connected service still decides what data that person's account may see. So a new AI seat does not open the file server. The file server's own permissions still apply.

**Test as an ordinary user.** The rollout guide says to test sign-in and feature access "with a member who has the intended permissions". Before people rely on the setup, it says to "Verify every applicable boundary with representative identities". A representative identity is a test account that has the same rights as the real users. Our reading: a test by an administrator proves little, because an admin can often do things that a normal member cannot.

**An owner for every part.** The OpenAI rollout guide starts by naming an owner for each part of the rollout:

- workspace access,
- local runtime policy,
- Codex cloud,
- connected systems,
- reporting and compliance.

The [Claude Code admin guide](https://code.claude.com/docs/en/admin-setup) frames setup as a series of decisions: where the tool signs in, how settings reach devices, what to enforce, how to see usage and spend, and how data is handled. Our reading: both guides point the same way. Each decision needs a person behind it.

**Skills are shared assets.** The Claude docs page [Skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise) describes a lifecycle: plan, create and review, test, deploy, monitor, then iterate or deprecate. Three rules matter most to a manager:

1. **Separate duties.** The page says: "Skill authors should not be their own reviewers."
2. **Keep a registry.** For each skill, record what it is for (purpose), who owns it, its version, what it depends on, and its evaluation status.
3. **Start narrow.** Begin with skills for one specific workflow. Merge them into a broader skill only when its tests "confirm equivalent performance to the individual Skills it replaces".

The page also has a risk table to use before approval. It rates these as **high** concern: scripts that run code, network access such as web addresses or API calls, references to MCP tools (tools in connected systems), hidden instructions that change behaviour, and passwords or keys written into the files. It rates file access outside the skill's folder, and instructions to use other tools, as **medium**. Its review checklist covers skills from outside vendors and from your own staff alike.

The OpenAI rollout guide asks for similar facts before it adds a plugin or skill to the rollout:

1. Confirm its source, accountable owner, intended audience and review date.
2. Review what data and actions it needs.
3. Test it with non-sensitive data and the least access it needs.
4. Write down who will review it again later, and who will retire it.

## Worked example

### Step 1: the weak state

```text
Admin role:   11 people (2 IT + 8 pilot users + finance controller)
Skills:       22 shared, 13 with an owner, 5 with a review date
Skill "bid-translate":
  sends bid text to an outside translation website
  author: unknown   reviewer: none   review date: none
Seat question: "Can the AI now read every project folder?"
```

What goes wrong:

- **Admin is used as a feature pass.** Eight pilot users need features, not power over the workspace.
- **Skills have no owners.** 22 − 13 = 9 skills have nobody to fix them.
- **A high-risk skill runs unchecked.** It sends client text to an outside site.

### Step 2: fix the roles

```text
2 IT staff            Admin (they administer the workspace)
8 pilot users         Member + custom role (test features)
Finance controller    Analytics Viewer (reports, no settings)
Everyone else         Member + the default features
```

### Step 3: fix the skills

```text
Registry row (one per skill):
  Purpose | Owner | Version | Dependencies | Evaluation status | Review date

Rule: the author is never the only reviewer.
Rule: high-risk skills are paused until an independent review.
```

### Step 4: the hard case

**The hard case is "bid-translate".** It has no script, so a quick look says "safe". But it sends bid text to an outside web address. The Claude page rates network access as high concern, because it is a possible path for data to leave. It also has no owner. So the skill is paused. A reviewer who did not write it checks the address and the data that leaves. Then a named owner and a review date go into the registry, or the skill is retired.

### Step 5: why it is better

- **Power matches the job.** Only people who administer hold Admin. The controller can read reports but can't change settings.
- **Every skill has a person.** The registry shows who to call when a skill breaks.
- **Risk is reviewed by someone else.** The builder's view is not the only check.
- **The seat question has a clear answer.** No. The file server decides what each account can read. Check its rules as a separate rollout item.

## Common mistakes

1. **Giving Admin to people who only need features.** Fix: use a custom role for features; keep built-in admin roles for administrators.
2. **Thinking a seat opens connected systems.** Fix: check each connected system's own permissions for the account.
3. **Letting builders approve their own skills.** Fix: name a different reviewer, record an owner and set a review date.

## Try it

Not graded. Write your answer down before you read the answer.

Use the risk table from the Claude skills page. Rate each skill as high or medium concern.

```text
1. A skill with an API key typed into its instructions file.
2. A skill that reads files from folders outside its own folder.
3. A skill whose instructions say: "Call crm-server:update_deal
   to change the deal stage." (crm-server is an MCP server.)
```

Then answer: two narrow skills work well. When should you merge them into one?

### Answer

1. **High.** Keys or passwords written into skill files are high concern. The checklist says credentials should use environment variables or secure credential stores, and "never appear in Skill content".
2. **Medium.** The page says paths outside the skill's folder "may access unintended data".
3. **High.** It names a tool on an MCP server in the form `ServerName:tool_name`. The page says this "extends access beyond the Skill itself".

Merge only when tests show the merged skill performs as well as the two narrow skills it replaces.

## Recap

- A seat, a built-in role and a custom role are three different things. Keep admin roles for the people who administer.
- Access in an AI tool does not open other systems. Each connected system keeps its own permissions.
- Every shared skill needs a named owner, a reviewer who is not the author, a registry entry and a review date.

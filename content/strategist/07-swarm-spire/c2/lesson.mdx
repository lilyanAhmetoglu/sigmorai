## Goal

After this lesson you can:

- Map a process step by step and decide, for each step, if it needs fixed code, a model, or a person.
- Pick a known pattern (chaining, routing, parallel work, evaluator-optimizer) for the steps that use a model.
- Put approvals and checks next to the action that changes something, and move side work out of the main path.

## The problem

An asset manager sends a monthly letter to 4,000 clients. It covers fund returns and a market comment, in English, German and French. Today three writers and one compliance officer need eight working days for it.

The marketing director wants to "put an agent on it". Her draft gives one agent the whole job: build the numbers, write the letter, check it, translate it and email every client. Nobody has said which steps need judgment, which never change, and where a person signs off.

This lesson gives you the method. The advice below is from the Anthropic engineering post on agents and from the OpenAI docs and cookbooks (October 2026).

## The idea

A **workflow** here means the steps that turn a request into a result: a payment, a report, a meeting brief. Dropping an agent on top of an old process often keeps the old waste and adds new risk. A redesign looks at each step first.

**Workflow or agent.** The Anthropic post [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) draws a clear line:

- **Workflows** are systems where models and tools follow "predefined code paths".
- **Agents** are systems where the model directs its own process and its own tool use.

The post says workflows suit well-defined tasks, because they are predictable and consistent. Agents are the better option when flexibility and model-driven decisions are needed. It also says that for many applications, one well-prepared model call is usually enough. Our reading: if a step never changes from one run to the next, write it as code. Save the model for the parts that need judgment.

**Five patterns to reuse.** The same post names building blocks you can combine:

- **Prompt chaining:** a task split into fixed steps, with checks ("gates") between them. Example from the post: write an outline, check it meets set criteria, then write the document.
- **Routing:** decide what kind of input it is, then give each kind its own process. The post's example is customer service, where each type of query (general, refund, technical) goes to its own process. Easy questions can go to smaller, cheaper models.
- **Parallelization:** independent parts run at the same time ("sectioning"), or the same task runs several times and the results are compared ("voting").
- **Orchestrator-workers:** a central model splits the job and combines the results. The post says it suits jobs whose subtasks are not known in advance.
- **Evaluator-optimizer:** one model call writes, another checks it and gives feedback, in a loop. The post says this works best with clear evaluation criteria, when each round of improvement adds measurable value.

**Checks and people.** The [OpenAI guide on guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) separates two controls:

- A **guardrail** is an automatic check. It validates input, output or tool behaviour.
- **Human review** pauses the run, so a person or a policy can approve or reject a sensitive action.

The guide puts the pause in front of side effects, for example cancellations, edits, shell commands or sensitive MCP actions. (A side effect is an action that changes something in the real world. MCP actions are actions in connected tools.) When a tool needs approval, the run stops, waits for the decision, and then continues as the same run.

**Where checks run.** The same guide warns that agent-level guardrails "don't run everywhere":

- An input guardrail checks the first agent in the chain, and no other.
- An output guardrail checks only the agent that writes the final output.
- A tool guardrail checks the tool it is attached to.

So a check on the first agent never sees what a later agent does with a tool. The guide's answer: place the validation beside the tool whose action causes the side effect. The Anthropic post adds that an agent can stop and ask a person for feedback at set checkpoints, or when it hits a blocker. It also mentions stopping conditions, such as a "maximum number of iterations", to keep control.

**Keep the main path short.** The [OpenAI cookbook on support agents](https://developers.openai.com/cookbook/examples/agent_optimization/optimizing_agents_for_cost_and_quality) starts from a slow, costly **baseline** (the first version, before any changes). That baseline did internal QA, analytics tagging and routing audits before it replied. The fix keeps four things in the live path: classification, the lookups that are needed, the decision to resolve or escalate, and the reply. QA, tags, internal summaries, audits and reports move to follow-up work when they don't change the immediate outcome. Follow-up work can run later on cheaper, slower processing, such as the Batch API for offline jobs. The cookbook also right-sizes the model for each step: a very small model for triage and tags, a mid-size model for routine cases, and a full model only for high-risk cases.

A redesign can also add new value. The [OpenAI workspace agents cookbook](https://developers.openai.com/cookbook/articles/chatgpt-agents-sales-meeting-prep) starts from a real pain: sales teams pull account notes, customer feedback, usage numbers and company news by hand before each meeting. Its agent runs each day, checks tomorrow's customer meetings, gathers the context, writes a brief, saves it as a document and sends a summary.

## Worked example

### Step 1: the weak setup

```text
Draft: monthly client letter
  One agent, one prompt: "Write this month's letter from the fund
  data, check it, translate it and send it to all clients."
  Checks:  "check it" (no criteria)
  People:  none before sending
```

What goes wrong:

- **Fixed work is left to the model.** The number table has the same layout every month.
- **The check has no criteria.** "Check it" can mean anything.
- **Nobody signs off before 4,000 emails go out.** Sending can't be undone.

### Step 2: map each step

This short map is our own tool for this course:

```text
Step            Judgment?              Damage if wrong
Number table    no: fixed layout       wrong figure sent to clients
Market comment  yes                    weak or wrong view
Rules check     no: fixed phrase list  breach of marketing rules
Translation     some (tone)            confusing letter
Send            no                     4,000 wrong emails
```

### Step 3: the good design

```text
1  Code builds the number table from the fund data
2  Model writes the market comment
3  Gate: code checks it against the banned-phrase list
   (fail -> back to step 2)                    <- prompt chaining
4  A second model call checks the comment against the house
   style guide and sends notes back, at most 3 rounds
                                               <- evaluator-optimizer
5  German and French translations run at the same time
                                               <- sectioning
6  The run pauses: the compliance officer approves the letters
7  Code sends the emails
```

### Step 4: the hard case

**The hard case is the style loop.** A write-and-check loop can go on and on, or polish text that was already fine. The Anthropic post says evaluator-optimizer works best with clear evaluation criteria, when each round adds measurable value. The style guide gives the criteria. The cap of 3 rounds is a stopping condition, like the post's "maximum number of iterations". After round 3, the draft goes to the compliance officer as it is.

### Step 5: why it is better

- **Code for the parts that never change.** The number table is built the same way each month.
- **A model where judgment helps.** The market comment and the translations.
- **Checks with clear criteria.** A phrase list and a style guide, not "check it".
- **A person before the send.** 4,000 emails wait for one approval.

## Common mistakes

1. **Agents for the whole process.** Fixed steps then change from run to run. Fix: use code for well-defined steps and a model only where it adds judgment.
2. **One check at the front or the end.** A check on one agent does not cover every agent in the chain. Fix: attach the check and the approval to the tool that acts.
3. **Reporting in the live path.** Internal notes slow every reply. Fix: move any work that has no effect on the result to follow-up processing.

## Try it

Not graded. Write your answer down before you read the answer.

The OpenAI support-agent cookbook matches the model size to the step. Pick a very small, mid-size or full model for each step.

```text
1. Tag each incoming email with one of 12 topic labels.
2. Answer a routine question about delivery times.
3. A caller who can't prove who they are asks to change
   the account's email address.
```

### Answer

1. **Very small.** The cookbook uses a nano model for triage and tags.
2. **Mid-size.** Routine cases go to a mini model.
3. **Full model.** The cookbook keeps the full model for high-risk cases. Its example sends an unverified account-access request to escalation.

## Recap

- Map each step first. Use fixed code for well-defined steps, and an agent only where flexibility is needed.
- Give every check clear criteria. Put a person before actions that can't be undone, and attach checks to the tool that acts.
- Keep only outcome-changing work in the main path, and match the model size to the risk of each step.

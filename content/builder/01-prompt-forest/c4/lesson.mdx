## Goal

After this lesson you can:

- Control built-in reasoning with a setting (effort or thinking level), not with "think step by step".
- Size the output cap and the effort so reasoning has room and costs stay predictable.
- Use manual chain of thought, with the answer in tags, when a model has no thinking turned on.

## The problem

The support team now wants to catch duplicate bug reports. A new bug ticket arrives. The model compares it with the 15 open bugs and returns the id of the matching bug, or `new`.

The prompt was written a year ago for an older model:

```text
Let's think step by step. First, list every open bug. Then compare the
new ticket with each one. Write out all of your reasoning. Then answer.
```

The team moved it to a reasoning model and turned effort to the highest level "to be safe". Now:

1. Each reply is 600 words of reasoning, and the code must dig out the bug id.
2. The bill grew more than the team expected.
3. Easy tickets ("the export button is broken" when an open bug has that exact title) take as long as hard ones.

## The idea

**Chain of thought** means the model works through the steps before it answers. There are two ways to get it.

**1. Built-in reasoning (the main way today).** The [OpenAI docs](https://developers.openai.com/api/docs/guides/reasoning) say reasoning models "use internal reasoning tokens before producing a response". The [Gemini docs](https://ai.google.dev/gemini-api/docs/thinking) describe a "thinking process" that improves reasoning and multi-step planning. The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost) say "the model evaluates each request and determines whether to think and how much".

You control it with a setting:

```text
Claude:  output_config.effort             e.g. "low" ... "max"
OpenAI:  reasoning.effort                 e.g. "none" ... "max"
Gemini:  generation_config.thinking_level e.g. "low", "medium", "high"
```

Which values exist depends on the model. OpenAI: values are "model-dependent". Defaults differ too, so check the model's page.

**With built-in reasoning, drop "think step by step".** The [OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning-best-practices) says "Avoid chain-of-thought prompts", because asking to think step by step may not help "(and can sometimes hinder it)". The [Gemini docs](https://ai.google.dev/gemini-api/docs/prompting-strategies) say "it's generally not necessary to have the model outline, plan, or detail reasoning steps in the returned response itself". The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) say to "prefer general instructions over prescriptive steps". On the current Claude models listed there, a prompt that asks the model to write out its reasoning "may be declined".

**2. Manual chain of thought (the fallback).** When thinking is off, the Claude docs suggest asking the model "to think through the problem before it answers, and to put the final answer in `<answer>` tags so you can extract it".

**A self-check line can help.** The Claude docs suggest "Before you finish, verify your answer against [test criteria]." It "catches errors reliably, especially for coding and math". One exception on the same page: on Claude Opus 5, remove such lines, because they can cause over-verification.

**Reasoning costs money, even when hidden.** OpenAI: reasoning tokens are not visible, but they "are billed as output tokens". Claude: "You are billed for the full thinking process, not the thinking content visible in the response." Gemini: "response pricing is the sum of output tokens and thinking tokens." Example: a 50-token answer after 2,000 reasoning tokens costs 2,050 output tokens.

**The output cap includes reasoning.** Claude: `max_tokens` "is a hard cap on total output for the request, thinking and response text combined". OpenAI: when the cap is hit, the response is `incomplete`, and this "might occur before any visible output tokens are produced". OpenAI recommends "reserving at least 25,000 tokens for reasoning and outputs when you start experimenting". Gemini: to cut cost, lower the thinking level "instead of setting a small `max_output_tokens`".

**Match effort to the task.** OpenAI's effort guide maps `low` to "customer support / chat assistant workflows" and `high` to "hard reasoning, complex debugging, deep planning". For `xhigh`: "Only use when your evals show a clear benefit that justifies the extra latency and cost." The Claude docs say the same about any change: "measure before you ship".

## Worked example

### Step 1: the old setup

```text
model: a reasoning model
effort: the highest level
max output: 1,000 tokens

Let's think step by step. First, list every open bug. Then compare the
new ticket with each one. Write out all of your reasoning. Then answer.

New ticket: ...
Open bugs: ...
```

What goes wrong:

- The prompt asks for written reasoning on top of the hidden reasoning. You pay twice.
- The highest effort is used for a matching task.
- The answer has no fixed format, so the code must search the text.
- The cap is small for a reasoning model. A long think could use all of it before the answer.

### Step 2: move reasoning into the setting

Delete the step-by-step lines. Start with a low effort, and raise it only if your test set shows a gain. Give the cap room for reasoning and answer (OpenAI suggests at least 25,000 tokens while you experiment).

### Step 3: write the goal and the success rules

```text
Decide if the new bug ticket describes the same problem as one of the
open bugs.

Same problem means: the same feature fails in the same way.
Different wording, devices or customers do not make it a new problem.

Reply with one line only: the matching bug id (for example BUG-112),
or "new" if no open bug matches.

<open_bugs>
...15 open bugs, each with its id and description...
</open_bugs>

<new_ticket>
...
</new_ticket>
```

**The hard case:** the ticket says "the app freezes when I attach my 80 MB design file". An open bug says "uploads over 50 MB never finish". Different words, likely the same problem. The rule "same feature fails in the same way" gives the model a clear test. The model does the reasoning itself, inside its budget.

### Step 4: if the model has no thinking

On a model without built-in thinking, use the manual fallback:

```text
Compare the new ticket with each open bug before you answer.
Then put only the bug id, or "new", inside answer tags.
```

Your code reads only the text inside the answer tags.

### Step 5: why it is better

- **Cheaper.** No written reasoning, and a lower effort for a simple task.
- **Parseable.** One line, one id.
- **Safer.** The cap leaves room for reasoning, so answers do not come back empty.
- **Measured.** Run the same 30 past tickets at two effort levels. Keep the lower one if accuracy is the same.

## Common mistakes

1. **Old "think step by step" lines on a reasoning model.** They add cost and can hurt quality. Fix: delete them and write a clear goal with success rules.
2. **A small output cap to save money.** The reasoning can use the whole cap before any answer appears. Fix: lower the effort instead, and give the cap room for both the reasoning and the answer.
3. **One effort level for every request.** Easy and hard tasks then cost the same. Fix: pick the effort per task type, and check the choice on a test set.

## Try it

Not graded. Write your answer down before you read the answer.

A team reviews code changes with a Gemini model. Here is their setup:

```text
generation_config:
  thinking_level: high
  max_output_tokens: 300

Outline your plan step by step in your answer, then list any bugs
you find in this code change.
```

Some replies come back empty. Find three problems and fix them.

### Answer

1. **The cap is too small.** `max_output_tokens` includes thinking tokens. With a high thinking level, the model can use all 300 tokens before it writes the list. Fix: raise the cap, and lower `thinking_level` if cost is the worry.
2. **The plan is requested in the reply.** The Gemini docs say this is generally not necessary with thinking. Fix: delete "Outline your plan step by step in your answer".
3. **No output format and no success rule.** Fix: ask for one line per bug with the file, the line and the problem, and "none found" when there are no bugs. Then test two thinking levels on past code changes.

## Recap

- Built-in reasoning is a setting: Claude `output_config.effort`, OpenAI `reasoning.effort`, Gemini `thinking_level`. Drop "think step by step" and give a clear goal.
- Reasoning tokens are billed as output, and the output cap includes them. Lower the effort to save money; do not shrink the cap.
- When thinking is off, ask for reasoning first and the answer in tags. Measure any change on a test set.

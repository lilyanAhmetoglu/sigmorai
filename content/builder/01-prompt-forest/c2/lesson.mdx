## Goal

After this lesson you can:

- Turn a zero-shot prompt into a few-shot prompt with 3–5 tagged examples.
- Pick examples that are relevant, diverse and in one format, and include a hard case.
- Spot an example set that teaches the model a pattern you did not mean.

## The problem

A support team uses a model to route tickets. Each ticket gets one label: `billing`, `bug`, `account` or `other`. A script reads the label and sends the ticket to the right queue. The script expects one lowercase word.

Chapter 1 made the instruction specific. The team still sees three problems:

1. The format drifts. Some replies are `billing`, some are `Billing`, some are `This looks like a billing issue.` The script fails on the last two.
2. Tickets with two problems ("I was charged twice and now I can't log in") get a different label each time.
3. Questions that fit no queue ("Do you have an office in Lisbon?") get forced into `account`.

Rules help. This lesson adds a second tool: show the model a few solved tickets.

## The idea

A prompt with no examples is **zero-shot**. A prompt with a few input/output examples is **few-shot** (Anthropic also says "multishot"). The model picks up the pattern in the examples and applies it to the new input. You steer the model this way without fine-tuning it ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-engineering)).

Think of examples as a teacher's solved problems on the board. Students copy the method, and also the handwriting.

```text
zero-shot: rules + input
           -> model guesses the format
few-shot:  rules + examples + input
           -> model copies the pattern
```

All three vendor guides teach this technique. The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) call examples one of the most reliable ways to steer output format, tone and structure. They say good examples are:

- **Relevant**: close to your real use case.
- **Diverse**: they cover edge cases and vary, so the model does not pick up unintended patterns.
- **Structured**: each one in `example` tags, inside `examples` tags, so the model can tell them apart from the instructions.

Three more rules from the guides:

- **Keep one format.** Every example must have the same structure, or the replies can come back in formats you did not want ([Gemini](https://ai.google.dev/gemini-api/docs/prompting-strategies)).
- **Do not overdo it.** Claude suggests 3–5 examples. With too many, the model may overfit to them (Gemini). Each example also costs input tokens on every call (realm 0, chapter 6).
- **Mark them clearly.** Claude uses tags. OpenAI says examples typically go in the `developer` message.

The default differs by model type. Gemini recommends always including examples. For reasoning models, OpenAI says to try zero-shot first and add examples only if needed. When you add them, they must match the instructions closely, or results may be poor ([OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning-best-practices)). So test both versions on your model.

## Worked example

### Step 1: the zero-shot prompt

```text
Label the support ticket as billing, bug, account, or other.

Ticket: I was charged twice and now I can't log in.
```

What goes wrong:

- Nothing shows the output format, so the model has to guess it.
- The ticket has two problems. The prompt does not say which label wins.
- No example shows when `other` is right.

### Step 2: write the missing rules

Add the two rules the team had in their heads:

```text
Label the support ticket as billing, bug, account, or other.
Output only the label, in lowercase.
If a ticket has a billing problem and another problem, choose billing.
```

Rules are a good start, but they still leave room to guess. Does "only the label" allow `Label: billing`? Examples show the exact shape.

### Step 3: add examples

```text
Label the support ticket as billing, bug, account, or other.
Output only the label, in lowercase.
If a ticket has a billing problem and another problem, choose billing.

<examples>
<example>
Ticket: My invoice still shows the old price after I moved to the smaller plan.
Label: billing
</example>
<example>
Ticket: The export button does nothing.
Label: bug
</example>
<example>
Ticket: How do I add a second admin to our workspace?
Label: account
</example>
<example>
Ticket: I was charged twice this month, and since the second charge I can't log in to my account at all.
Label: billing
</example>
<example>
Ticket: Do you have an office in Lisbon?
Label: other
</example>
</examples>

Ticket: [the live ticket text]
Label:
```

**The hard example is the fourth one.** It has two problems and is the longest ticket. It shows the tie rule from the instructions in use.

### Step 4: why it is better

- **One format.** Every example ends `Label: <one lowercase word>`, and the prompt ends with `Label:`. The model has one shape to copy.
- **Diverse.** All four labels appear. Tickets are short and long. One example is a hard case.
- **Matches the instructions.** The hard example follows the billing rule. Examples and instructions never disagree.
- **Structured.** Tags keep the examples apart from the instructions and from the live ticket.
- **Five examples.** That is inside the 3–5 range, and it keeps the token cost per call small.

Then measure. Run the old and new prompts on the same set of real tickets and compare the labels.

## Common mistakes

1. **Examples that share a pattern you did not mean.** All four examples are billing, or all are one short sentence. The model can then over-use `billing` or struggle with long tickets. Fix: vary the labels and lengths, and include a hard case.
2. **Mixed formats.** Four examples say `bug`, one says `Category: bug`. Now the prefix can show up in some replies. Fix: give every example exactly the same structure.
3. **Too many examples.** Forty examples cost tokens on every call and can make the model overfit. Fix: start with 3–5, and add more only when a test shows a gap.

## Try it

A team labels ticket urgency. Find two problems in these examples before you read the answer.

```text
<examples>
<example>
Ticket: SITE IS DOWN!!! Nobody can pay.
Urgency: urgent
</example>
<example>
Ticket: PLEASE HELP, ALL OUR ORDERS FAILED
Urgency: urgent
</example>
<example>
Ticket: small typo on the pricing page
Priority: normal
</example>
</examples>
```

Write your answer down first.

### Answer

1. **An unintended pattern.** Every urgent ticket is in capital letters. The model may learn "capitals = urgent". A calm ticket like "Payments have failed since 9am" could then get `normal`. Fix: add an urgent ticket written calmly.
2. **Mixed formats.** Two examples say `Urgency:`, one says `Priority:`. Fix: use `Urgency:` in every example.

## Recap

- Few-shot means a few input/output examples in the prompt. The model copies their pattern: format, tone and labels.
- Good examples are relevant, diverse and in one format. Use about 3–5, tagged, and include one hard case.
- The model copies everything the examples share, including patterns you did not mean. Check what your examples have in common.

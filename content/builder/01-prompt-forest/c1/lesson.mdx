## Goal

After this lesson you can:

- Use the colleague test to find every place where a prompt makes the model guess.
- Replace vague words with rules you can check: reader, format, length and content.
- Turn "don't" rules into "do" rules with a reason, and keep a small test set for every prompt change.

## The problem

A support team at a software company gets about 300 tickets a day. They want the model to write a first draft of each reply. An agent reads the draft, edits it and sends it.

Their first prompt is one line:

```text
Write a reply to this ticket. Be professional and helpful. Don't make promises.
```

After a week, the agents rewrite most drafts:

1. Some drafts are three lines. Others are 400 words with headings.
2. Some drafts ask the customer for details that are already in the ticket.
3. One draft told a customer "We will refund this month in full". Only billing staff can approve a refund.

The model is not broken. The prompt leaves almost every choice open, so the model guesses. This lesson shows how to close those gaps.

## The idea

The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) say to think of the model "as a brilliant but new employee who lacks context on your norms and workflows". It is smart, but it does not know your product, your customers or your rules.

They give a **golden rule**: "Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too."

Every question a new colleague would ask is a guess the model makes for you:

```text
vague word      -> colleague asks         -> checkable rule
"short"         -> how short?             -> 60 to 120 words
"professional"  -> which tone? headings?  -> plain text, short sentences
"don't promise" -> so what do I say?      -> "a team member will confirm it"
```

Four habits close the gaps:

- **Name the output.** The Claude docs say to "be specific about the desired output format and constraints". The [Gemini docs](https://ai.google.dev/gemini-api/docs/prompting-strategies) add: "explicitly explain any ambiguous terms or parameters". Words like "short" or "professional" mean different things to different readers.
- **Say what to do, not only what not to do.** The Claude docs: "Tell Claude what to do instead of what not to do". Their example swaps a ban on markdown for a request for flowing prose paragraphs. A "don't" removes one choice. A "do" names the target.
- **Give the reason.** The Claude docs say that explaining "why such behavior is important" helps the model "better understand your goals".
- **Use steps when order matters.** The Claude docs advise "numbered lists or bullet points when the order or completeness of steps matters".

How much method you write depends on the model. The [OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-engineering) say GPT models "benefit from more explicit instructions around how to accomplish tasks", like "a junior coworker". Reasoning models are like "a senior co-worker. You can give them a goal to achieve and trust them to work out the details." But the [OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning-best-practices) still says to "provide specific guidelines" and "be very specific about your end goal". So a reasoning model needs less method, not a vaguer goal.

Last, a specific prompt is a testable prompt. The OpenAI docs recommend "pinning your production applications to specific model snapshots" and "building tests and evaluation suites that measure prompt behavior". The Gemini docs say: "Prompt engineering is iterative."

## Worked example

### Step 1: run the colleague test

Read the one-line prompt as a new agent would. Write down every question:

- Who reads the draft: the agent or the customer? Both, in the end.
- How long? Bullets or prose? Headings?
- What if the ticket has no clear fix?
- What should I say instead of a promise?
- Why can't I promise? Who can?

Each question is a gap. Close them one by one.

### Step 2: rewrite the prompt

```text
Draft a first reply to the customer support ticket below.
A support agent will read and edit your draft before it is sent.

Write the reply in this order:
1. Thank the customer in one sentence and name their problem in your own words.
2. Give one next step: a fix from the ticket notes, or one question
   about information that is not already in the ticket.
3. End with the line: [agent name]

Rules:
- Plain text, 60 to 120 words. No headings and no bullet points.
- Use short sentences and everyday words. Explain any technical term.
- If the customer asks for a refund, a discount or a fix date, say that
  a team member will confirm it. Only billing staff can approve refunds,
  and only the product team sets dates.

Ticket: [the ticket text and the agent's notes]
```

### Step 3: test the hard case

**The hard case is a refund request.** Use a real one:

```text
Ticket: The app was down all Monday and my team lost a day of work.
I want a refund for this month.
```

The old prompt only said "Don't make promises". The model had to invent what to say instead. The new prompt names the target sentence and gives the reason. A good draft now says that a team member from billing will confirm the refund question.

### Step 4: why it is better

- **Reader and use are clear.** The model knows an agent edits the draft and a customer reads it.
- **Format and length are checkable.** You can count words and look for headings.
- **The order is fixed.** Numbered steps keep every part in every draft.
- **The "don't" became a "do" with a reason.** The model knows what to write and why.

### Step 5: make it testable

Keep 20 real tickets, including two refund requests and one ticket with no clear fix. For each, write what a pass looks like: 60 to 120 words, no headings, no promise. Run every prompt change against these 20 tickets. Pin the model snapshot, so the results stay comparable.

If the team later moves to a reasoning model, keep the goal, the rules and the format. You may need less step-by-step method. Run the 20 tickets on the new model before you switch.

## Common mistakes

1. **Adjectives as rules.** "Clear", "brief" and "friendly" mean different things to different readers. Fix: replace each one with something you can count or see.
2. **A list of "don'ts" with no target.** The model still has to guess what is allowed. Fix: say what to do instead, and add the reason in one line.
3. **Changing the prompt or the model without a test set.** You cannot tell if the change helped. Fix: keep a small set of real inputs with pass rules, and rerun it on every change.

## Try it

Not graded. Write your answer down before you read the answer.

A team uses this prompt to write release notes for their app store page:

```text
Write release notes for these changes. Keep them short and not too
technical. Don't mention internal stuff.
```

Run the colleague test. List at least three guesses the model must make, then rewrite the prompt.

### Answer

Guesses the model must make:

1. **How short?** One line per change, or one paragraph in total?
2. **Who reads it?** "Not too technical" for whom?
3. **What is "internal stuff"?** Ticket numbers? Code names? Team names?
4. **What format?** Bullets, prose, a title?

One possible rewrite:

```text
Write release notes for our app store page. Readers are everyday users,
not developers.
- One bullet per change, at most 15 words each, with the most useful change first.
- Say what the user can now do, in everyday words.
- Leave out ticket numbers, code names and team names: the page is public.
```

## Recap

- The model is a smart new employee with no context. If a colleague would ask a question, the model will guess.
- Replace vague words with checkable rules: reader, format, length, content. Say what to do, and why.
- A specific prompt can be tested. Keep a small test set, pin the model snapshot, and rerun the tests on every change.

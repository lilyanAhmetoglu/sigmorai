Agent Citadel, chapter 2 (Stop conditions), used a `Stop` hook to keep Claude from saying "done" too early. Chapter 3 (The harness) drew the line: an instruction is a request, a hook is enforcement. This chapter uses hooks at other moments in the loop, with four recipes: format, guard, notify and validate.

A note on dates: the event names and fields below are from each vendor's page in October 2026.

## One idea, three sets of names

A hook is a script the agent's harness runs at a fixed moment, such as before a tool call (our plain gloss). Anthropic: hooks give "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." Google: Gemini CLI runs hooks "at specific points in the agentic loop".

The moments have different names per tool:

| Moment                   | Claude Code    | Codex          | Gemini CLI     |
| ------------------------ | -------------- | -------------- | -------------- |
| Before a tool call       | `PreToolUse`   | `PreToolUse`   | `BeforeTool`   |
| After a tool call        | `PostToolUse`  | `PostToolUse`  | `AfterTool`    |
| The agent sends an alert | `Notification` | not listed     | `Notification` |
| The agent's turn ends    | `Stop`         | `Stop`         | `AfterAgent`   |
| A session starts         | `SessionStart` | `SessionStart` | `SessionStart` |

All three use the same three levels in JSON: an event, a `matcher` that filters it (for tool events, a pattern on the tool name), and one or more handlers with a `command`. Where the file lives:

- **Claude Code:** a `hooks` block in a settings file, such as `.claude/settings.json` for one project.
- **Codex:** `hooks.json` or `[hooks]` in `config.toml`, for example `<repo>/.codex/hooks.json`.
- **Gemini CLI:** `.gemini/settings.json` in the project.

## How a hook answers

The hook gets the event as JSON on stdin (standard input; our plain gloss). It answers with an exit code (the number a script returns when it ends; 0 means OK) and, sometimes, JSON on stdout (the script's normal output). A reason for a block goes to stderr (its error output). Our plain glosses.

- **Exit 2 blocks a tool call** in all three. Claude Code: "Claude Code blocks the action. Write a reason to stderr." Codex: "You can also use exit code `2` and write the blocking reason to `stderr`." Gemini CLI: "The target action (tool, turn, or stop) is aborted."
- **Exit 0 is not a yes.** Claude Code: for `PreToolUse`, exit 0 "doesn't approve the tool call: the normal permission flow still applies."
- **Other codes don't block on their own.** In Claude Code, with plain text or empty stdout, the action "proceeds as a non-blocking error". In Gemini CLI, "the interaction proceeds using original parameters."
- **Keep stdout clean in Gemini CLI.** "Your script must not print any plain text to `stdout` other than the final JSON object."

Our example: a guard script that prints nothing and exits 1 by mistake does not block anything. It only shows an error.

## Recipe 1: format on edit

Anthropic's example runs Prettier "on every file Claude edits". It uses `PostToolUse` with an `Edit|Write` matcher, in `.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

In Codex, file edits go through `apply_patch`, and "`matcher` values can use `apply_patch`, `Edit`, or `Write`". Gemini CLI lists "run tests" as a common use of `AfterTool`.

Know the limit. Anthropic: "`PostToolUse` hooks can't undo actions since the tool has already executed." Codex says the same: it "can't undo side effects from a tool that already ran." So format after an edit, but guard before one.

## Recipe 2: guard a command

A guard is a `PreToolUse` hook on the shell tool (`Bash`) that blocks a risky command. Anthropic's example script (shortened):

```bash
if echo "$COMMAND" | grep -q "drop table"; then
  echo "Blocked: dropping tables is not allowed" >&2
  exit 2
fi
exit 0
```

Claude gets the stderr text as feedback, so it can change its plan. In Codex, a JSON answer with `"permissionDecision": "deny"` also blocks. Gemini CLI uses `BeforeTool` to "block dangerous ops".

Three facts make a guard strong or weak:

- **Claude Code: a deny holds in every mode.** "A hook that returns `permissionDecision: "deny"` blocks the tool even in `bypassPermissions` mode" (the mode that skips every permission prompt; our plain gloss).
- **Hooks run side by side.** Claude Code: "One hook returning `deny` doesn't stop sibling hooks from executing." Codex: "one hook can't prevent another matching hook from starting."
- **Codex: not every tool passes the hook.** Hosted tools such as `WebSearch` "don't use the local function-tool hook path". OpenAI's advice: "Treat tool hooks as a useful guardrail, not a complete enforcement boundary."

## Recipe 3: notify a person

Claude Code fires `Notification` "when Claude is waiting for input or permission". Anthropic's example sends a desktop alert, "so you can switch to other tasks without checking the terminal." Gemini CLI also has `Notification`, for "Forward to desktop alerts, logging". Google marks its impact "Advisory".

Codex's hooks page lists no `Notification` event. Two other events can send the alert (our advice): `Stop`, which runs at the end of each turn, and `PermissionRequest`, which "runs when Codex is about to ask for approval".

## Recipe 4: validate before the turn ends

Chapter 2 of Agent Citadel used Claude Code's `Stop` hook for this. Codex has the same idea. One use it lists: "Run a custom validation check when a chat turn stops, enforcing standards". A `Stop` hook that returns `"decision": "block"` with a `reason` "tells Codex to continue", using the reason as the next prompt. Gemini CLI's `AfterAgent` can "force retry or halt execution".

Some checks need judgment, not a fixed rule. Claude Code also has hooks "that use a Claude model to evaluate conditions" (`"type": "prompt"` and `"type": "agent"`).

## Who decides that a hook may run

A hook is code that runs on your machine. Anthropic: "Command hooks execute shell commands with your full user permissions." So each tool has a trust step:

- **Codex:** for hooks an admin does not manage, "Codex requires you to review and trust the exact hook definition." It records trust against the hook's hash (a fingerprint of the file's text; our plain gloss), "so new or changed hooks are marked for review and skipped until trusted."
- **Gemini CLI:** "If a hook's name or command changes (for example, via `git pull`), it is treated as a **new, untrusted hook** and you will be warned before it executes."
- **Claude Code:** in an interactive session, hooks wait until you accept the workspace trust dialog. But in a `-p` or SDK run (no person at the screen), "Claude Code never shows the dialog and treats the folder as trusted". Before you run `claude -p` on a repo you didn't write, Anthropic says to review its `.claude/` settings, or turn hooks off for that run with `--settings '{"disableAllHooks": true}'`.

## Key points

- Hooks run at fixed moments. Claude Code and Codex say `PreToolUse` / `PostToolUse`; Gemini CLI says `BeforeTool` / `AfterTool`.
- Exit 2 blocks a tool call in all three. In Claude Code, exit 0 is not approval. Other codes don't block on their own.
- Format with a post-tool hook. It can't undo, so guard with a pre-tool hook.
- Claude Code: a `PreToolUse` deny holds even in `bypassPermissions` mode.
- Codex: hosted tools skip tool hooks. A hook is a guardrail, not a full wall.
- Notify with `Notification` (Claude Code, Gemini CLI); Codex lists no such event.
- Validate at turn end: `Stop` (Claude Code, Codex), `AfterAgent` (Gemini CLI).
- Hooks run as you. Codex and Gemini CLI re-ask after a hook changes; `claude -p` trusts the folder, so review the repo first.

## Goal

After this lesson you can:

- Run two or three agent sessions on one repo at the same time, each in its own worktree.
- Set up, clean up and undo work in each tool, and know what a checkpoint cannot undo.
- Split tasks so the branches merge back without a fight.

## The problem

A developer has three small tasks on one web app: a dark-mode switch, a CSV export and a rate limit on the API. Each takes an agent about twenty minutes. Doing them one after another wastes an hour.

So the developer starts three agent sessions in the same folder. Soon one session's half-done edit breaks another session's test run. Two sessions write to the same file. Nobody can tell which change came from which task.

## The idea

### A worktree: one repo, many folders

A **git worktree** is a second folder for the same repo, with its own files and its own branch. Think of it as three desks that share one filing cabinet: each worker has a desk, but the history is in one place.

- The [Claude Code docs](https://code.claude.com/docs/en/worktrees): "a separate working directory with its own files and branch, sharing the same repository history and remote as your main checkout."
- The [Codex docs](https://learn.chatgpt.com/docs/environments/git-worktrees): "Each worktree has its own copy of every file in your repo but they all share the same metadata (`.git` folder) about commits, branches, etc."
- The [Gemini CLI docs](https://geminicli.com/docs/cli/git-worktrees/): "This prevents changes in one session from colliding with another."

### Start a session in a worktree

| Tool        | How                                    | Where it lives              |
| ----------- | -------------------------------------- | --------------------------- |
| Claude Code | `claude --worktree <name>` (or `-w`)   | `.claude/worktrees/<name>/` |
| Codex app   | select **Worktree** under the composer | `$CODEX_HOME/worktrees`     |
| Gemini CLI  | `gemini --worktree <name>` (or `-w`)   | `.gemini/worktrees/<name>/` |

- **Claude Code** puts the worktree "on a new branch named `worktree-<name>`".
- **Codex** shows the choice under the composer (the box where you type). By default it works in a "detached HEAD" (no branch checked out), so it can make "several worktrees without polluting your branches."
- **Gemini CLI** marks worktrees "experimental". Turn them on first with `"experimental": { "worktrees": true }` in `settings.json`.

### Each new worktree starts clean

It has your tracked files and nothing else.

- **Set it up.** The Claude Code docs: "A worktree is a fresh checkout, so initialize your development environment there". The Gemini CLI docs say the same.
- **Copy ignored files on purpose.** Files like `.env` are gitignored, so they are not there. Claude Code and Codex both read a `.worktreeinclude` file at the repo root. The Claude Code docs: "Only files that match a pattern and are also gitignored are copied, so tracked files are never duplicated."
- **Check the starting point.** By default, Claude Code starts new worktrees "from the repository's default branch" on the remote. Set `worktree.baseRef` to `"head"` to "branch from your current local `HEAD`" (the commit you have checked out now). Then the worktree "carries your unpushed commits".

### One branch, one place

The Codex docs: "Git only allows a branch to be checked out in one place at a time." In the Codex app, **Create branch here** turns a worktree into a branch. "From here you can commit your changes, push your branch to your remote repository, and open a pull request." To move the work to your main folder (called Local), use **Hand off** instead.

### Clean up

- **Claude Code:** when you leave an interactive session, it removes a clean worktree or asks about one with work in it. But "Non-interactive runs with `-p` have no exit prompt, so Claude doesn't clean up their worktrees." Remove those with `git worktree remove`.
- **Codex:** "By default, Codex keeps your most recent 15 Codex-managed worktrees." Before it deletes one, "Codex saves a snapshot of the work on it."
- **Gemini CLI:** "it **does not automatically delete** your worktree or branch."

### Parallel in the cloud

You can also run sessions on the vendor's machines.

- **Claude Code:** "each `--cloud` command creates its own cloud session that runs independently." But "The cloud VM clones your current directory's GitHub remote at your current branch, not your local checkout, so push first if you have local commits." (A VM is a virtual machine.) `claude --teleport` brings a cloud session and its branch back to your terminal.
- **Codex Cloud:** you start tasks "from a published environment", and "Each task has its own workspace" ([Codex Cloud docs](https://learn.chatgpt.com/docs/cloud)).

### Checkpoints: undo inside one session

A **checkpoint** is a saved state you can go back to inside one session.

- **Claude Code** saves one "before each prompt you send that starts a turn". Run `/rewind`, or press `Esc` twice, to restore code, the conversation, or both.
- **Gemini CLI** saves one before a tool changes files, in "a special, shadow Git repository". It is "disabled by default". Turn it on with `"general": { "checkpointing": { "enabled": true } }` in `settings.json`, and restore with `/restore`.

Know the gaps in Claude Code's checkpoints ([Checkpointing docs](https://code.claude.com/docs/en/checkpointing)):

- "Checkpointing does not track files modified by Bash commands."
- "edits from other concurrent sessions are normally not captured".
- It is "Not a replacement for version control".

## Worked example

The three tasks from The problem, run with Claude Code.

### Step 1: the weak setup

Three terminals, one folder:

```bash
claude "Add a dark-mode switch to the settings page"
claude "Add CSV export to the reports API"
claude "Add a rate limit to the public API"
```

All three edit the same files on disk. A test run in one terminal sees half-done edits from the other two. One wrong change spoils all three tasks.

### Step 2: one worktree per task

```bash
claude -w dark-mode "Add a dark-mode switch to the settings page"
claude -w csv-export "Add CSV export to the reports API"
claude -w rate-limit "Add a rate limit to the public API"
```

Each session now has its own folder under `.claude/worktrees/` and its own branch, such as `worktree-csv-export`. Before each agent runs tests, it installs dependencies in its own folder, because each new folder starts with no installed packages.

### Step 3: the hard case, two tasks touch one file

The CSV export and the rate limit both add a line to `api/routes.ts`. The worktrees kept them apart while they worked. But each branch changed the same lines, so the second merge conflicts.

Worktrees separate the work, not the result. The Claude Code docs ask one question when you plan parallel work: "Do the tasks touch the same files?" Here the answer was yes for one file.

Our merge order:

1. Merge `worktree-dark-mode` first. It touches no shared file.
2. Merge `worktree-csv-export` through a pull request with its checks.
3. Update `worktree-rate-limit` from the default branch, fix the `api/routes.ts` conflict in that branch, and run its tests again.
4. Merge it.

Better still, next time: plan so each task owns different files. For example, the first task adds both routes, and the others only fill in the handlers.

### Step 4: clean up

Close each session. If you ran any of them with `-p`, nothing asks you, so remove those folders yourself:

```bash
git worktree remove .claude/worktrees/rate-limit
```

### Why it is better

- No session sees another's half-done edits.
- Each task ends as its own branch, so you can review and merge it alone.
- The one shared file is handled on purpose, with tests run again after the fix.

## Common mistakes

1. **Starting ten sessions at once.** The Claude Code docs: "Running several sessions or subagents at once multiplies token usage." Fix: start with two or three, and add more when merges stay calm.
2. **Using an agent team and expecting worktrees.** The docs: "Agent teams don't isolate teammates in worktrees". Fix: "partition the work so each teammate owns a different set of files."
3. **Leaving Gemini CLI worktrees behind.** The docs say "You are responsible for cleaning up your worktrees manually". Fix: remove each one when its branch is merged.

## Try it

Not graded. Write your answer down before you read the answer.

A team has a custom Claude Code subagent that renames a function across many files. Two copies sometimes run at once and edit the same files.

1. What one frontmatter line makes this subagent always run in its own worktree?
2. What happens to that worktree when the subagent finishes and changed nothing?

### Answer

1. `isolation: worktree`. The Claude Code docs: add it "to its frontmatter" to make the isolation permanent.
2. Claude Code "removes automatically" a subagent's temporary worktree "when the subagent finishes without changes". A worktree with changes stays on disk until a later sweep can remove it "without losing work".

## Recap

- A worktree is a second folder for the same repo, with its own files and branch. Start one with `claude --worktree <name>`, the Codex app's **Worktree** option, or `gemini --worktree <name>`.
- Each new worktree starts clean: set it up, and copy gitignored files with `.worktreeinclude`. Git lets one branch live in only one folder at a time. Clean-up differs per tool.
- Worktrees keep work apart, not branches. Split tasks by file, merge one branch at a time, and rerun tests. Checkpoints undo inside one session, but Claude Code's skip Bash changes.

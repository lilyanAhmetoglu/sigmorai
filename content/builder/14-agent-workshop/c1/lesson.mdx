## Goal

After this lesson you can:

- Decide if a piece of guidance belongs in an instruction file, a skill or a subagent.
- Write a `SKILL.md` with a description that makes the agent pick it at the right time.
- Put a skill where each agent tool can find it, and control who can start it.

## The problem

A developer on a payments API team adds a new REST endpoint about once a week. Each time, they paste the same 40-line checklist into the agent chat: route name, input checks, error format, tests, docs. They also paste parts of a 1,200-line table of error codes.

The pasting is slow, and people forget steps. But the big table should not load in every session, because most sessions have nothing to do with endpoints.

A **skill** solves this. A skill is a folder of instructions that the agent loads only when a task needs it.

## The idea

### What a skill is

All three vendors use the same shape: a folder with a `SKILL.md` file in it. The [Codex docs](https://learn.chatgpt.com/docs/build-skills) say: "A skill is a directory with a `SKILL.md` file plus optional scripts and references. The `SKILL.md` file must include `name` and `description`." In [Gemini CLI](https://geminicli.com/docs/cli/skills/), a skill is "a self-contained directory that packages instructions and assets into a discoverable capability." All three pages point to the same open standard, Agent Skills (agentskills.io).

`SKILL.md` has two parts: frontmatter (a short block of `key: value` lines between `---` markers) that says when to use the skill, and the instructions below it. The fields differ a little:

- **Codex** requires `name` and `description`.
- **Claude Code**: "All fields are optional. Only `description` is recommended" ([Claude Code docs](https://code.claude.com/docs/en/skills)).
- **Gemini CLI**'s guide creates a skill with both `name` and `description`.

Scripts are optional: the Codex docs list `scripts/`, `references/` and `assets/` as optional parts.

### Only the card loads first

Think of a skill like a recipe card in a box. The agent reads the label on every card. It pulls out the full card only when it cooks that dish.

```text
session start -> name + description of every skill
task matches  -> full SKILL.md loads
step needs it -> reference file is read, script is run
```

- **Codex:** "ChatGPT and Codex start with each skill's name and description, then load the full `SKILL.md` instructions when they decide to use that skill."
- **Gemini CLI:** "Only skill metadata (name and description) is loaded initially."
- **Claude Code:** by default, "Description always in context, full skill loads when invoked".

So the description is the trigger. The agent compares the task with the descriptions, not with the body. The Codex docs say: "Front-load the key use case and trigger words so a host can still match the skill if descriptions are shortened." Codex keeps the first list of skills to "at most 2% of the model's context window" and shortens descriptions first when many skills are installed. In Claude Code, the description plus `when_to_use` "is truncated at 1,536 characters in the skill listing".

### Instruction file, skill or subagent

The [Claude Code overview](https://code.claude.com/docs/en/features-overview) compares them in a table. `CLAUDE.md` loads "Every session, automatically". A skill loads "On demand". Its advice:

- "Put it in CLAUDE.md if Claude should always know it".
- "Put it in a skill if it's reference material Claude needs sometimes (API docs, style guides) or a workflow you trigger with `/<name>`".

The skills page names the moment to make one: "Create a skill when you keep pasting the same instructions, checklist, or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact."

The other vendors agree. The [Codex customization page](https://learn.chatgpt.com/docs/customization/overview) says "skills package repeatable processes". Gemini CLI calls skills "on-demand expertise", unlike `GEMINI.md`.

A skill is not a subagent (a helper agent that works in its own context window). A skill adds its text to your main conversation. A subagent works apart and sends back a summary. They can combine: in Claude Code, `context: fork` runs a skill "in a forked subagent context".

Our habit:

- True in every session → `CLAUDE.md` or `AGENTS.md`.
- Steps or reference you need sometimes → a skill.
- A big side job whose middle steps you do not need to see → a subagent.

### Who can start a skill

By default, both you and the agent can start a skill. You type `/skill-name` in Claude Code. In Codex you type `$` to mention a skill, or run `/skills`.

To stop the agent from starting one on its own:

- **Claude Code:** `disable-model-invocation: true`. The docs: "Claude can't invoke the skill on its own. Use this for workflows with side effects or that you want to control timing". Their example is a deploy: "You don't want Claude deciding to deploy because your code looks ready."
- **Codex:** in the optional `agents/openai.yaml` file, set `allow_implicit_invocation: false` under `policy:`. Then "Codex won't implicitly invoke the skill based on user prompt; explicit `$skill` invocation still works."

The frontmatter field is the lock. A folder name or a short description does not change who can start a skill.

### Keep the body short

The Claude Code docs warn: "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost." Their tip: "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." Link those files from `SKILL.md` and say when to read each one.

### Where skills live

| Tool        | Personal                                   | Project (commit it)                                                  |
| ----------- | ------------------------------------------ | -------------------------------------------------------------------- |
| Claude Code | `~/.claude/skills/<name>/SKILL.md`         | `.claude/skills/<name>/SKILL.md`                                     |
| Codex       | `$HOME/.agents/skills`                     | `.agents/skills` in each folder from where you start, up to the root |
| Gemini CLI  | `~/.gemini/skills/` or `~/.agents/skills/` | `.gemini/skills/` or `.agents/skills/`                               |

Codex and Gemini CLI both read `.agents/skills/`. Google calls it "an interoperable path". Claude Code reads `.claude/skills/`, not `.agents/skills/`.

Claude Code and Codex both accept a skill folder that is a symlink (a symlink is a file-system shortcut to another folder). The Codex docs: "Codex supports symlinked skill folders and follows the symlink target when scanning these locations." So a mixed team can keep one copy in `.agents/skills/` and link to it from `.claude/skills/` (our advice).

## Worked example

Our example: the endpoint checklist from The problem, on a team that uses Claude Code.

### Step 1: the weak skill

```md
---
name: api
description: API stuff
---

(40-line endpoint checklist)
(1,200-line error code table)
```

What goes wrong:

- `API stuff` names no task and no trigger words. A request to add a refunds endpoint may not match it.
- When the skill does load, all 1,240 lines enter the conversation and stay there for every later turn.

### Step 2: a description that says what and when

```md
---
name: add-endpoint
description: Adds a new REST endpoint to the payments API with input checks, error format, tests and docs. Use when asked to add, create or expose an endpoint or route.
---
```

The use case comes first, then trigger words, so a shortened listing still matches.

### Step 3: the hard case, the 1,200-line table

The agent needs only one or two error codes per endpoint. If the table stays in `SKILL.md`, every endpoint task pays for 1,200 lines on every turn after the skill loads. It also breaks the "under 500 lines" tip.

Move it into its own file and tell the agent when to read it:

```text
.claude/skills/add-endpoint/
├── SKILL.md              (about 40 lines: the steps)
└── references/
    └── error-codes.md    (1,200 lines: read when needed)
```

```md
## Steps

1. Name the route as resource/action, for example refunds/create.
2. Validate the input body before any database call.
3. Return errors in the team format. Look up the code in
   [references/error-codes.md](references/error-codes.md).
4. Add one success test and one failure test.
5. Add the endpoint to the API docs page.
```

### Step 4: why it is better

- The description names the task, so the agent can match it.
- The loaded skill is about 40 lines, not 1,240. The table is read only when a step needs a code.

## Common mistakes

1. **A field name with the wrong spelling.** `disable_model_invocation` with underscores does nothing. The Claude Code docs: "Claude Code ignores a field it doesn't recognize without reporting an error." Fix: copy field names from the frontmatter reference, hyphens included.
2. **Steps written as a one-time message.** Claude Code "does not re-read the skill file on later turns". Fix: write guidance that holds for the whole task as standing rules.
3. **Ten jobs in one skill.** A skill that formats, tests, deploys and writes docs needs a vague description to cover it all. Fix: the Codex docs say "Keep each skill focused on one job."

## Try it

Not graded. Write your answer down before you read the answer.

A Claude Code team has a skill called `service-map`. It explains what each of 30 old internal services does. The agent should use it when it reads code that calls those services. But typing `/service-map` makes no sense as a command, and the team wants it out of the `/` menu.

1. Which frontmatter field fits?
2. With that field, is the skill's description still in context in each session?

### Answer

1. `user-invocable: false`. The Claude Code docs say it is for "background knowledge that isn't actionable as a command". Only Claude can invoke the skill then, and it is hidden from the `/` menu.
2. Yes. The docs' table says "Description always in context, full skill loads when invoked" for this field. Compare `disable-model-invocation: true`, where the table says "Description not in context". If the agent can never start a skill, it does not need the card.

## Recap

- A skill is a folder with a `SKILL.md`: a name and description that say when to use it, plus instructions. Scripts and reference files are optional.
- At first the agent sees just each skill's name and description. Lead with the main task and trigger words, and keep the body short, with big reference material in separate files.
- Always true → instruction file; needed sometimes → skill. Lock side-effect skills with `disable-model-invocation: true` or `allow_implicit_invocation: false`, and keep shared skills in `.agents/skills/` with a symlink from `.claude/skills/`.

## Goal

After this lesson you can:

- Sort an agent's tools into allow, ask and deny by risk.
- Predict which rule wins in Claude Code, and pick a safe permission mode.
- Pause an OpenAI Agents SDK run for approval and resume it, even hours later.

## The problem

Nora's on-call agent can now do real things. Its tools: read metrics and logs, list pods with `kubectl get`, restart a service, roll back a deploy, and delete old log data.

The first setup was "allow everything, it runs on our own server". The prompt said "ask before a rollback". One night the agent restarted the search service three times in ten minutes. Nobody was asked. Another night it started to delete log data "to free disk space".

The model decides which tool to call. The harness must decide if that call may run.

## The idea

**Why the model can't be the only check.** The [Anthropic post on agents](https://www.anthropic.com/engineering/building-effective-agents) warns of "the potential for compounding errors" and advises "the appropriate guardrails". The [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) says there "**SHOULD** always be a human in the loop with the ability to deny tool invocations." The [agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop) put it plainly: Claude picks the tools, "but you control whether those calls are allowed to execute."

**Three answers.** Every tool call gets one: **allow** (run it), **ask** (pause for a person or your code), or **deny** (block it). A denied call is not a crash. Claude gets a rejection as the tool result and "typically attempts a different approach or reports that it couldn't proceed."

**Claude: rules, then mode.** The [Claude Code permissions docs](https://code.claude.com/docs/en/permissions) fix the order: "Rules are evaluated in order: deny, then ask, then allow." They add: "The first match in that order determines the outcome". A more specific rule does not jump the line. A bare deny such as `Bash` removes the tool; a scoped one such as `Bash(rm *)` keeps the tool and blocks matching calls ([SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)).

A permission mode handles calls that no rule settles. In short:

| Mode                | What it does with the rest                                 |
| ------------------- | ---------------------------------------------------------- |
| `default`           | Sends them to your `canUseTool` callback                   |
| `dontAsk`           | Denies anything that would prompt                          |
| `acceptEdits`       | Approves file edits and file commands like `mkdir`, `rm`   |
| `plan`              | Explores and plans; never auto-approves a file edit        |
| `auto`              | A model classifier allows or blocks each action it reviews |
| `bypassPermissions` | Approves almost everything; for isolated environments only |

Hooks run before all of this. A `PreToolUse` hook can deny a call, and "a hook deny applies even in `bypassPermissions` mode."

**OpenAI: approval on the tool.** In the [OpenAI Agents SDK](https://github.com/openai/openai-agents-python/blob/main/docs/human_in_the_loop.md), set `needs_approval=True` on a tool, or pass a function that decides per call. Local MCP servers use `require_approval`. The [OpenAI guide](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) says the run "records an approval interruption" and does not run the tool yet. The result returns `interruptions` plus a resumable `state`.

Think of a bank. Anyone can look at the balance. A big transfer needs a second signature. Nobody can delete the vault.

## Worked example

### Step 1: the weak setup

```python
options = ClaudeAgentOptions(
    permission_mode="bypassPermissions",
    system_prompt="... Always ask before a rollback. ...",
)
```

Every call runs. The prompt line is only a request (chapter 3).

### Step 2: sort the tools by risk

| Risk           | Tools                                          | Answer |
| -------------- | ---------------------------------------------- | ------ |
| Read only      | `error_rate`, `search_logs`, `kubectl get ...` | allow  |
| Changes things | `rollback`, `kubectl rollout restart ...`      | ask    |
| Can't undo     | `delete_log_data`, `kubectl delete ...`        | deny   |

### Step 3: write the rules

```python
options = ClaudeAgentOptions(
    permission_mode="default",            # unsettled calls -> canUseTool
    allowed_tools=["error_rate", "search_logs", "Bash(kubectl get *)"],
    disallowed_tools=["delete_log_data", "Bash(kubectl delete *)"],
)
# + a canUseTool callback that pages the on-call engineer and waits
# .claude/settings.json: "ask": ["rollback", "Bash(kubectl rollout restart *)"]
```

(Short tool names here. Custom tools get MCP-style names in a real config, like `mcp__ops__rollback`.)

`delete_log_data` is a bare name, so the agent never even sees that tool. `kubectl delete` stays blocked for every `kubectl delete` call. A rollback or a restart now pages the engineer first.

### Step 4: a rule that does not work

A teammate wants restarts to stop asking for one safe service. He adds an allow rule:

```text
ask:   Bash(kubectl rollout restart *)
allow: Bash(kubectl rollout restart deploy/search)
```

It still asks. Ask comes before allow in the order, so the ask rule decides. A narrow allow can't cut a hole in a broader ask or deny. To change it, he must change the ask rule itself.

### Step 5: the hard case — approval at 3 a.m.

The engineer's chat agent runs on the OpenAI Agents SDK. Its `rollback` tool is marked `needs_approval=True`. At 03:12 the agent wants a rollback, so the run stops and waits for a decision. The engineer answers at 03:50. By then the chat server has restarted.

Starting a new run with the same question would repeat the whole investigation, and it is not the same run. The OpenAI guide says: "serialize `state`, store it, and resume later. That's still the same run." So Nora's app saves the state when the pause happens. When the answer comes, it loads the state, calls approve or reject on the interruption, and resumes.

One more edge from the same guide: input guardrails run "only for the first agent" in a chain. Text that arrives later, for example in a log line, is not checked by them. So the check lives on the `rollback` tool itself, next to the side effect.

### Step 6: why it is better

- **Risk decides the answer.** Reads run, changes ask, and actions that can't be undone are blocked.
- **Rules in code.** Deny and ask rules hold whatever the prompt says.
- **Approvals survive a restart.** The run pauses, waits and resumes as the same run.

## Common mistakes

1. **`bypassPermissions` with a short tool list.** The list only pre-approves those tools; the mode approves the rest. Fix: for a headless agent, list its tools in `allowedTools` and set the mode to `dontAsk`, so anything else is denied.
2. **A narrow allow under a broad deny.** It never wins, because deny is checked first. Fix: make the deny rule narrower instead.
3. **Approval as a new turn.** Starting over loses the run's state. Fix: resolve the interruption and resume from the saved `state`.

## Try it

Not graded. Write your answer down before you read the answer.

A Claude Code project has these rules. What happens to each call?

```text
deny:  Bash(rm *)
ask:   Bash(git push *)
allow: Bash(git *)

1) git log --oneline
2) git push origin fix-login
3) rm -rf build
```

### Answer

1. **Runs.** No deny or ask rule matches. The allow rule `Bash(git *)` does.
2. **Asks.** Both the ask rule and the allow rule match. Ask is checked before allow, so the ask wins.
3. **Blocked.** The deny rule matches first. No other rule can change that.

## Recap

- The model proposes a call; the harness allows, asks or denies it. Sort tools by risk: read, change, can't undo.
- Claude Code checks deny rules first, then ask, then allow. The first rule that matches decides. A hook deny holds in every mode. Keep `bypassPermissions` for isolated environments.
- In the OpenAI SDK, `needs_approval` pauses the run. Save the `state`, then approve or reject and resume the same run.

Chapter 1 ended the loop in one way: the model stops asking for tools. That is the happy path. A real agent needs more ways to stop, and it needs a way to tell a finished run from a run that only stopped.

## The natural stop is not enough

The Claude docs say that without limits, "the loop runs until Claude finishes on its own." That is fine for well-scoped tasks, but it "can run long on open-ended prompts", such as "improve this codebase". Their advice: "Setting a budget is a good default for production agents."

So an agent needs two kinds of stop:

- **A done check:** the task is really finished.
- **A safety stop:** the run ends even if the task is not finished, before it costs too much.

## Hard limits: turns and money

**Claude Agent SDK.** Two options, both with no limit by default:

| Option                            | What it caps              |
| --------------------------------- | ------------------------- |
| `max_turns` / `maxTurns`          | Tool-use round trips      |
| `max_budget_usd` / `maxBudgetUsd` | Cost before the run stops |

At either limit, the SDK returns a `ResultMessage` with subtype `error_max_turns` or `error_max_budget_usd`. The budget cap also covers subagents: their spend counts toward the total.

**OpenAI Agents SDK.** The runner takes `max_turns`. If a run goes past it, the SDK raises a `MaxTurnsExceeded` exception. `max_turns=None` turns the limit off. If you want a controlled answer instead of an exception, the runner accepts `error_handlers` with a `"max_turns"` key, which returns a fallback final output.

Example: a research agent gets `max_turns=30` and `max_budget_usd=2.00`. A normal question takes 6 turns and 20 cents. A prompt that sends it in circles stops at 2 dollars, not 200.

## Always check how the run ended

A stop is not a success. In the Claude SDK, the `subtype` field "is the primary way to check termination state":

| Subtype                               | Meaning                                       |
| ------------------------------------- | --------------------------------------------- |
| `success`                             | Claude finished the task normally             |
| `error_max_turns`                     | Hit the turn limit first                      |
| `error_max_budget_usd`                | Hit the budget limit first                    |
| `error_during_execution`              | An error interrupted the loop                 |
| `error_max_structured_output_retries` | No valid structured output within the retries |

The final `result` text is only present on `success`, so "always check the subtype before reading it". The result also has a `stop_reason`, such as `end_turn`, `max_tokens` or `refusal`.

Example: an app that shows `result` without checking the subtype shows nothing, or crashes, every time the budget runs out.

## Stop on a tool

Sometimes the right end of a run is a tool call, not a text reply. The OpenAI SDK sets this with `tool_use_behavior`:

- `"run_llm_again"` (the default): tool results go back to the model.
- `"stop_on_first_tool"`: the first tool's output becomes the final response.
- `StopAtTools(stop_at_tool_names=[...])`: stop when any named tool is called.

The same page warns about a loop trap. If you force a tool call with `tool_choice`, the model may call a tool again after every result, "ad infinitum". To prevent this, the SDK resets `tool_choice` to `"auto"` after a tool call, controlled by `reset_tool_choice`.

## Stop before you start

A guardrail can end a run early. In the OpenAI SDK, an input or output guardrail can trip a "tripwire". The runner "immediately" raises an exception and halts the agent.

Timing matters. By default an input guardrail runs in parallel with the agent, so when it trips, the agent "may have already consumed tokens and executed tools". In blocking mode (`run_in_parallel=False`), the guardrail finishes first, and if it trips, "the agent never executes".

## A pause is not a stop

Human approval looks like a stop, but it is not one. OpenAI's guide: "Treat approvals as paused runs, not as new turns." The run returns pending `interruptions` and a saved `state`. After the decision, you resume the same run from that state (chapter 6).

## The other failure: stopping too early

Limits stop runs that go too long. The harder bug is a run that ends too soon. In Anthropic's long-running agent experiments, a later agent session would "look around, see that progress had been made, and declare the job done." Claude also tended "to mark a feature as complete without proper testing."

Their fix was a done check the agent could not skip: a JSON list of features, each starting as failing, and a rule to mark one passing only "after careful testing".

Claude Code gives you a mechanical version: a `Stop` hook. When it returns `decision: "block"` with a `reason`, it "prevents Claude from stopping", and Claude gets the reason as the next thing to act on. Example reason: "Run the test suite before finishing." Two guards stop this from looping forever: the hook input has `stop_hook_active`, and Claude Code ends the turn after stop hooks have continued it eight times in a row.

## Key points

- Every production agent needs a done check and a safety stop.
- Claude SDK: `max_turns` and `max_budget_usd`, no limit by default. OpenAI SDK: `max_turns`, which raises `MaxTurnsExceeded`.
- Check the result subtype before you read the answer. A stop is not a success.
- OpenAI's `tool_use_behavior` can end a run on a tool call.
- A tripwire in blocking mode stops a run before the agent spends anything.
- Approvals pause a run; they don't end it.
- Guard against early "done" too: a feature list or a `Stop` hook that checks the work.

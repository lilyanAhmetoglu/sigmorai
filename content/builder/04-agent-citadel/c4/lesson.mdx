## Goal

After this lesson you can:

- Decide when a subagent helps and when one agent is better.
- Write a delegation prompt that gives the subagent everything it needs.
- Choose between a handoff and an agent-as-tool in the OpenAI Agents SDK.

## The problem

A bad incident hits Nora's shop. Four services show errors at once: checkout, payments, search and shipping. The on-call agent reads the logs of all four, one after the other. After 30 turns its context is full of log lines. Its answer mixes up which error came from which service.

A teammate says: "Let's start one subagent per service." The first try uses the same short prompt four times: "Check the logs for errors." Two subagents report the same payments timeout. Nobody looks at the time window before the alert.

The team also has a support chat on the OpenAI Agents SDK. They want it to tell customers about incidents. Should a status specialist talk to the customer, or should the main chat agent stay in charge?

## The idea

**A subagent is a second agent with its own context.** The [Claude Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/subagents) describe it like this: tool calls and results "stay inside the subagent", and the parent gets back just the last message. The [Anthropic post on context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) gives sizes: a subagent may use "tens of thousands of tokens or more", but it returns a summary that is "often 1,000-2,000 tokens".

Think of a manager who sends four people to four rooms. Each one comes back with one page, not with every paper in the room.

The SDK docs name four benefits: context isolation, parallel work, special instructions per subagent, and fewer tools per subagent. A subagent has a `description` (when to use it) and a `prompt` (its own system prompt). It can also have `tools`, `model` and `maxTurns`. Claude picks a subagent from "the task and each subagent's `description`", so write clear descriptions.

**It knows only what you send.** A subagent does not see the parent's conversation, unless it is a fork. The docs: "The only content you pass from parent to subagent is the Agent tool's prompt string". So the prompt must carry the facts: times, error messages, decisions.

The [Anthropic research system post](https://www.anthropic.com/engineering/multi-agent-research-system) found that short, vague tasks made subagents repeat each other. Its rule: give each one "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."

**It costs more.** In the same post's data, "multi-agent systems use about 15× more tokens than chats." It works best for parallel, wide tasks. Tasks where agents must share one context, or depend a lot on each other, "are not a good fit for multi-agent systems today."

**OpenAI: who owns the reply?** The [OpenAI orchestration guide](https://developers.openai.com/api/docs/guides/agents/orchestration) asks one question first: who owns the final answer for the user?

- **Handoff:** use it when "A specialist should take over the conversation for that branch of the work". The model sees a handoff as a tool. By default the tool name is `transfer_to_<agent_name>`, so a `Status Agent` becomes `transfer_to_status_agent` ([handoffs docs](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)).
- **Agent as tool** (`as_tool()`): use it when "A manager should stay in control and call specialists as bounded capabilities". Good for a bounded job, "like summarization or classification".

The guide also warns that "Splitting too early" means more prompts, more traces and more steps to approve, "without necessarily making the workflow better."

## Worked example

### Step 1: one agent, four services

The single agent reads every log in its own context. The context grows each turn (chapter 1), and the four stories get mixed.

### Step 2: the weak split

```text
to sub 1..4:  "Check the logs for errors."
```

Each subagent starts fresh. It doesn't know the alert time, the service it owns, or what to send back. So two look at payments, and none looks at the right time window.

### Step 3: a full delegation prompt

```text
Objective: find the first error in the SHIPPING service and its likely cause.
Time window: 01:50-02:20 UTC. The alert fired at 02:10 UTC.
Known so far: payments deployed at 02:03 UTC (checked by the main agent).
Boundaries: shipping only. Other agents cover checkout, payments and search.
Tools: search_logs and error_rate. At most 10 tool calls.
Output: 5 lines max:
  first error time | error text | likely cause | evidence | confidence
```

It has an objective, boundaries, guidance on tools and an output format. It also carries the facts the subagent can't see.

### Step 4: define the subagent once

```python
agents={
    "service-investigator": AgentDefinition(
        description="Investigates ONE service during an incident. Use when "
                    "the alert touches several services and each needs a log search.",
        prompt="You check logs and metrics for one service. Report in the "
               "5-line format you are given. Never guess a cause without evidence.",
        tools=["search_logs", "error_rate"],   # read-only
        maxTurns=12,
    ),
}
```

The main agent now gets four short reports instead of thousands of log lines. It writes the final answer from them.

### Step 5: the hard case — a step that depends on another

Next, the team wants a fifth subagent: "roll back the bad deploy". But which deploy is bad? That is only known after the four reports come back. This step depends on the others, so it stays with the main agent. A subagent would only see its prompt, and the main agent already holds the answer.

The team also caps the tree. A subagent can start its own subagents, so the SDK has limits: nesting depth (default `3` layers), subagents at once (default `20`), and spend (`max_budget_usd`, "No limit" by default). Nora sets a budget, so four subagents can't turn into forty.

### Step 6: the support chat (OpenAI)

The customer should get one clear voice, and the status facts are a bounded lookup. So the status specialist becomes a tool of the main chat agent, with `as_tool()`. The main agent keeps the reply. A handoff would fit if the specialist had to take over the whole conversation, for example a billing specialist that talks to the customer from then on.

### Step 7: why it is better

- **Clean context.** The main agent gets four short reports, not every log line.
- **No gaps, no repeats.** Each prompt has an owner, a time window and a format.
- **Fewer tools.** The investigators can read but can't change anything.
- **Clear limits.** Steps that depend on each other stay in one agent, and the budget caps the tree.

## Common mistakes

1. **A one-line delegation.** "Look into it" gives no owner or format. Fix: objective, boundaries, tools and sources, output format.
2. **Assuming shared memory.** The subagent can't see what the parent saw. Fix: put the facts it needs in the prompt.
3. **Splitting everything.** Subagents for tiny or dependent steps only add tokens. Fix: start with one agent, and split only parallel, independent work.

## Try it

Not graded. Write your answer down before you read the answer.

For each task, say "subagents" or "one agent", and give one reason.

```text
A) Compare the error logs of 6 services for one hour.
B) Rename one config key, then update the 2 files that use it.
C) Summarize 40 long incident reports from last year, one paragraph each.
```

### Answer

- **A: subagents.** Six independent searches can run in parallel. Each one returns a short report, so the main context stays clean.
- **B: one agent.** It is small, and step 2 depends on step 1. Subagents would only add tokens.
- **C: subagents.** The reports are independent, and together they are too long for one context. Give each subagent a batch, a fixed output format and a length limit.

## Recap

- A subagent works in its own context and returns only its final message. It sees only the prompt you pass.
- A good delegation has an objective, an output format, tools or sources, and boundaries.
- Subagents cost many more tokens. Use them for parallel, independent work, and cap depth, count and spend. In OpenAI's SDK, a handoff gives the reply to the specialist; an agent-as-tool keeps it with the manager.

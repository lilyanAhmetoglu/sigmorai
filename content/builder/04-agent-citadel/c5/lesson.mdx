## Goal

After this lesson you can:

- Sort what an agent should remember by how long it must last.
- Put human rules in an instruction file and agent notes in a memory store.
- Write a memory handler that a bad path or a secret can't break.

## The problem

Nora's on-call agent forgets everything between nights.

- Every night at 03:00 the search service shows errors for ten minutes. It is the nightly reindex, and it is harmless. The agent finds this out again every night, after 15 turns.
- The engineer on duty chats with the agent during an incident. When the chat app restarts, the agent loses the whole chat.
- A teammate wants to "just put everything in the system prompt". It is already 300 lines long.

An agent remembers nothing on its own. Anything it "remembers" is text that something saved and loaded back. So memory is a harness job: what to save, where, and what to load next time.

## The idea

**Split memory by how long it lives.** This split is ours, but each vendor has a tool for each kind.

| Kind            | Lives for        | In Nora's agent                      |
| --------------- | ---------------- | ------------------------------------ |
| Working context | One run          | Tonight's tool results               |
| Session history | One conversation | The chat with tonight's engineer     |
| Long-term notes | Across sessions  | "Search errors at 03:00 are reindex" |

**Session history.** In the [OpenAI Agents SDK](https://github.com/openai/openai-agents-python/blob/main/docs/sessions/index.md), a session loads the history "Before each run" and stores new items "After each run". `SessionSettings(limit=N)` fetches "only the most recent `N` items"; the default, `limit=None`, fetches all. The [OpenAI guide](https://developers.openai.com/api/docs/guides/agents/running-agents) says to "pick one strategy per conversation", because mixing your own history with server-managed state "can duplicate context".

**Notes a human writes.** The [Claude Code docs](https://code.claude.com/docs/en/memory) say: "Each Claude Code session begins with a fresh context window." An instruction file, `CLAUDE.md` (or a repo's `AGENTS.md`), loads at the start of each session. The docs give three rules:

- Make lines "concrete enough to verify": "Use 2-space indentation" instead of "Format code properly".
- Keep each file under 200 lines. A long file costs more context and can "reduce adherence."
- Remove conflicts: with two rules that disagree, Claude "may pick one arbitrarily."

**Notes the agent writes.** The [Anthropic post on context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) calls this structured note-taking: the agent writes notes "outside of the context window", and they "get pulled back into the context window at later times." Three versions:

- The [Claude memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) stores files under `/memories`. It "operates client-side": Claude asks, your code reads and writes.
- Claude Code auto memory keeps a `MEMORY.md` index. At the start of a conversation it loads "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first". Detail goes in topic files.
- [OpenAI sandbox memory](https://developers.openai.com/api/docs/guides/agents/sandboxes) puts `memory_summary.md` in at the start of a run. The agent searches `MEMORY.md` only "when prior work looks relevant".

Think of a desk and a filing cabinet. A short summary sits on the desk every day. The full files stay in the cabinet until you need one.

**Memory is not a lock.** The Claude Code docs say Claude treats loaded memory "as context, not enforced configuration". To block an action, use a hook.

## Worked example

### Step 1: the weak setup

```text
System prompt: 300 lines (rules, old incident stories, service facts)
Chat history:  kept in the app's RAM, lost on restart
Agent notes:   none
```

### Step 2: human rules go in the instruction file

Nora moves the team's rules out of the prompt into `CLAUDE.md` and cuts them hard:

```text
Before:  "Be careful with times."
After:   "Write all times in UTC, like 02:04 UTC."

Before:  "Search can be noisy at night."   (line 40)
         "Treat every search error as real." (line 212)   <- conflict
After:   one line, the second one deleted
```

The old incident stories leave the file. They are notes, not rules. The file is now 60 lines.

### Step 3: the agent's own notes go in a memory store

The agent gets the memory tool. Nora's handler maps `/memories` to one folder per service:

```text
/memories/index.md               one line per note, read first
/memories/search/known-noise.md  "03:00-03:10 UTC errors = nightly reindex.
                                   Seen 14 nights. Ignore unless > 10 min."
/memories/payments/deploys.md    ...
```

With the tool on, Claude "automatically checks its memory directory before starting a task." So tonight it reads the index, opens `search/known-noise.md`, and skips the 15 turns.

### Step 4: the chat survives a restart

The engineer's chat goes through the chat app, which runs on the OpenAI Agents SDK. Nora gives it an `SQLiteSession` per incident and `SessionSettings(limit=40)`. A restart now loads the last 40 items. A long incident can't flood the context.

### Step 5: the hard case — the handler is the attack surface

The service name in a memory path comes from the alert text. The alert text comes from an outside monitor. One day a bad alert sets the service name to `..%2f..%2fconfig`. A naive handler builds:

```text
"/data/memories/" + "..%2f..%2fconfig" + "/known-noise.md"
-> after URL decoding: /data/config/known-noise.md     (outside the store!)
```

The memory tool docs warn: "A malicious path such as `/memories/../../secrets.env` can reach files outside the `/memories` directory." Their list of checks includes:

- Resolve each path "to their canonical form" and check that it stays inside the memory folder.
- Reject `../` and also "URL-encoded traversal sequences (`%2e%2e%2f`)".

Two more rules from the same page fit Nora's agent. A log line with an API key once ended up in a note. Claude "usually refuses" to store such data, but "For stronger guarantees", strip it in the handler before you write. And cap file sizes, and delete notes no one has read in a long time.

### Step 6: why it is better

- **Each memory has a home.** Rules in a short instruction file, chat in a session, lessons in notes.
- **Small loads.** An index loads every time; details load only when needed.
- **A safe handler.** Paths are checked in code, secrets are stripped, and size has a cap.

## Common mistakes

1. **Everything in the prompt.** Old stories and rules mix, and the prompt grows. Fix: rules in a short instruction file, lessons in notes.
2. **Trusting memory to block things.** A note like "never page the CEO" is only context. Fix: put hard rules in a hook.
3. **A handler that trusts the path.** Any path can come from model output or outside text. Fix: resolve it, check it stays in the folder, reject `../` in every form.

## Try it

Not graded. Write your answer down before you read the answer.

Where does each item belong: instruction file, session history, agent notes, or a hook?

```text
a) "Write all times in UTC."
b) What the engineer said ten minutes ago in tonight's chat.
c) "The shipping API is slow every Monday at 09:00 UTC; it recovers by itself."
d) "Never restart the database."
```

### Answer

- **a) Instruction file.** A team rule a human writes. It loads every session.
- **b) Session history.** It belongs to this one conversation.
- **c) Agent notes.** A lesson learned from past nights. The agent can read it back when shipping looks slow.
- **d) A hook.** It must hold every time. Memory and instructions are only context, so they can't block a call.

## Recap

- An agent remembers only what the harness saves and loads back. Sort memory into working context, session history and long-term notes.
- Human rules go in a short, concrete instruction file with no conflicts. Agent notes go in a store with a small index that loads first.
- Memory is context, not enforcement. Your handler must check every path, strip secrets and cap size.

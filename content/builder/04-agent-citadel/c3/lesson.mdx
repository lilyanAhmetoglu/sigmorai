## Goal

After this lesson you can:

- Say what a harness is, and pick who runs the loop: you, a library or the vendor.
- Put each rule in the right place: an instruction for habits, a hook for rules that must always hold.
- Hand a new session the state it needs when one task spans many sessions.

## The problem

Nora's on-call agent works. Now the team wants to run it for real. Three questions come up:

1. Today the loop is 80 lines of their own code. Should they keep it, use a library, or let a vendor host it?
2. The prompt says "never roll back the payments service at night". One night the agent rolled it back anyway.
3. A big incident lasted all night. The team restarted the agent three times. Each new session started from zero and checked the same things again.

None of these is about the model. They are about the code around it.

## The idea

**The harness is everything around the model.** The [Claude Code docs](https://code.claude.com/docs/en/how-claude-code-works) say Claude Code is "the layer around the model": it gives the model its tools and "manages the context the model sees". The docs call this layer the agentic harness. The [OpenAI architecture page](https://developers.openai.com/api/docs/guides/agents-api/architecture) means the same thing: its harness "maintains the agent's session" and "runs the model and tool loop".

Think of a race car. The model is the engine. The harness is the car around it: wheels, brakes and dashboard.

**Three levels.** Both vendors let you pick who runs the loop. The grouping is ours; each vendor compares its own options.

| Who runs the loop  | Anthropic        | OpenAI        |
| ------------------ | ---------------- | ------------- |
| Your own code      | Client SDK       | Responses API |
| A library you host | Claude Agent SDK | Agents SDK    |
| The vendor         | Managed Agents   | Agents API    |

- The [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) says: with the Client SDK, "You write the tool loop yourself". The Agent SDK is "a library that runs the Claude Code binary". It comes with tools, hooks, permissions and sessions built in. Managed Agents is "a hosted agent harness": Anthropic runs the loop for you.
- The [OpenAI agents guide](https://developers.openai.com/api/docs/guides/agents) rates the work for you as Low for the Agents API, Medium for the Agents SDK and High for the Responses API.

**The environment is a second choice.** Where commands run is not the same as where the loop runs. OpenAI's Agents API can use an OpenAI-hosted sandbox, your own compute (`self_hosted`), or no environment (`none`). Without one, the built-in shell and patch tools are gone too: the docs say "workspace files, and executor MCPs are unavailable." Claude Managed Agents can also run sessions in a self-hosted sandbox.

**Requests and guarantees.** The [Claude Code docs on extensions](https://code.claude.com/docs/en/features-overview) list what you add to a harness: an instruction file (`CLAUDE.md`), skills, MCP, subagents and hooks. Their key rule: an instruction in `CLAUDE.md` or a skill "is a request, not a guarantee". A hook "Always fires on its event", while for instructions the "outcome can vary". So a rule that has to hold every single time belongs in a hook, "rather than a prompt instruction."

## Worked example

### Step 1: the weak setup

```text
Loop:        80 lines of custom code around the Client SDK
Rules:       all in the system prompt, including the payments rule
Between runs: nothing is saved
```

It works, but every new feature (approval, limits, logs) is more custom code. And every rule is only a request.

### Step 2: pick the level

Nora's team wants hooks, permissions and ready-made tools. They also want the loop inside their own service, next to the metrics and pager code. So Nora picks a library harness: the Claude Agent SDK. (On OpenAI, the match is the Agents SDK.)

A team that wants less code could pick a hosted harness instead. If its commands must still run inside its own network, it adds a self-hosted environment or sandbox.

### Step 3: put each rule in the right place

```text
CLAUDE.md (habits, can vary):
  - Error rate comes from error_rate(), not from log counts.
  - Write times in UTC, like 02:04 UTC.

Skill (loaded when needed):
  - The payments runbook: steps for a payments incident.

Hook (must hold every time):
  - PreToolUse on rollback: if service == "payments"
    and the time is 22:00-07:00 UTC -> deny.
```

The night rule moved from the prompt to a hook. The agent can still try a payments rollback at night, but the hook stops the call before it runs.

### Step 4: the hard case — one incident, many sessions

The all-night incident is harder. Each session starts with "no memory of what came before", as the [Anthropic post on long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) puts it. In their tests, compaction alone "isn't sufficient".

Their fix was in the harness. A first session set up a progress file, an `init.sh` script and a git commit. Every later session read the progress file and git log first. The first session also listed every feature the app needed (over 200 in their test) and set each one to "failing". A later session picked one, built it, tested it, and only then flipped it to passing. Nora copies the idea for incidents:

```text
incident-0412/notes.md      what each session found, newest at the top
incident-0412/checks.json   [ { "check": "payments error rate", "done": false }, ... ]

Each session starts with:
  1. Read notes.md and checks.json.
  2. Pick the first check with "done": false.
  3. Before stopping, add a note and set "done": true only for checks really run.
```

Why JSON for the checklist? The post found the model "less likely to inappropriately change" a JSON file than a Markdown one.

### Step 5: why it is better

- **Less custom code.** The library runs the loop, tools, hooks and permissions.
- **Real enforcement.** The payments rule is a hook. It holds even when the model forgets it.
- **A clean handover.** Each new session starts from the notes, not from zero.

## Common mistakes

1. **A hard rule in the prompt.** "NEVER do X" in capitals is still a request. Fix: make it a hook or a permission rule.
2. **Mixing up harness and environment.** "Hosted" can mean the loop, the sandbox, or both. Fix: decide each one on its own.
3. **Hoping memory carries over.** A new session knows only what the harness gives it. Fix: save notes and a checklist, and read them at the start.

## Try it

Not graded. Write your answer down before you read the answer.

Sort these four lines from Nora's draft into "instruction file" or "hook".

```text
a) Prefer short answers with one line per finding.
b) Never run DROP TABLE on the orders database.
c) Use the team's incident template for summaries.
d) Never send customer emails from the agent.
```

### Answer

- **Instruction file:** a and c. They are habits. If the agent slips once, nothing breaks.
- **Hook:** b and d. They must hold every time, and a slip can't be undone. A hook that blocks the call is enforcement. A line in the prompt is only a request.

## Recap

- The harness is the code around the model: loop, tools, context and state. You can write it, use a library, or let the vendor host it.
- Where commands run (the environment) is a separate choice from who runs the loop.
- Habits go in instructions. Rules that must always hold go in hooks or permissions. Long tasks need saved notes that each new session reads first.

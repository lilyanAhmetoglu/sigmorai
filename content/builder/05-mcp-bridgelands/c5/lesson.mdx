An MCP server can run on the user's laptop or in the cloud. That choice is the transport, and it decides which hosts can reach the server, how it scales, and what you must secure. The messages stay the same: the spec says "Protocol semantics are identical on every transport."

## The two standard transports

The spec defines two:

1. **stdio:** the client launches the server as a subprocess and talks over its standard streams.
2. **Streamable HTTP:** the server is an independent process that "can handle multiple client connections". Each message is an HTTP POST to one MCP endpoint.

Custom transports are allowed, but they must keep the JSON-RPC format and the message patterns.

## stdio: a local process

With stdio, the server reads messages from `stdin` and writes them to `stdout`, one JSON-RPC message per line. The rules are strict:

- The server must not write anything to `stdout` that is not a valid MCP message.
- The server may write logs to `stderr`. The client should not assume `stderr` output means an error.
- To shut down, the client closes the server's input and waits. If the server process dies, the client should restart it.

A common bug follows from rule one. A developer adds a `print("debug")` to a stdio server, the line lands on `stdout`, and the client can't parse it. Log to `stderr` instead.

stdio fits tools that need the local machine. Claude Code says stdio servers "run as local processes on your machine" and are "ideal for tools that need direct system access or custom scripts."

## Streamable HTTP: a remote service

With Streamable HTTP, the server has one endpoint, for example `https://example.com/mcp`. The client POSTs every request there. For each request, the server answers with either one JSON object or a Server-Sent Events (SSE) stream for that request. The stream can carry progress notifications before the final response.

The spec gives three security rules for this transport:

- Servers must validate the `Origin` header on all incoming connections, to prevent DNS rebinding attacks. An invalid `Origin` gets HTTP 403.
- When running locally, servers should bind only to localhost (127.0.0.1), not all interfaces (0.0.0.0).
- Servers should implement proper authentication for all connections (chapter 6).

The older HTTP+SSE transport is deprecated. The spec says new implementations should not adopt it. The Claude Code docs and the OpenAI Agents SDK docs both mark SSE as deprecated too.

## No sessions: state goes in handles

In the 2026-07-28 revision, MCP has no protocol-level session. Every request carries its own version and capabilities, and Streamable HTTP no longer uses session ids. Our reading: this makes scaling simpler, because no request depends on hidden state from an earlier one on the same connection.

What if a tool needs state, like a shopping cart? The tools page suggests a handle: a creation tool returns an id such as `bsk_a1b2c3`, and later calls pass it as an argument. On an authenticated server, check the caller's authorization against the handle on every call. Say the handle's lifetime in the tool description, for example "baskets expire after 24 hours of inactivity".

## Which hosts can reach which servers

This is where the vendors differ most:

- **Claude API MCP connector:** the server "must be publicly exposed through HTTP". It supports Streamable HTTP and SSE. The `url` must start with `https://`. "Local STDIO servers cannot be connected directly."
- **OpenAI Responses API:** remote servers must support Streamable HTTP or HTTP/SSE. For a private, on-premises or firewalled server, OpenAI offers Secure MCP Tunnel, which connects it "without exposing it to the public internet".
- **Claude Code:** local stdio, remote HTTP (the recommended option for remote servers), deprecated SSE, and WebSocket servers.
- **OpenAI Agents SDK:** `HostedMCPTool` lets the Responses API call a public server for you. `MCPServerStreamableHttp`, `MCPServerSse` and `MCPServerStdio` let your own process connect.

So a stdio server on a laptop works with Claude Code or the Agents SDK. To use it from the Claude API, it has to become a public HTTPS server.

## Latency and cost of tool lists

A remote server adds a network call before the model can even see its tools. The vendors offer ways to reuse the list:

- **OpenAI Responses API:** while the `mcp_list_tools` item stays in context, the API does not fetch the list again each turn. OpenAI recommends keeping it there.
- **OpenAI Agents SDK:** `cache_tools_list` caches `list_tools()`. Use it only if tool definitions rarely change.
- **Claude API:** a beta lets you pin a server's tool list, so a server that changes its tools does not change what Claude sees mid-conversation.

Big tool lists also cost tokens. OpenAI says you "only pay for tokens used when importing tool definitions or making tool calls". Both Claude and OpenAI let you defer loading MCP tools with tool search, so only the tools a task needs are loaded.

## Key points

- stdio: local subprocess, messages on `stdout` only, logs on `stderr`.
- Streamable HTTP: one POST endpoint, JSON or a per-request SSE stream. Validate `Origin`, bind locally to 127.0.0.1, authenticate.
- HTTP+SSE is deprecated.
- No protocol sessions in 2026-07-28. Keep state in explicit handles and check authorization on each call.
- The Claude API connector needs a public `https://` server. OpenAI can reach private servers through Secure MCP Tunnel.
- Reuse tool lists: keep `mcp_list_tools` in context, cache in the Agents SDK, pin on Claude.

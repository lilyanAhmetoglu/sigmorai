## Goal

After this lesson you can:

- Choose the right kind of credential for a production service and keep it out of the browser.
- Rotate a key with no downtime, and act fast when a key leaks.
- Check which features store data before you build on them under a zero data retention deal.

## The problem

A small agency builds a homework helper for a school on the Claude API. Students type questions, and the app explains the steps. The school's contract with Anthropic includes zero data retention (ZDR), and the school has a firm rule: no student text may stay at the vendor after the answer.

The prototype works, but a review finds:

1. The API key sits in a `config.js` file that the browser downloads.
2. Staging and production use the same key, in the same workspace.
3. The key was made by a freelancer who leaves at the end of the month.
4. A new feature uploads each worksheet with the Files API, so the model can read it later.

Each item is a risk. Some are about secrets, and some are about data.

## The idea

An API key is money and access in one string. Treat it like a house key: keep it in a safe, give each person or service their own, and change the lock when one goes missing. User prompts are other people's data, so you protect them too.

### The right kind of key

The [Claude authentication page](https://platform.claude.com/docs/en/manage-claude/authentication) lists three API key types:

- **Personal key:** acts as you, with your roles. "A shared personal key acts as one person and breaks when they leave." The [workspaces page](https://platform.claude.com/docs/en/manage-claude/workspaces) says: "Personal keys are archived when their user is removed from the organization."
- **Service account key:** belongs to a service account, so the workload has its own identity. The docs say shared or automated workloads, such as CI and production services, should use one.
- **Workspace key:** legacy. It still works, but identity-backed keys are preferred.

There is also Workload Identity Federation. Your workload swaps a short-lived token from your identity provider for a short-lived Claude token, so there is no long-lived key to rotate. The docs add that it "does not, on its own, guarantee end-to-end security". It is only as strong as your identity provider's setup.

Other vendors move the same way. OpenAI administrators can "allow only service-account keys, allow only user-owned project keys, or disable all new API key creation". Gemini's newer authorization keys are bound to a service account and give "fast-acting leaked key enforcement".

### Where keys live

- **In a secrets manager or environment variable.** Claude: "Store API keys in a secrets manager, rotate them periodically, and disable or delete any key you suspect has leaked." OpenAI: "Avoid exposing the API keys in your code or in public repositories".
- **Never in the browser.** The [Gemini key page](https://ai.google.dev/gemini-api/docs/api-key) says: "Keys compiled in client-side code can be extracted by users. To secure client-side apps, run a backend proxy server to make the actual API calls." Hiding or minifying the code does not help, because anyone can watch the network requests.

Your server then holds the key and owns the rules. It checks who the user is and applies a per-user limit. It can also send a per-user id. The [OpenAI safety page](https://developers.openai.com/api/docs/guides/safety-best-practices) calls this `safety_identifier`: "a string that uniquely identifies each user". It says to "Hash the username or email address" so no personal data is sent.

### Expiry and rotation

Claude lets you pick an expiry when you create a key: 3 hours, 1 day, 7 days, 30 days, a custom duration, or Never. The Claude docs say:

- Expiration "is set at creation time and cannot be changed afterward".
- After it, requests "return a `401 authentication_error`".
- "Create a new key to restore access; expired keys cannot be reactivated."
- Expiry "is not a substitute for secret hygiene".

The [OpenAI production guide](https://developers.openai.com/api/docs/guides/production-best-practices) "strongly" recommends an expiry on every project key and regular rotation. Its order: "create a replacement, update your applications to use it, and revoke the old key once you've verified that the replacement works". Both keys stay valid while you switch, so no request fails.

### When a key leaks

The OpenAI safety page says: "revoke it promptly and replace it with a new key". In the Claude Console, Disable can be undone and Delete is permanent. Claude's Usage and Cost API can filter usage by API key, so you can look for misuse.

### Separate environments

On Claude:

- Workspaces "separate different projects, environments, or teams".
- A key "created for a specific workspace" works there and nowhere else. Its requests "can omit the workspace ID".
- Each workspace can have its own limits (chapter 1).

OpenAI suggests separate staging and production projects, with "custom rate and spend limits per project".

### What the vendor keeps

The [Claude retention page](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) and the [OpenAI data page](https://developers.openai.com/api/docs/guides/your-data) compare like this:

| Topic        | Claude                                                                                 | OpenAI                                                           |
| ------------ | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Default      | Conversation content "is not retained by default", except for Covered Models (30 days) | Abuse monitoring logs kept "for up to 30 days" by default        |
| No retention | ZDR, enabled per organization through the sales team                                   | Zero Data Retention or Modified Abuse Monitoring, after approval |
| Training     | "never used for model training without your express permission"                        | Not used to train models unless you opt in                       |
| Not eligible | Batch (29-day retention), Files, code execution, Managed Agents                        | `/v1/batches`, `/v1/files`, `/v1/conversations` and more         |

Three details matter:

- **ZDR does not block features.** Under ZDR, the Claude API "does **not** block" features marked No. "Using them is a choice to step outside your ZDR arrangement" for that data. ZDR covers Claude's Messages and Token Counting endpoints, for eligible features only.
- **ZDR has limits.** If a chat is flagged by trust and safety systems, Anthropic "may retain inputs and outputs for up to 2 years".
- **OpenAI ZDR changes `store`.** It "will always be treated as `false`, even if the request attempts to set the value to `true`". Endpoints marked No "may still store application state".

## Worked example

Our example: the homework helper, fixed one finding at a time.

### Step 1: the weak setup

```text
browser:   config.js holds the API key and sends requests straight to Claude
key:       personal key of the freelancer, expiry Never
envs:      staging and production share one key and one workspace
feature:   worksheets uploaded with the Files API
```

### Step 2: move the key to a server

```text
browser -> our server (login, per-user limit) -> Claude API
key:       in the server's secrets manager, read from an environment variable
```

The old key was public, so treat it as leaked. Disable or delete it, and look at its usage by API key.

### Step 3: a service account per environment

```text
workspace "homework-staging":  service account key, small spend limit
workspace "homework-prod":     service account key, its own rate limit
```

The freelancer can leave. No production key belongs to a person.

### Step 4: rotate without downtime (the hard case)

The production key must be replaced next week. Our example: a deploy takes about 15 minutes.

```text
weak order:   revoke old -> create new -> deploy (15 min)   => 15 min of 401 errors
good order:   create new -> deploy (15 min) -> check calls work -> revoke old
```

In the good order the old key keeps working while the new one rolls out. The gap is zero minutes.

### Step 5: check the data rule

Files is a "No" feature under ZDR. The API would not stop the upload, but the worksheets would be stored. Our fix: send the worksheet text inside each normal Messages request instead, which is ZDR eligible. Read the eligibility table before you design a feature, not after.

### Step 6: why it is better

- No key in the browser, and no key tied to one person.
- A staging bug cannot spend the production budget.
- Rotation has no gap, and a leak has a plan.
- The school's data rule holds, because every feature is eligible.

## Common mistakes

1. **Relying on expiry for a leaked key.** The date cannot be changed after creation, and the key stays usable until then. Fix: disable or delete it now.
2. **Assuming ZDR blocks risky features.** It does not. Fix: check each feature in the eligibility table.
3. **Putting secrets in prompts.** Our rule: anything in a prompt can show up in an output, a log or a trace (chapter 3). Fix: never send keys or passwords to the model, and send only the fields the task needs.

## Try it

Not graded. Write your answer down before you read the answer.

Pick a Claude credential for each workload, and say why:

1. A developer's own test script on a laptop.
2. A GitHub Actions job that runs the eval suite on every pull request.
3. A production server that should have no long-lived key at all.

### Answer

1. **A personal key.** The docs suggest it for your own development and scripts.
2. **A service account key** in the CI secret store. CI is a shared, automated workload, so it needs its own identity. Workload Identity Federation also fits, because GitHub Actions can issue identity tokens.
3. **Workload Identity Federation.** The server swaps a short-lived token from its identity provider, so there is no `sk-ant-api...` string to store or rotate. Keep that identity provider locked down, because the docs say federation alone does not guarantee security.

## Recap

- Production uses a service account key or federation, kept in a secrets manager, and never in the browser.
- Rotate by creating the new key first and revoking the old one last. Disable or delete a leaked key at once.
- ZDR does not block features that store data. Check each feature's eligibility before you build.

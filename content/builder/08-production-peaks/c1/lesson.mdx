## Goal

After this lesson you can:

- Tell a temporary rate limit apart from a spend cap that retries cannot fix.
- Write a retry policy that waits long enough, adds jitter and has one layer only.
- Keep one heavy workload from taking the capacity that another one needs.

## The problem

A recipe app shows a short cooking tip on each recipe page. A model writes the tip on the Claude API. On Sunday evening a TV show mentions the app, and traffic jumps from a few calls a minute to hundreds.

The team sees three things in one evening:

1. Some calls get a 429, but the dashboard says they are far below the per-minute limit.
2. A worker that gets a 429 retries at once. Then it gets another 429.
3. Late at night every call fails with a 429, and retries never help. In the morning the calls still fail.

The team treats every 429 the same way. That is the mistake.

## The idea

A rate limit is a cap on how much you can send in a time window. Claude measures requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM), per model class. Think of a water tank that refills at a steady speed. The Claude docs name the token bucket algorithm for this, so "your capacity is continuously replenished up to your maximum limit, rather than being reset at fixed intervals". There is no clean minute boundary to wait for.

### Limits also work over short windows

A limit per minute is not a promise for every second. The [Claude rate limits page](https://platform.claude.com/docs/en/api/rate-limits) says "a rate of 60 requests per minute (RPM) might be enforced as 1 request per second". Short bursts can trigger a 429 even when the minute total is low.

Growth speed matters too:

- **Claude:** the docs warn about acceleration limits. When usage rises sharply, you can get 429 errors. Their advice: "ramp up your traffic gradually and maintain consistent usage patterns".
- **OpenAI:** the [rate limits guide](https://developers.openai.com/api/docs/guides/rate-limits) has the `slow_down` code. It "can occur even when your traffic is within its requests-per-minute and tokens-per-minute limits".
- **OpenAI's rule of thumb:** once traffic reaches 1 million input tokens per minute, "increase it by no more than 50% every 15 minutes".

### Not every 429 is a rate limit

The [Claude errors page](https://platform.claude.com/docs/en/api/errors) says a 429 `rate_limit_error` can mean a rate limit, the usage tier's monthly spend cap, or a spend limit on the Claude Code workspace.

| What you see                                                                               | What it means                  |
| ------------------------------------------------------------------------------------------ | ------------------------------ |
| Claude 429 with `retry-after`                                                              | A temporary rate limit         |
| Claude 429, no `retry-after`, `error.details.error_code` is `enforced_spend_limit_reached` | The tier's monthly spend cap   |
| Claude 400 `invalid_request_error`, "You have reached your specified API usage limits"     | A spend limit you set yourself |
| Claude 500 or 529, OpenAI 503 `server_is_overloaded`                                       | A problem on the vendor side   |

The spend-cap 429 is the trap. The Claude docs say: "Retrying, including the SDK's automatic retries, fails until access resumes." Usage pauses until the first day of the next month, unless the organization gets a higher limit sooner. The cap covers all of the organization's spending. Another key gets the same error. OpenAI has a similar case: a hard spend limit makes affected requests return a 429. Its guide adds that `Retry-After` does not mean quota or billing errors "can be resolved by retrying".

### Retries can make it worse

The [OpenAI guide](https://developers.openai.com/api/docs/guides/rate-limits) gives the rules for a safe retry:

- Treat `Retry-After` "as a minimum", and add "a small random delay so multiple clients don't retry at the same time". This random delay is called jitter.
- If the header is missing, use exponential backoff with jitter.
- "Limit both the number of attempts and the total time spent retrying."
- Remember that "unsuccessful requests contribute to your per-minute limit".

SDKs retry too. The Claude SDK retries rate limits and 5xx errors "twice by default", and honors `retry-after`. You can change this with `max_retries`. OpenAI's SDKs retry eligible 429 and 503 responses. The OpenAI guide says: if you manage retries yourself, "disable SDK retries or account for them in those limits so nested retry loops don't multiply requests". Two layers multiply, they do not add.

Streams need care. The Claude docs note that an error can arrive after the API already returned 200. The OpenAI guide says: "don't automatically replay a request after consuming output."

### Read the headers

Every Claude response tells you how much room is left: `anthropic-ratelimit-requests-remaining`, `anthropic-ratelimit-input-tokens-remaining` and `anthropic-ratelimit-output-tokens-remaining`, each with a `-reset` time. Token values are "rounded to the nearest thousand". OpenAI sends `x-ratelimit-remaining-requests` and `x-ratelimit-remaining-tokens`. When these numbers are high and you still get a 429, think of bursts or acceleration, not the minute total.

### Keep workloads apart

By default, workloads in one organization share its limits. The Claude docs let you set custom spend and rate limits per workspace, "to protect Workspaces in your Organization from potential overuse". Three rules from that page:

- "You can't set limits on the default Workspace."
- "If not set, Workspace limits match the Organization's limit."
- "Organization-wide limits always apply, even if Workspace limits add up to more."

The other vendors work the same way:

- **OpenAI:** limits are set at the organization and project level, "not user level". The [production guide](https://developers.openai.com/api/docs/guides/production-best-practices) lets you set custom rate and spend limits per project.
- **Gemini:** the [rate limits page](https://ai.google.dev/gemini-api/docs/rate-limits) says: "Rate limits are applied per project, not per API key." An extra key in that project shares the same budget.
- **Gemini daily quotas** "reset at midnight Pacific time", and preview models have tighter limits.

### Caching adds room

For most Claude models, "only uncached input tokens count toward your ITPM rate limits". The docs' example: with a 2,000,000 ITPM limit and an 80% cache hit rate, you can process about 10 million input tokens a minute (2M uncached plus 8M cached).

## Worked example

Our example: the recipe app's retry policy.

### Step 1: the weak policy

```text
SDK client:  default settings (2 retries)
Our wrapper: on any error, wait 1 s and retry, up to 3 times
Launch:      all traffic switched on at once
```

What goes wrong:

- It retries before `retry-after` ends, so the retry fails again.
- Every worker waits exactly 1 s, so they all retry in the same moment.
- It retries everything, including the spend cap and bad requests.
- Two layers multiply. The wrapper makes 4 tries (1 plus 3). The SDK turns each of those into as many as 3 requests (1 plus 2). So one tip can send 4 × 3 = 12 requests, and every failed one counts against the limit.

### Step 2: sort the errors first

```text
429 + retry-after                                   -> retry after the wait
429, no retry-after, enforced_spend_limit_reached   -> stop, alert a person
400 "You have reached your specified API usage..."  -> stop, raise or remove the limit
500 or 529                                          -> retry with backoff
any other 4xx                                       -> stop, fix the request
```

### Step 3: one retry layer, with limits

```text
SDK client:  max_retries = 0
Our wrapper: wait = retry-after (or backoff 1 s, 2 s, 4 s) + random 0-1 s
             at most 3 attempts in total, at most 30 s in total
```

Now one tip sends at most 3 requests, not 12.

### Step 4: the hard case, a 429 with plenty of room

The late-evening logs show a 429 while `anthropic-ratelimit-requests-remaining` still shows most of the limit. The limit is 600 RPM. The traffic is 300 requests in the minute, so the total is fine.

Two explanations fit the docs. Traffic grew from a few calls to hundreds in minutes, so acceleration limits are likely. And a burst can trip a short window. Our reading of the docs' 60 RPM example: 600 RPM might act like about 10 requests a second, and a queue that sends 50 at once breaks that. The fix is not more retries. Release queued work in steady steps, and grow traffic slowly.

### Step 5: why it is better

- Spend-cap errors stop at once, and a person hears about it.
- Jitter spreads the retries, so workers do not hit the limit together.
- One layer and a time cap keep the worst case small: 3 requests and 30 s.
- A steady ramp avoids the 429s that come from fast growth.

## Common mistakes

1. **Retrying every 429.** A spend-cap 429 keeps failing. Fix: check `retry-after` and `error_code` before you retry.
2. **A new API key to get more room.** Keys share the limits of their organization, workspace or project. Fix: use a separate workspace or project with its own limit.
3. **Retry loops inside retry loops.** The counts multiply. Fix: keep one layer, and turn the SDK retries off or count them.

## Try it

Not graded. Write your answer down before you read the answer.

A Gemini app gets 429 errors on its free project. A teammate says: "Make three more API keys in the project and rotate between them." Another says: "Let the daily quota reset at noon, then run the job." Find the problem in each idea.

### Answer

1. **More keys add nothing.** Gemini limits are per project, not per API key. All four keys share one budget. Fix: send less traffic, or move the project to a higher usage tier.
2. **The reset time is wrong.** Daily quotas reset at midnight Pacific time, not at noon. Fix: plan the job for after that reset, in your own time zone.

## Recap

- A 429 can be a rate limit, an acceleration limit or a spend cap. Only some of them clear with time.
- Never retry before `retry-after` ends, add jitter, cap attempts and total time, and keep one retry layer.
- Keep workloads apart with workspaces or projects. Limits belong to the organization, workspace or project, not the key.

## Goal

After this lesson you can:

- Find where the time goes in a model call, and pick the change that saves the most.
- Cut waiting with parallel steps, fewer requests and streaming.
- Decide when a paid fast mode fits, and set deadlines for long calls.

## The problem

An online shop has a "compare two products" button. It takes 8.3 seconds, and many users leave before the answer shows. The team's first idea is to shorten the prompt. The second idea is to buy a faster tier for everything, including the nightly jobs.

Neither idea is the best place to start. You first need to know where the 8.3 seconds go.

## The idea

### Two numbers to measure

The [Claude latency guide](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency) separates two numbers:

- **Baseline latency:** the time to process the prompt and generate the response.
- **Time to first token (TTFT):** the time "to generate the first token of the response, from when the prompt was sent". You need it most when you stream.

Measure both, and use percentiles (chapter 3). The Claude guide also says to get the prompt working first, because reducing latency too early "might prevent you from discovering what top performance looks like".

### Output is the slow part

The [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization) splits a request into steps: the trip to the API, reading the prompt, generating tokens, and the trip back. It says generating tokens "is almost always the highest latency step". Its two rules of thumb:

- "cutting 50% of your output tokens may cut ~50% of your latency"
- "cutting 50% of your prompt may only result in a 1–5% latency improvement"

Think of a phone call: listening to a long question is quick, but the reply is spoken one word at a time. So the order of work is:

1. **A smaller or faster model,** if your evals still pass. The OpenAI guide: "smaller models usually run faster (and cheaper)". For speed-critical apps, the Claude guide names Claude Haiku 5.5.
2. **Shorter output.** The Claude guide says that asking for an exact word count "is not as effective" as limits in sentences or paragraphs. It calls `max_tokens` "a blunt technique", because a reply can stop mid-sentence. For structured output, OpenAI suggests shorter function names and less syntax.
3. **Shorter input,** only when the context is very large, or to save money.

### Do less, and do it in parallel

The OpenAI guide lists more ways to cut waiting:

- **Make fewer requests.** Steps that run one after another can often go in one prompt.
- **Parallelize.** Steps that do not depend on each other can run at the same time. "Two shirts take just as long to dry as one."
- **Speculative execution.** If step 2 needs step 1 to pass, start both at once anyway. If step 1 fails, cancel step 2. When it passes, you "essentially got to run it with zero added latency".
- **Don't default to an LLM.** Fixed messages, such as an action confirmation, can be hard-coded.

### Make waiting feel shorter

The OpenAI guide lists these ways to make users wait less:

- **Streaming:** "The single most effective approach". The first words show in "a second or less".
- **Chunking:** process the output in parts, and show each part when it is ready.
- **Showing your steps and loading states:** these have "a mostly psychological effect".

Streaming and chunking, by contrast, really do cut the time before users can read.

The Claude guide says streaming improves "perceived responsiveness". But streaming does not make the full answer finish sooner.

### Paying for speed

Both vendors sell a faster mode for the same model, at a higher price:

- **Claude fast mode** ([docs](https://platform.claude.com/docs/en/build-with-claude/fast-mode)) is a research preview, by request or waitlist.
  - Set `speed: "fast"` with the `fast-mode-2026-02-01` beta header on Claude Opus 5.5, Claude Opus 5 or Claude Opus 4.8.
  - You get "up to 2.5x higher output tokens per second" at premium pricing.
  - Only the output speed goes up, "not time to first token (TTFT)".
  - It has its own rate limit, and `speed` is not supported in a batch (chapter 2).
- **OpenAI Fast mode** ([docs](https://developers.openai.com/api/docs/guides/priority-processing)) gives "up to 2.5× faster speeds".
  - Set `service_tier` to `fast` (or `priority`). It "charges a per-token premium".
  - The docs say to "Avoid running large extract, transform, and load (ETL) or batch jobs in Fast mode".
  - If traffic ramps too fast, some requests drop to standard speed and price, and the response shows `service_tier: "default"`.

Our rule: use a fast mode for user-facing calls where speed matters. Use batch or Flex for work nobody waits for (chapter 2). Claude's Priority Tier is a different product: the [service tiers page](https://platform.claude.com/docs/en/api/service-tiers) says commitments "are no longer available for purchase".

### Long calls and deadlines

The [Claude errors page](https://platform.claude.com/docs/en/api/errors) warns against a large `max_tokens` without streaming or the Batch API: "Some networks may drop idle connections after a variable period of time". The SDKs check that a non-streaming request is not expected to run past "a 10-minute timeout".

Retries add up too. The [OpenAI rate limits guide](https://developers.openai.com/api/docs/guides/rate-limits) says: "A timeout for each attempt isn't necessarily a deadline for the entire operation." So set one deadline for the whole operation, not just a timeout per try.

### Scale the app around the model

The [OpenAI production guide](https://developers.openai.com/api/docs/guides/production-best-practices) lists horizontal scaling, vertical scaling, caching and load balancing. Caching frequently used data can "improve response times without needing to make repeated calls to our API". Our additions:

- **Keep servers stateless.** Store conversation state in a database, so any server can take any request.
- **Size workers from your limits.** Divide the limit by the tokens per request. Our example: a limit of 2 million input tokens a minute and 10,000 uncached input tokens per request allow about 200 requests a minute. Queue the rest, and show a "busy" message when the queue grows too long.

Even within your own limits, Claude can return 529 `overloaded_error` when "the API experiences high traffic across all users". Chapter 6 covers a fallback.

## Worked example

Our example: the shop's "compare two products" button.

### Step 1: measure the steps

```text
A  load both products from the database    0.3 s   (no model)
B  model: summarize product 1               2.5 s   (needs A)
C  model: summarize product 2               2.5 s   (needs A)
D  model: write the comparison, 600 tokens  3.0 s   (needs B and C)
in a row: 0.3 + 2.5 + 2.5 + 3.0 = 8.3 s
```

Cutting the prompt in half would save 1 to 5% of each model call, so well under half a second in total. That is the weak idea.

### Step 2: run B and C in parallel

B and C do not depend on each other. Run them at the same time.

```text
0.3 + max(2.5, 2.5) + 3.0 = 5.8 s
```

### Step 3: cut the output of D

The comparison was 600 tokens of long paragraphs. Ask for "three short sentences per product, then one sentence with the better pick". It comes out at about 300 tokens. By OpenAI's rule of thumb, half the output may cut about half the time of D.

```text
0.3 + 2.5 + about 1.5 = about 4.3 s
```

### Step 4: stream D

Users now see the first words of the comparison a short time after D starts. The total stays about 4.3 s, but the wait feels much shorter.

### Step 5: the hard case, retries and a deadline

The team's client has a 30 s timeout per attempt and 3 attempts. On a bad day one click can take 3 × 30 = 90 s before the user sees an error. Our fix: one deadline of 15 s for the whole button. When it passes, stop retrying and show a clear message with a retry button.

### Step 6: why it is better

- 8.3 s became about 4.3 s, with the first words much sooner.
- No fast mode was needed, so the price per call did not go up.
- The worst case is now 15 s, not 90 s.

## Common mistakes

1. **Trimming the prompt first.** Input cuts rarely save much time. Fix: cut output, or use a smaller model that still passes your evals.
2. **Fast mode for background jobs.** It costs a premium for speed nobody needs. Fix: use batch or Flex for jobs that can wait.
3. **A huge `max_tokens` with no streaming.** Idle connections can drop. Fix: stream long replies, or use the Batch API when nobody is waiting.

## Try it

Not graded. Write your answer down before you read the answer.

A team turns on Claude fast mode for its chat. They see that the time to first token did not change, and they say: "Fast mode is broken." They also plan to switch the model to Claude Opus 4.7 to save money. Find the two problems.

### Answer

1. **Fast mode is working.** The docs say it speeds up the output, and the first token is not where the gain is. Check how fast the full reply arrives instead.
2. **Opus 4.7 does not support fast mode.** The docs say requests to it with `speed: "fast"` return an error. Fast mode works on Claude Opus 5.5, Claude Opus 5 and Claude Opus 4.8.

## Recap

- Measure total time and time to first token. Output length drives latency; input length matters much less.
- The best levers: a faster model, shorter output, parallel or fewer requests, and streaming.
- Fast modes cost a premium and suit user-facing calls. Stream long calls, and set one deadline for the whole operation.

## Goal

After this lesson you can:

- Size a batch job so it fits the vendor's per-batch limits.
- Match results to inputs safely and resend only the requests that failed.
- Choose between a batch, OpenAI Flex and a normal call for work that can wait.

## The problem

A news archive wants a one-line summary for each of its 180,000 old articles. Nobody is waiting for the answers. Next week is fine.

A developer writes a loop that calls the normal API for each article. Three problems show up:

1. The loop competes with the live site for the same rate limit (chapter 1).
2. It pays the full price for work that has no deadline.
3. When it crashes at article 41,000, nobody knows which summaries are done.

A batch API fixes all three, if you use it the right way.

## The idea

A batch is a job you hand in and collect later. You send many requests at once. The vendor runs them when it has room, and you fetch the results when the job ends. Think of a dry cleaner: you drop off a bag today, it is cheaper than express service, and you pick it up tomorrow.

### Half price, a window, its own limits

All three vendors charge half:

- [Claude docs](https://platform.claude.com/docs/en/build-with-claude/batch-processing): "All usage is charged at 50% of the standard API prices."
- [OpenAI docs](https://developers.openai.com/api/docs/guides/batch): "50% cost discount compared to synchronous APIs".
- [Gemini docs](https://ai.google.dev/gemini-api/docs/batch-api): "50% of the standard cost".

You get a time window, not a speed:

- **Claude docs:** "most batches completing within 1 hour". Batches expire if processing does not complete within 24 hours.
- **OpenAI docs:** "Each batch completes within 24 hours (and often more quickly)".
- **Gemini docs:** "The target turnaround time is 24 hours". A job expires after more than 48 hours.

Batches also use separate capacity:

- **OpenAI docs:** "using the Batch API will not consume tokens from your standard per-model rate limits".
- **Claude docs:** batch usage "does not affect rate limits in the Messages API". The Batches API has its own limits, including how many batch requests can wait in the queue.
- **Gemini docs:** batch requests are "subject to their own rate limits".

### Per-batch limits

| Limit     | Claude                                            | OpenAI                                   | Gemini                                    |
| --------- | ------------------------------------------------- | ---------------------------------------- | ----------------------------------------- |
| Per batch | 100,000 requests or 256 MB, whichever comes first | 50,000 requests; input file up to 200 MB | Inline under 20 MB; input file up to 2 GB |
| Expiry    | 24 hours                                          | 24-hour window                           | After 48 hours                            |

The OpenAI docs say "each input file can only include requests to a single model", and you can create up to 2,000 batches per hour.

Some options do not work in a Claude batch. `stream: true` is not supported, because "Batch results come back as a single file, not a stream". Fast mode's `speed` setting and `max_tokens: 0` are not supported either.

### Errors arrive late

Claude validates every request's `params` in the background, and "validation errors are returned when processing of the entire batch has ended". The docs' advice: "Dry run a single request shape with the Messages API to avoid validation errors."

### Match by id, never by position

Every request needs a unique `custom_id`. On Claude it is 1 to 64 characters: letters, digits, hyphens and underscores. The Claude docs say results "can be returned in any order". The OpenAI docs say the output line order "may not match" the input order. So read the `custom_id` on each result. Sorting your input first does not fix the output order.

### Plan for partial failure

The Claude docs say "the failure of one request in a batch does not affect the processing of other requests". Each Claude result has a type:

- `succeeded`: the message is in the result.
- `errored`: "Possible errors include invalid requests and internal server errors." Not billed.
- `canceled`: you canceled before the request was sent. Not billed.
- `expired`: the 24 hours ended first. Not billed.

Nothing retries for you. The Claude docs tell you to "implement appropriate retry logic for failed requests". An invalid request needs a fix first. A server error or an expired request can go again as it is.

The other vendors differ when time runs out:

- **OpenAI:** unfinished requests are cancelled, but "any responses to completed requests are made available via the batch's output file". Those tokens are billed. The rest go to the error file with the code `batch_expired`.
- **Gemini:** an expired job "will not have any results to retrieve". The docs suggest submitting again or "splitting up the requests into smaller batches". `JOB_STATE_CANCELLED` is another state: the user stopped the job.

### Batches and caching

Caching and batch discounts can stack, but hits are not certain. The Claude docs say:

- "cache hits are provided on a best-effort basis".
- Users typically see "cache hit rates ranging from 30% to 98%".
- Put the same `cache_control` blocks in every request, and "consider using the 1-hour cache duration", since a batch may run for more than 5 minutes.

Gemini supports context caching in batch requests too.

### OpenAI Flex: batch prices on a normal call

[Flex processing](https://developers.openai.com/api/docs/guides/flex-processing) trades speed for price on Responses or Chat Completions requests. Tokens are priced "at Batch API rates". It is in beta with limited models. You set `service_tier` to `flex` on a normal request, so there is no file to build. The default SDK timeout is 10 minutes, and the docs' examples raise it to 15.

Flex can run out of room and return `429 Resource Unavailable`. The docs say: "You will not be charged when this occurs." It is not a spend limit. You have two choices: retry with exponential backoff, or send it again on standard processing by setting `service_tier` to `auto` or removing it, at a higher cost.

### What the vendor keeps

The Claude docs say batch data is stored "for up to 29 days after batch creation". You can delete a batch after processing. Chapter 4 covers what this means for data rules.

## Worked example

Our example: the news archive's 180,000 summaries on Claude's Message Batches API.

### Step 1: the weak plan

```text
submit:  two batches of 90,000 requests
check:   none before the run
retry:   if anything failed, run the whole batch again
```

What goes wrong:

- 90,000 is under the request limit, but each batch is too big in MB (step 3).
- A wrong field fails every request, and you only learn it at the end.
- A full rerun pays again for thousands of good results.

### Step 2: test one request first

Send one article to the normal Messages API with exactly the same `params`. If it works, the shape is right.

### Step 3: size the batches (the hard case)

Count is not the only limit. Each request carries the article text, about 5 KB on average.

```text
180,000 requests x 5 KB = about 900 MB in total
two batches of 90,000:   90,000 x 5 KB = 450 MB each  -> over 256 MB
four batches of 45,000:  45,000 x 5 KB = 225 MB each  -> fits
```

Two batches pass the count limit but fail the size limit. Four batches pass both. Leave room for long articles, or group them by size.

### Step 4: read by `custom_id`

Give each request an id from your own data, such as `article-20190412-0031`. When a result arrives, look up the article by that id. Ignore the line number.

### Step 5: retry only the failures

Batch 1 ends. Sort the results that did not succeed by type:

```text
errored, invalid request  -> fix the params, then resend
errored, server error     -> resend as it is
expired                   -> resend as it is
succeeded                 -> keep; never resend
```

Put the resend ids into one new, small batch. The good summaries stay as they are.

### Step 6: why it is better

- Every batch fits both the count and the size limit.
- A bad request shape fails in one second, not after a night.
- Results join the right article, whatever the order.
- Retries cost only the requests that failed, and failed ones were not billed.

## Common mistakes

1. **Treating the batch as one unit.** A few failed requests do not spoil the rest. Fix: collect the failed ids and resend only those.
2. **Expecting live results.** Streaming is off and errors come at the end. Fix: test one request on the normal API before the batch.
3. **Big Gemini jobs.** An expired Gemini job returns nothing. Fix: use smaller batches, so one expiry loses less work.

## Try it

Not graded. Write your answer down before you read the answer.

A team on the OpenAI API has three jobs. Pick a normal call, Flex or the Batch API for each, and say why.

1. A reply in the live help chat.
2. A test run of 2,000 prompts. The team wants results in the afternoon, and slow replies are fine.
3. New embeddings for 3,000,000 documents. They are needed next week.

### Answer

1. **A normal call.** A user is waiting, so slow replies or a 24-hour window do not fit.
2. **Flex.** It costs the same as batch per token, needs no input file, and a slow reply is fine. Raise the client timeout, and plan for `429 Resource Unavailable`.
3. **The Batch API.** Nobody waits, and it does not use the live rate limits. Embedding batches hold at most 50,000 inputs, so plan at least 60 batches (3,000,000 ÷ 50,000). That is well under 2,000 new batches per hour.

## Recap

- Batch work that nobody waits for. All three vendors charge 50%, give a time window, and use capacity apart from live traffic.
- Respect both the count and the size limit. Test one request on the normal API first, because batch validation errors come at the end.
- Match results by `custom_id`, and resend only failed ids. Expiry differs by vendor: OpenAI keeps finished work, Gemini returns nothing.

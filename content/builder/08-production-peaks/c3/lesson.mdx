## Goal

After this lesson you can:

- Write one log line per model call that lets you, and the vendor, find that call later.
- Pick the numbers to chart and alert on, so slow or costly changes show up early.
- Keep customer content out of logs and ids out of metric labels.

## The problem

A company runs an internal help bot for its staff on the OpenAI API. It answers questions about holidays and expenses. On Thursday a manager writes: "Yesterday after lunch the bot was slow, and once it gave up with an error."

The team opens its logs. Each call wrote one line:

```text
2026-10-07 13:42:10 bot call ok
```

There is no request id, no model, no time taken and no token count. The team cannot find the slow call, cannot tell the vendor which call failed, and cannot say if it will happen again.

Observability means you record enough while the system runs to answer such questions afterwards.

## The idea

There are three layers, from small to big. Think of a flight: the log line is one passenger's ticket, the dashboard is the departures board, and the trace is the full journey with every connection.

```text
log line   -> one model call: ids, status, time, tokens
dashboard  -> numbers over time: errors, p95, tokens, cost
trace      -> one multi-step run: every call and tool in order
```

### Ids that the vendor understands

- **Claude:** every response has a `request-id` header. The same value is the `request_id` field in error bodies. The [Claude errors page](https://platform.claude.com/docs/en/api/errors) asks you to include it when you contact support.
- **OpenAI:** responses carry `x-request-id`. The [API reference](https://developers.openai.com/api/reference/overview) says: "OpenAI recommends logging request IDs in production deployments".

### Your own id, for calls that never came back

A timeout or a network error can leave you with no server id. OpenAI lets you send your own id in the `X-Client-Request-Id` header. The OpenAI API reference sets the rules: "only ASCII characters and be no more than 512 characters long; otherwise, the request will fail with a 400 error". Make it unique per request. In cases like timeouts, you can share it with support "to look up whether OpenAI received the request and when". A timeout on your side does not prove the request never arrived.

[Claude Code's telemetry](https://code.claude.com/docs/en/monitoring-usage) uses the same idea. Its `api_error` events carry a `client_request_id`, which stays available "for failures such as timeouts that never produced a server `request_id`".

### Your time versus the vendor's time

OpenAI responses also carry `openai-processing-ms`. The reference gives it one line: "Time taken processing your API request". Log it next to the time your client measured. Our reading: the header covers only the vendor's processing. So when your client time is much bigger, the extra time is outside it: in the network, your server or a queue. When the two are close, look at the model work itself (chapter 5).

### What to chart and alert on

A final status of 200 can hide trouble. Our list of numbers worth a chart:

- **Errors by status code.** More 429 means a limit (chapter 1). More 5xx means the vendor.
- **Attempts per call.** A call that needed three tries made the user wait, and the failed tries used up rate limit.
- **Latency as p50 and p95**, not only the average. p95 is the time that 95 of every 100 calls finish within; only the slowest 5% take longer. A few very slow calls hide in an average.
- **Time to first token.** The [Claude latency guide](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency) defines it as the time "to generate the first token of the response, from when the prompt was sent".
- **Reply length (output tokens) for each feature.** Generating tokens is usually the slowest step (chapter 5), so longer replies mean slower replies and a bigger bill.
- **Cost per day, by feature.**

Alert on change, not only on fixed limits. A prompt edit can double reply length with no error at all. A monthly invoice shows it weeks too late.

### The vendor's own numbers

Your logs show what you sent. The vendor shows what it counted. The [Claude Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) is part of the Admin API. It breaks usage down by model, workspace and service tier, can filter by API key, and uses `1m`, `1h` or `1d` buckets. The cost endpoint has "Daily granularity only (`1d`)", and Priority Tier costs are not in it. From the docs:

- One listed use is "Cost reconciliation".
- Data "typically appears within 5 minutes of API request completion".
- "The API supports polling once per minute for sustained use."
- "Cache results for dashboards that need frequent updates."

### Traces for agents

An agent run is many calls and tools. One log line per call cannot show how they connect.

- **OpenAI Agents SDK.** The [tracing page](https://developers.openai.com/api/docs/guides/agents/integrations-observability) says tracing "is enabled by default in the normal server-side SDK path". Every run can record "model calls, tool calls, handoffs, guardrails, and custom spans", and you can view them in the Traces dashboard. `withTrace` groups several runs into one trace. The docs name two uses: debug one run, and feed good examples into evals.
- **Claude Code.** It exports metrics and events with OpenTelemetry (an open standard for sending metrics, logs and traces), and traces in beta. Each user prompt starts a `claude_code.interaction` span (one timed step inside a trace), and API calls and tool calls are its children. The `prompt.id` attribute links "all events produced while processing a single user prompt".

### Logs hold customer data

A full prompt log is a copy of your users' words. Claude Code shows a careful default:

- `OTEL_LOG_USER_PROMPTS` is "default: disabled", and prompt text shows as `<REDACTED>`.
- `OTEL_LOG_RAW_API_BODIES` is also off. The docs warn: "Bodies include the entire conversation history."

Watch cardinality too. That is the number of different values a label can take. Claude Code keeps `prompt.id` on events and never on metrics, "because they would cause unbounded cardinality". The docs add that lower cardinality means "better performance and lower storage costs". Put ids in log lines and events. Keep metric labels to a few values, such as feature and model.

## Worked example

Our example: the staff help bot, rebuilt step by step.

### Step 1: the weak log line

```text
2026-10-07 13:42:10 bot call ok
```

It cannot tell you which call it was, how slow it was, how many tries it took, or how many tokens it used.

### Step 2: one structured line per call

```text
time=2026-10-07T13:42:10Z feature=expenses model=<model id>
user=hash:5f2a... server_id=req_8c1d... client_id=bot-7f3e21
status=200 attempts=1 total_ms=2900 vendor_ms=2750 first_token_ms=900
in_tokens=2400 out_tokens=180 cached_tokens=2000
```

The user is a hash, not a name or email. The prompt and reply text are not in the line. Here `total_ms` and `vendor_ms` are close, so this call spent its time in processing, not on the way there.

### Step 3: the hard case, a call with no answer

```text
time=2026-10-07T13:47:55Z feature=holidays model=<model id>
user=hash:91bb... server_id=none client_id=bot-7f3e90
status=timeout attempts=1 total_ms=60000
```

No server id came back. But the team sent `bot-7f3e90` as `X-Client-Request-Id`, so OpenAI support can check whether the request arrived. Without it, this call would be lost.

### Step 4: charts and alerts

Our example rules:

```text
chart:  errors by status, attempts per call, p95 total_ms, first_token_ms
chart:  out_tokens per request by feature, cost per day by feature
alert:  attempts per call rises above its normal level
alert:  out_tokens per request changes by more than 30% in a day
check:  daily totals vs the vendor's usage report
```

### Step 5: why it is better

- Each call can be found, by you and by the vendor, even after a timeout.
- Retries and slow calls show up before users complain.
- A quiet prompt change that makes replies longer triggers an alert on day one.
- Customer text stays out, and metric labels stay small.

## Common mistakes

1. **Watching only the final status.** A 200 after three tries still cost time and limit. Fix: log and chart attempts and 429s too.
2. **Logging every full prompt "for debugging".** You store a copy of customer data. Storing a hash of the text instead does not help you debug, because you cannot read the original words back from it. Fix: keep ids, status, timings and token counts in every line. Turn on prompt text only when you debug, for a short time and for a few people.
3. **Ids as metric labels.** Each new id makes a new series, and storage grows without end. Fix: keep ids on events and log lines.

## Try it

Not graded. Write your answer down before you read the answer.

A research agent on the OpenAI Agents SDK answers one question with 4 model calls and 3 tool calls. Users say some answers take 40 seconds. The team has one log line per model call, and nothing else. What can they not see, and what should they add?

### Answer

They cannot see how the calls connect: which tool calls belong to which run, in what order, and which step took the 40 seconds. A slow tool call does not appear at all, because only model calls are logged. Fix: use the SDK's tracing, which is on by default in the normal server-side path. One trace then shows every model call, tool call and handoff of a run. Add a custom span around any slow step you want to time, and group related runs with `withTrace`.

## Recap

- Log one line per call with the server request id, your own client id, status, attempts, time and tokens.
- Chart and alert on attempts, p95, first-token time and output tokens per request, not only on errors.
- Keep prompt text out of logs by default, keep ids off metric labels, and use traces for multi-step runs.

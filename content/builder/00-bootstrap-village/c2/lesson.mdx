## Goal

After this lesson you can:

- Build a request as an ordered list of messages with the right roles.
- Store and resend a conversation, because the API keeps no memory between calls.
- Read the stop signal of a reply before you show it or save it.

## The problem

A team builds a language-tutor chat. In the first message the learner writes: "I am a beginner. Please answer in very simple Spanish." The first reply is simple. The third reply uses long, hard sentences.

The team looks at their code. Each call sends only the newest thing the learner typed. The model never saw the first message on turn 3.

A second bug: some long grammar explanations end in the middle of a sentence, and the app shows them as if they were complete.

This lesson fixes both.

## The idea

You talk to a model by sending a list of **messages**. Each message has a **role** (who said it) and **content** (what was said). The model reads the whole list and writes the next message.

- **user**: what the person, or your app for them, says.
- **assistant**: what the model said. The [OpenAI docs](https://developers.openai.com/api/docs/guides/text) say: "Messages generated by the model have the `assistant` role."
- **Developer instructions** have their own place: a top-level `system` field on Claude, and an `instructions` parameter or a `developer` role message on OpenAI. Chapter 3 covers this.

**The API has no memory.** The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) say: "The Messages API is stateless, which means that you always send the full conversational history to the API." The [OpenAI docs](https://developers.openai.com/api/docs/guides/conversation-state) say "each text generation request is independent and stateless". So your app is the memory. Think of the model as a reader with no notebook: each time, you hand it the whole story so far.

```text
turn 1 request: [user1]
turn 2 request: [user1, assistant1, user2]
turn 3 request: [user1, assistant1, user2, assistant2, user3]
                 \___ your app stores and resends this ___/
```

**Two ways to carry history.**

1. **Resend it yourself.** Keep the list in your database and send all of it each time. This works on every vendor.
2. **Let the vendor link the turns.** On OpenAI, `previous_response_id` lets you "share context across generated responses". You send the id of the last response, not the full list. This saves sending, not paying. The OpenAI docs say the earlier input tokens in the chain "are billed as input tokens in the API".

**History makes each turn bigger.** Because the history is resent, input tokens grow with every turn. The price per token stays the same; the number of tokens grows. A short question late in a long chat still costs more than the same question in turn 1.

**Earlier turns can be written by you.** The Claude docs say earlier turns "don't necessarily need to actually originate from Claude". You can use synthetic `assistant` messages, for example one sample answer that shows the style you want.

**The reply tells you why it stopped.** A Claude reply is also a message. Its `content` is a list of blocks, each with a `type`, and it has a `stop_reason`:

```json
{
  "role": "assistant",
  "content": [{ "type": "text", "text": "Hola. ¿Cómo estás?" }],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 212, "output_tokens": 9 }
}
```

The [Claude stop reasons page](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) lists the values:

- `end_turn`: "Claude finished its response naturally."
- `max_tokens`: "The response reached your `max_tokens` limit." The suggested action: "Raise `max_tokens` or continue the response".
- `tool_use`: "Claude is calling a tool."
- Others include `refusal` and `model_context_window_exceeded`.

On OpenAI, when the output budget runs out, the [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) says "you'll receive a response with a `status` of `incomplete`", with the reason `max_output_tokens`.

## Worked example

### Step 1: the broken request

This is what the tutor app sent on turn 3 (trimmed: `model` left out):

```json
{
  "max_tokens": 80,
  "messages": [{ "role": "user", "content": "Explain the past tense, please." }]
}
```

What goes wrong:

- Turns 1 and 2 are missing, so "beginner, simple Spanish" is gone.
- The app shows the reply without checking `stop_reason`.
- 80 output tokens is too small for a grammar explanation.

### Step 2: store every turn

The app saves each message to a `messages` table: conversation id, position, role and content. Before each call it loads the rows for that conversation, in order.

### Step 3: send the full list

```json
{
  "max_tokens": 600,
  "messages": [
    { "role": "user", "content": "I am a beginner. Please answer in very simple Spanish." },
    { "role": "assistant", "content": "¡Claro! Hablo despacio y fácil." },
    { "role": "user", "content": "What is 'to eat' in Spanish?" },
    { "role": "assistant", "content": "'Comer'. Yo como pan." },
    { "role": "user", "content": "Explain the past tense, please." }
  ]
}
```

Now the model sees the learner's level on every turn.

### Step 4: check why it stopped

```text
if stop_reason == "end_turn":   show and save the reply
if stop_reason == "max_tokens": the reply is cut off:
                                continue it in a new request,
                                or set a higher cap for long answers
```

**The hard case is a reply that looks fine but is cut.** A cut reply can end on a full stop by chance. Only `stop_reason` tells you for sure.

### Why it is better

- **Memory lives in the app.** The database holds the conversation, so every request is complete.
- **Roles are right.** The learner's turns are `user`; the model's turns are `assistant`.
- **No silent cut-offs.** The app reads the stop signal before it shows or saves anything.
- **Cost is visible.** `usage.input_tokens` grows each turn, and the logs show it. Later realms show how to shorten long histories.

## Common mistakes

1. **Saving only the user's side.** The app stores what the user typed but not the model's replies. The model then sees questions with no answers. Fix: store both roles, in order.
2. **Trusting a reply without its stop signal.** Text can be cut by your own output cap. Fix: check `stop_reason` (Claude) or `status` (OpenAI) on every call.
3. **Thinking "linked by id" means "free".** Linking turns by id changes what you send, not what you pay. Fix: budget for the full history as input on every turn.

## Try it

Not graded. Write your answer down before you read the answer.

A recipe chat adds about 150 tokens per turn (user plus assistant). Its log shows:

```text
turn 12  input_tokens: 1,800  stop_reason: end_turn
turn 13  input_tokens: 150    stop_reason: end_turn
turn 14  input_tokens: 300    stop_reason: max_tokens
```

1. What changed between turn 12 and turn 13?
2. What should the app do with the turn 14 reply?

### Answer

1. **The history was dropped.** Turn 13 sent only about one turn of tokens, so the model lost turns 1–12. It looks cheaper, but the model has lost the context. Fix: load and resend the stored history.
2. **Treat it as cut off.** `max_tokens` means the reply hit your limit. Do not show it as complete; continue it in a new request or raise the cap.

## Recap

- A request is an ordered list of messages with roles: `user` and `assistant`, plus developer instructions in their own slot.
- The APIs are stateless. Your app stores the history and resends it; input tokens grow each turn, even when linked by id.
- Read the stop signal before you trust a reply: `end_turn` is a natural stop, `max_tokens` is a cut.

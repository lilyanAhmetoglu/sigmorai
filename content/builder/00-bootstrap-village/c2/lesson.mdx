You talk to a model by sending a list of **messages**. Each message has a **role** (who said it) and **content** (what was said). The model reads the list and writes the next message. This is the basic unit of every chat app, agent and pipeline you will design.

## Roles

Both Anthropic and OpenAI use roles to mark who is speaking:

- **user**: what the person (or your app, on their behalf) says.
- **assistant**: what the model said. OpenAI's docs: "Messages generated by the model have the `assistant` role."

There is also a place for the developer's own instructions. Anthropic uses a top-level `system` field; OpenAI uses an `instructions` parameter or a `developer` role message. Chapter 3 covers this.

A small conversation looks like this (Claude shape):

```json
"messages": [
  { "role": "user", "content": "Hello, Claude" },
  { "role": "assistant", "content": "Hello!" },
  { "role": "user", "content": "Can you describe LLMs to me?" }
]
```

The same conversation in OpenAI's shape is an `input` array:

```json
"input": [
  { "role": "user", "content": "Hello" },
  { "role": "assistant", "content": "Hello!" },
  { "role": "user", "content": "Can you describe LLMs to me?" }
]
```

The field names differ by vendor. The model is the same: an ordered list of turns.

## The API does not remember you

This is the most important design fact in this chapter.

- Anthropic: "The Messages API is stateless, which means that you always send the full conversational history to the API."
- OpenAI: "each text generation request is independent and stateless".

So the model has no memory between calls. If the user said their name in turn 1, and you send only turn 5, the model does not know the name. **Your system** stores the conversation and sends it again on every call.

Example: a support bot that saves each turn to a database row, then loads the last turns into `messages` before each call. Memory lives in your database, not in the model.

## Two ways to carry history

1. **Resend it yourself.** Keep the list in your app and send all of it each time. This works on both vendors.
2. **Let the vendor link turns.** OpenAI also offers `previous_response_id` to "share context across generated responses". You send the id of the last response instead of the full list.

Option 2 changes how much you send over the wire. It does not change what you pay. OpenAI's docs: "Even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API."

Example: a 30-turn chat. With option 1, request 31 resends all 30 turns. With option 2, request 31 sends one id plus the new message, but the bill still counts all 30 earlier turns as input.

## History makes every turn bigger

Because history is resent, input grows each turn.

Example: each turn adds about 200 tokens (user plus assistant).

- Turn 1 sends about 200 input tokens.
- Turn 10 sends about 2,000 input tokens.
- Turn 50 sends about 10,000 input tokens.

A long conversation costs more per turn than a short one, even when the user asks a short question. Plan for it: cap history length, summarise old turns, or start a new thread. Later realms cover these patterns in depth.

## You can write the assistant's past turns

Earlier turns do not have to come from the model. Anthropic's docs: "Earlier conversational turns don't necessarily need to actually originate from Claude. You can use synthetic `assistant` messages."

Example: you seed a conversation with one example exchange (a user question and a short, well-formatted assistant answer) so the model sees the style you want.

## What comes back

A response is also a message, plus metadata. A Claude response looks like this (trimmed):

```json
{
  "role": "assistant",
  "content": [{ "type": "text", "text": "Hello!" }],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 12, "output_tokens": 6 }
}
```

Note that `content` is a list of **blocks**, each with a `type`, not one plain string. Store and read it as a list. Chapter 4 shows image blocks inside a user message.

## Why did it stop?

Always check why generation ended before you trust the output.

- **Claude** sets `stop_reason`. `end_turn` means the model finished naturally. `max_tokens` means "the response reached your `max_tokens` limit". Other values include `tool_use`, `refusal` and `model_context_window_exceeded`.
- **OpenAI** reasoning docs: when the output budget runs out, "you'll receive a response with a `status` of `incomplete`" with `incomplete_details.reason` set to `max_output_tokens`.

Example: a summary job saves every reply to a report. One day the reports end mid-sentence. The cause is a low output cap. The fix is to read the stop signal on every call, and to raise the cap or continue the reply when it says the limit was hit. The Claude docs list both options: raise `max_tokens`, or continue the response in another request.

## Key points

- A request is an ordered list of messages with roles: user and assistant (plus developer instructions, chapter 3).
- The APIs are stateless. Your system stores and resends history.
- Linking turns by id (OpenAI `previous_response_id`) still bills all previous input tokens.
- Input grows each turn. Design for long conversations.
- Read `stop_reason` (Claude) or `status` (OpenAI) before you trust a reply.

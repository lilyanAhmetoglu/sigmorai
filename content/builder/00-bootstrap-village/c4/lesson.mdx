## Goal

After this lesson you can:

- Send an image or a PDF as a content block, and estimate its token cost.
- Cut image cost with resizing and file IDs.
- Say where vision is not exact, and plan a speech-to-text step when a model takes no audio.

## The problem

A factory builds a helper for repair technicians. A technician takes a photo of a machine's nameplate, attaches the machine's PDF manual, and asks: "Which spare part do I need?" Some technicians also want to send a voice memo instead of typing.

After one week the team sees:

1. Each chat costs much more than the plan. Photos are sent at full phone size, and the chat goes on for many turns.
2. On a few blurry photos, the model read a serial number wrong.
3. Product asks: "Can we just send the voice memo to the model?"

This lesson gives the team a plan for images, PDFs and audio.

## The idea

**Multimodal input** means the model takes more than text. An image or a PDF goes in as one more **content block** in a user message, next to a text block (chapter 2):

```json
{
  "role": "user",
  "content": [
    { "type": "image", "source": { "type": "url", "url": "https://example.com/nameplate.jpg" } },
    { "type": "text", "text": "What is the model number on this plate?" }
  ]
}
```

**Three ways to send an image.** The [Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision) list base64 data in the request, a URL, or a `file_id` from the Files API. The [OpenAI vision docs](https://developers.openai.com/api/docs/guides/images-vision) list a URL, "a Base64-encoded data URL", or "a file ID". On order, the Claude docs say "Claude works best when images come before text".

**Images cost input tokens.** Claude cuts an image into small squares called patches. The docs say: "Each patch is a 28×28-pixel block of the image", and an image "costs `⌈width / 28⌉ × ⌈height / 28⌉` visual tokens". Images above a model's size limit "are downscaled before processing", which caps the cost. The docs give a 1000×1000 image as 1296 tokens. Their advice: "downsample images before sending to control token costs". Newer OpenAI models also cut images into patches (some older ones use tiles), and a `detail` setting controls how much detail it keeps. The OpenAI docs add: "Image tokens also count toward your tokens per minute (TPM) limits."

**Images in long chats.** The API is stateless, so each turn resends the history, images too. The Claude docs warn that with base64, "the full image bytes are included in the payload on every turn". Uploading once and sending the `file_id` "keeps request payloads small". OpenAI accepts file IDs too.

```text
base64:  turn 1 [photo bytes] turn 2 [photo bytes] turn 3 [photo bytes] ...
file id: upload once -> turn 1 [id] turn 2 [id] turn 3 [id] ...
```

**Vision is not exact.** Both vendors list limits, and they overlap:

- **Counting.** The Claude docs: Claude "can give approximate counts". The OpenAI docs: the model "may give approximate counts for objects in images".
- **Position.** Claude's location outputs "are approximate". The OpenAI docs say the model "struggles with tasks requiring precise spatial localization".
- **Poor images.** Claude "might hallucinate or make mistakes" on low-quality, rotated or very small images. For small text, the OpenAI docs say: "Enlarge text within the image to improve readability."

The Claude docs say: "Do not use Claude for tasks requiring perfect precision or sensitive image analysis without human oversight."

**PDFs are text plus page images.** In the [Claude PDF docs](https://platform.claude.com/docs/en/build-with-claude/pdf-support), "The system converts each page of the document into an image", and the text of each page "is extracted and provided alongside each page's image". The [OpenAI file inputs docs](https://developers.openai.com/api/docs/guides/file-inputs) say that on vision models "the API extracts both text and page images and sends both to the model". So each page costs text tokens and image tokens. The Claude docs say each page "typically uses 1,500–3,000 tokens per page" of text, before the image cost. Both vendors also set size limits per request; check them before you design bulk uploads.

**Audio differs by vendor.** The [OpenAI audio docs](https://developers.openai.com/api/docs/guides/audio) list file transcription ("A transcript of an audio file"), audio input in Chat Completions, and the Realtime API for speech-to-speech agents. The Claude docs document image input (vision) and PDF support; none of the cited Claude pages (vision, PDF support, the [features overview](https://platform.claude.com/docs/en/build-with-claude/overview) and the [models overview](https://platform.claude.com/docs/en/models/overview)) mentions audio input. So if your chosen model takes no audio, add a **speech-to-text** step: turn the audio into text first, then send the text.

## Worked example

### Step 1: the first design

```text
photo:   2000×1500, base64, kept in the chat
manual:  PDF, 80 pages, sent with every question
voice:   "send the audio file to the model"
answer:  shown to the technician as final
```

What goes wrong:

- The photo is large and its bytes go again on every turn.
- 80 pages of text and page images go with every question.
- The plan assumes every model takes audio.
- A misread serial number goes straight to the technician.

### Step 2: estimate the photo, then resize

On a Claude high-resolution model, the docs' table gives a 2000×1500 photo as 3888 tokens (not resized). A nameplate does not need that much detail. The app resizes it to 1120×840 first:

```text
⌈1120 / 28⌉ × ⌈840 / 28⌉ = 40 × 30 = 1,200 tokens
```

That is less than a third of the tokens. Test that the serial number is still easy to read at this size.

### Step 3: upload once, then send the file ID

The app uploads the resized photo once and keeps the `file_id`. Turn 1 and every later turn carry the short ID, not the image bytes.

### Step 4: send only the pages you need

At 1,500–3,000 text tokens per page, 80 pages is about 120,000–240,000 text tokens, plus 80 page images. The app sends only the parts list pages (say 4 pages) for this machine.

### Step 5: plan the voice memo

The team checks each vendor's docs. If the chosen model takes audio, they can test it. If it does not, the pipeline is:

```text
voice memo -> speech-to-text service -> transcript (text) -> model
```

### Step 6: the hard case

**The hard case is a blurry nameplate.** A wrong serial number orders the wrong part. The app shows the number it read next to the photo, and the technician confirms it before the order goes out.

### Why it is better

- **Cheaper images.** Resizing cut the photo's tokens by more than two thirds on a high-resolution model, and file IDs keep later turns small.
- **Smaller PDFs.** Only the needed pages are sent.
- **Works on any vendor.** A transcription step covers models without audio input.
- **A person checks the risky part.** Exact numbers from photos are confirmed before an action.

## Common mistakes

1. **Sending full-size photos by default.** Pixels cost tokens. Fix: shrink each image to the size the job needs, then test on real images.
2. **Base64 images in a long chat.** Each turn sends the full image again. Fix: upload once and reference the file ID.
3. **Trusting an exact reading from an image.** Counts, positions and tiny text are approximate. Fix: keep a person in the loop for exact or high-stakes values.

## Try it

Not graded. Write your answer down before you read the answer.

A recipe app lets users photograph a page of a cookbook. The photo is 1400×700 pixels. Assume it is not downscaled.

1. Use the Claude formula. How many tokens is the image?
2. The user then chats for 15 turns about the recipe. How should the app send the image so it is not resent as bytes each turn?
3. The app wants to read the exact grams of each ingredient from the photo and order them automatically. What is the risk?

### Answer

1. ⌈1400 / 28⌉ × ⌈700 / 28⌉ = 50 × 25 = **1,250 tokens**.
2. Upload it once with a Files API and send the **file ID** on later turns.
3. Small text in photos can be **misread**. Show the values to the user to confirm before any order.

## Recap

- Images and PDFs go in as content blocks in a user message. They cost input tokens: images by patches, PDF pages as text plus a page image.
- Resize images to the detail you need, and use file IDs when an image stays in a long chat.
- Vision is approximate for counts, positions and tiny details; keep a person on high-stakes values. Audio input differs by vendor; add speech-to-text when the model takes no audio.

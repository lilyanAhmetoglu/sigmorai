## Goal

After this lesson you can:

- Turn a word count into a rough token count, and say when that rough rule is not safe.
- List every part of a request that counts as input tokens, not only the user's text.
- Measure tokens before a call with a counting tool, and after a call with the `usage` data.

## The problem

A team builds a code-review helper. Each request sends a system prompt, one tool called `search_docs`, and the diff that the developer wants reviewed. Before launch, the team lead asks: "How big is one request, and what will it cost?"

A developer counts the words in a typical diff: 1,200 words. The developer says: "So 1,200 per request." That number is wrong in two ways:

1. Models do not count words. They count **tokens**.
2. The diff is not the only thing in the request.

This lesson shows how to get a number you can plan with.

## The idea

A token is a small piece of text. The [OpenAI docs](https://developers.openai.com/api/docs/concepts) say tokens "represent commonly occurring sequences of characters". A common word like "the" can be one token. A longer word can be two or more.

Think of tokens as the coins the API counts. Price, context size and rate limits are all counted in these coins, not in words:

- **Cost.** Both vendors price input and output per million tokens. The [OpenAI pricing page](https://developers.openai.com/api/docs/pricing) says: "Prices per 1M tokens." Input and output have separate prices.
- **Context.** A model can only read a fixed number of tokens in one request (chapter 5).
- **Rate limits.** Limits count tokens per minute, not words per minute (chapter 5).

**The rough rule for English.** Both vendors give the same rule of thumb. The [Claude pricing page](https://platform.claude.com/docs/en/about-claude/pricing) says: "1 token is approximately 4 characters or 0.75 words in English. The exact count varies by language and content type." The OpenAI docs give the same 4 characters or 0.75 words "for English text". So the rule is for a first sketch in English only. For other languages and for code, measure.

**Everything in the request is input.** The system prompt, the conversation history, tool definitions, images and PDF pages all count as input tokens. Tools add more than their own text. The Claude pricing page says that when you use `tools`, "the API also automatically includes a special system prompt for the model that enables tool use." The model's reply is **output**, counted and priced on its own.

**A token count belongs to one model.** Each model family has a **tokenizer**: the part that cuts text into tokens. Two tokenizers can cut the same text differently. The [Claude token counting docs](https://platform.claude.com/docs/en/build-with-claude/token-counting) give a real case: on newer models, "the same input text produces approximately 30 percent more tokens than on earlier models." They also say: "Recount prompts against the model you plan to use rather than reusing counts measured against earlier models."

**Count before the call, then trust `usage` after it.**

```text
plan:    words / 0.75        -> rough sketch (English only)
before:  counting tool       -> estimate for one model
after:   usage in response   -> what you really used
```

- **Before.** The Claude token counting endpoint "accepts the same structured list of inputs for creating a message", including system prompts, tools, images and PDFs. It is "free to use" but has its own requests-per-minute limit. The docs say the result is an **estimate**: the real number "might differ by a small amount". The OpenAI docs point to a tokenizer tool to "test specific strings and see how they are translated into tokens".
- **After.** Every response reports what it used. A Claude response has a `usage` block with `input_tokens` and `output_tokens`. An OpenAI response has a `usage` object too; the [OpenAI caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) reads `usage.input_tokens_details.cached_tokens` from it. Log these numbers on every call. They are the real numbers for cost dashboards.

## Worked example

### Step 1: the first guess

```text
diff: 1,200 words  ->  "1,200 tokens per request"
```

What goes wrong:

- It treats words as tokens.
- It forgets the system prompt and the tool.
- It does not say which model the number is for.

### Step 2: convert words to tokens, for every part

The team writes down every part of the request. The diff is code, and the system prompt is English.

```text
part                 words    rough tokens (words / 0.75)
system prompt          450      600
tool: search_docs      120      160   (+ the tool-use system prompt)
diff (code)          1,200    1,600   <- code: rule may be wrong
---------------------------------------------------------------
rough input                    2,360+ tokens
output (the review)            not input; counted on its own
```

This is better, but two lines are still guesses. **The hard case is the diff.** It is code, not English prose. The 0.75 rule is for English text, so the real count can be quite different.

### Step 3: measure on the launch model

The team sends one real request (system prompt, tool and a real diff) to the token counting endpoint, with the model they will launch on. The shape of the request is the same as a normal call:

```json
{
  "model": "<the launch model id>",
  "system": "You review code diffs for our team...",
  "tools": [{ "name": "search_docs", "description": "...", "input_schema": { "type": "object" } }],
  "messages": [{ "role": "user", "content": "<the real diff>" }]
}
```

The answer is one number: `{ "input_tokens": ... }`. They repeat this for 20 real diffs, short and long, and use the average.

### Step 4: check with `usage` after launch

In week 1, the app logs `usage.input_tokens` and `usage.output_tokens` for every call. The team compares the logs with the plan and updates the budget.

### Why it is better

- **Every part counts.** The system prompt and the tool are in the number, not only the diff.
- **One model.** The count is for the launch model's tokenizer.
- **Measured, not guessed.** The code diff, the hard case, is measured instead of converted with an English rule.
- **Checked after launch.** `usage` shows the real numbers, so the plan does not drift.

## Common mistakes

1. **Counting only the user's text.** The system prompt, the history, tool definitions and images are input too. Fix: list every part of the request, then count all of them.
2. **Using the English rule for everything.** Code, numbers and other languages can split very differently. Fix: use words ÷ 0.75 only for an English sketch; measure a real sample for the rest.
3. **Keeping old counts after a model change.** A new tokenizer can change the count for the same text. Fix: recount with the new model id before you update the budget.

## Try it

Not graded. Write your answer down before you read the answer.

A team plans a meeting-notes app. Each request has:

- a system prompt of 300 English words,
- a meeting transcript of 2,400 English words,
- no tools.

1. Use the rough rule. About how many input tokens is one request?
2. Next month, half of the meetings will be in German. Can the team use the same rule for those?
3. The app goes live. Which number should the monthly cost report use?

### Answer

1. (300 + 2,400) ÷ 0.75 = **about 3,600 input tokens**. This is only a sketch for English text.
2. **No.** The docs give the rule for English, and the count "varies by language". Fix: measure a few real German transcripts with a counting tool for the model you use.
3. **The `usage` numbers** from each response. The counting tool gives a planning number before the call; `usage` reports what each call really used.

## Recap

- A token is a small piece of text. For English, about 4 characters or 0.75 words. Other languages, code and other content can differ.
- Every part of a request is input: system prompt, history, tools, images. The reply is output, priced on its own.
- A count belongs to one model's tokenizer. Recount when you change models. Estimate before the call, then trust `usage` after it.

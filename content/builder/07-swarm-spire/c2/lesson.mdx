## Goal

After this lesson you can:

- Choose between a handoff and an agent-as-tool by asking who owns the reply.
- Control which past messages a specialist can read, and know where that control stops.
- Send small metadata with a handoff and check permissions in the right place.

## The problem

A software company built its help chat with the OpenAI Agents SDK. The first agent a user meets is a triage agent. It has a tool, `lookup_account`, that returns the user's plan, seat count and billing address. It can hand off to two specialists: a tech agent and a plan agent.

Last week, four things went wrong:

1. A user asked about an app crash. The tech agent replied: "I can see your billing address is in Porto..." The tech agent never needed that.
2. The support lead wants a log line for each tech handoff: the user's language and how urgent the problem is.
3. A user asked to add 80 seats. The plan agent took over and made the change. Big changes like that should go to a sales person.
4. After the tech agent answered, the user wrote "it still crashes". The message went back to triage, which routed it all over again.

The same team also uses Claude Code subagents for internal work. One subagent was asked to "fix the failing test" and spent 20 minutes finding which test failed. The main agent already knew.

Each problem sits on one edge of the graph: the moment work moves from one agent to another.

## The idea

Every move between agents answers two questions:

- **Who owns the answer after the move?**
- **What does the next agent see?**

**Ownership.** The [OpenAI orchestration guide](https://developers.openai.com/api/docs/guides/agents/orchestration) says the first choice is "who owns the final user-facing answer". It offers two patterns:

- **Handoff.** "Control moves to the specialist agent". The specialist talks to the user.
- **Agents as tools.** The manager stays the owner of the reply. It calls the specialist like a function, reads the result and writes the answer.

The guide says agents as tools is usually the better fit when the manager should combine the final answer, or when the specialist does a bounded job "like summarization or classification". The [SDK docs](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md) add that you can mix them: a specialist that got a handoff can still call other agents as tools.

Think of a hospital. A handoff is a transfer to another doctor, who now talks to the patient. An agent-as-tool is a lab test: the same doctor orders it, reads it and explains it.

**A handoff is a tool.** The [handoffs docs](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md) say: "Handoffs are represented as tools to the LLM." By default the tool name is `transfer_to_<agent_name>`, so a "Tech agent" becomes `transfer_to_tech_agent`. You can change it with `tool_name_override`, but you set that name once, in code. If you pass a plain `Agent`, its `handoff_description` is added to the tool description. The guide's advice: give each specialist a narrow job, and keep that description "short and concrete". With several specialists, the docs say to "register one handoff per destination and let the model choose".

**What the next agent sees: two defaults.**

- **OpenAI handoffs pass the history.** The docs: the new agent "gets to see the entire previous conversation history." To change that, set an `input_filter`. A ready-made filter, `handoff_filters.remove_all_tools`, strips the tool call and tool result items. But tool data that was already written into a normal message stays. The docs say the filter "does not redact" that text. The docs also say to "Treat the receiving agent and its model provider as recipients of the forwarded history."
- **Claude subagents start fresh.** The [Claude Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/subagents) say a subagent's window "starts fresh". It has none of the parent's conversation. The only thing passed down is the prompt that the Agent tool sends. The exception is a fork, which inherits the parent conversation.

The two defaults fail in opposite ways. Full history can leak data. A fresh start can miss the one fact the worker needed. With a fresh start, the brief is everything. The [Anthropic research-system post](https://www.anthropic.com/engineering/multi-agent-research-system) lists what a good brief has: "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."

**Limits of the filter.** Two more rules from the handoffs docs:

- **Nested history is not redaction.** `nest_handoff_history` is an opt-in beta that is off by default. It summarizes earlier turns into a block. The docs say it only changes how the transcript looks. It "does not redact" anything sensitive.
- **Server-managed history ignores filters.** If the run uses `conversation_id`, `previous_response_id` or `auto_previous_response_id`, handoff input filters are not supported. To keep history away from a specialist, start a separate run and pass in only the input you chose ("explicitly selected input"). In that new run, leave out the old conversation id and the old response id.

**Data on the handoff.** `input_type` sets a schema for the handoff tool's arguments. The model fills it in, the SDK checks it, and your `on_handoff` callback receives it. The docs call it metadata that "the model decides" during the handoff, like a reason or a priority. Two limits:

- It does not change the specialist's main input, and it does not hide the history. App state you already have belongs in the run context instead.
- It does not authorize anything. `is_enabled` turns a handoff on or off. It runs while the SDK prepares the handoffs, before the model fills in any arguments. Those values do not exist yet. If permission depends on the arguments, check them first thing in `on_handoff`, before any side effects, and raise to stop. The docs add that tool input guardrails are for function tools. They do not run on handoffs.

**Checks stay behind.** A handoff moves control, but agent guardrails do not move with it. The [guardrails docs](https://github.com/openai/openai-agents-python/blob/main/docs/guardrails.md) say input guardrails "run only for the first agent in the chain", and output guardrails only for the agent that writes the final output. For checks around each function-tool call, use tool guardrails.

**Claude Code puts a boundary on the way back.** The [subagents docs](https://code.claude.com/docs/en/sub-agents) say a subagent's report arrives under a header. It says that instructions or approval claims inside are the subagent's words and "carry no authority from you."

**The next turn.** The [results guide](https://developers.openai.com/api/docs/guides/agents/results) says to reuse `last_agent` in Python "after handoffs" when the same specialist should answer next time.

## Worked example

### Step 1: the weak setup

```python
triage = Agent(
    name="Triage agent",
    tools=[lookup_account],
    handoffs=[tech_agent, plan_agent],
)
result = await Runner.run(triage, user_message)
```

Why it fails:

- No `input_filter`, so the tech agent sees the `lookup_account` result with the billing address.
- Nothing records why or how urgently the tech handoff happened.
- Nothing stops an 80-seat change.
- Every new user message starts at `triage` again.

### Step 2: filter, metadata and a log

```python
from pydantic import BaseModel
from agents import Agent, RunContextWrapper, Runner, handoff
from agents.extensions import handoff_filters

class TechReason(BaseModel):
    language: str
    urgency: str  # "low" or "high"

async def log_tech(ctx: RunContextWrapper[AppContext], data: TechReason):
    print(f"tech handoff: language={data.language} urgency={data.urgency}")

tech_handoff = handoff(
    tech_agent,
    input_type=TechReason,
    on_handoff=log_tech,
    input_filter=handoff_filters.remove_all_tools,
)
```

The names are real SDK names. `AppContext` is our own class, and the log line is simplified.

Now the tech agent no longer gets the tool items. But check the rest. If triage wrote "I see you are in Porto" in a normal message, the address is still there. A custom `input_filter` can remove or redact that text too.

### Step 3: the hard case, a check that needs the arguments

The plan agent changes seats. Changes over 50 seats must go to sales. The model chooses the seat number during the handoff, so `is_enabled` cannot see it. Check it inside `on_handoff`, before anything else:

```python
class SeatChange(BaseModel):
    seats: int

async def check_seats(ctx: RunContextWrapper[AppContext], data: SeatChange):
    if data.seats > 50:
        raise SeatLimitError("Send to sales")  # our own exception class
    # only now: start any side effects

plan_handoff = handoff(plan_agent, input_type=SeatChange, on_handoff=check_seats)
```

If `check_seats` returns normally, the SDK goes on with the transfer. If it raises, the transfer stops. Your app catches the error and sends the user to sales.

### Step 4: keep the specialist for the next turn

```python
result = await Runner.run(current_agent, history + [new_message])
current_agent = result.last_agent
```

"It still crashes" now goes straight to the tech agent.

### Step 5: the internal Claude subagent

The weak brief was "fix the failing test". A better brief carries what the main agent knows:

```text
Objective: make test_export_csv pass.
Known: it fails with "KeyError: 'currency'" since commit 4f2a1c.
Scope: only src/export/. Do not change the test.
Output: the diff, plus 2 lines on the cause.
```

### Step 6: why it is better

- The tech agent gets the conversation without the tool output, and the team checks the messages too.
- The log shows language and urgency for every tech handoff.
- Big seat changes stop at a check in code, not at a model's choice.
- Follow-up messages stay with the right specialist.
- The subagent starts with the facts it cannot see on its own.

## Common mistakes

1. **Trusting the default history.** A specialist sees everything earlier in the chat. Fix: set an `input_filter`, then read what is left in plain messages.
2. **Checking permission in the wrong place.** `is_enabled` runs too early to see the model's arguments. Fix: check them first in `on_handoff`, and raise if the check fails.
3. **Assuming guardrails follow the handoff.** An input guardrail on a middle agent never runs. Fix: put input checks on the first agent and use tool guardrails for checks around each function tool.

## Try it

Not graded. Write your answer down before you read the answer.

For each case, choose "handoff" or "agent as tool", and give one reason.

```text
A) A travel chat needs a short weather summary for the user's city.
   The main agent will mention it in its own reply.
B) A user wants to dispute a charge. A disputes specialist must
   ask questions and guide them through several turns.
C) A writing assistant asks three specialists for feedback on a
   draft and merges their notes into one answer.
```

### Answer

- **A: agent as tool.** It is a bounded job, and the main agent keeps the reply.
- **B: handoff.** The specialist should take over the conversation for this branch. Keep it in control next turn with `last_agent`.
- **C: agent as tool.** The manager must combine the answers, so it should keep ownership of the reply.

## Recap

- Decide ownership first. A handoff gives the specialist the reply. An agent-as-tool keeps it with the manager.
- OpenAI handoffs pass the full history unless you filter it, and filters do not work with server-managed history. Claude subagents get only the prompt string, so write a full brief.
- `input_type` carries model-chosen metadata. Authorize inside `on_handoff`. Input guardrails run only on the first agent, and output guardrails only on the last.

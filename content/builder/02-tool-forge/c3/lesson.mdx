## Goal

After this lesson you can:

- Send a tool result back in the right format, matched to its call.
- Shrink a large result to the fields the model needs, with paging or filters.
- Turn a failure into an error result that the model can act on.

## The problem

The library assistant can now search the catalogue with `search_catalog`. The first tests go badly:

1. A reader asks for "books about bees for children". The tool returns 1,400 records, each with 60 catalogue fields. The answer is slow, and the model misses the one book on the shelf nearby.
2. One morning the catalogue server is down. The tool code throws an exception, and the whole chat stops.
3. A reader cancels a hold. The `cancel_hold` tool sends back an empty result, and the model says: "I think the hold is cancelled."

The model continues from whatever you return. So a tool result is also a prompt, and it needs the same care.

## The idea

**Match each result to its call.** Every call has an id, and the result carries the same id.

- Claude: the call is a `tool_use` block with an `id`. The result is a `tool_result` block. Its `tool_use_id` field holds that id, and it goes in the next `user` message ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)).
- OpenAI: the call is a `function_call` item with a `call_id`. The result is a `function_call_output` item with the same `call_id` ([OpenAI docs](https://developers.openai.com/api/docs/guides/function-calling)).

The Claude docs add two format rules. Tool results "must immediately follow their corresponding tool use blocks in the message history". And in that user message, the results "must come FIRST in the content array"; any text goes after them.

**What a result holds.** OpenAI: the output "should typically be a string, where the format is up to you (JSON, error codes, plain text, etc.)". Functions that return images or files can send an array of image or file objects instead. On Claude, `content` is a string or a list of blocks: text, image, document or search result. If the tool has nothing to return, OpenAI says to "return a string that indicates success or failure". Never leave the model to guess whether an action happened.

**Return only what matters.** The [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) say: "Design tool responses to return only high-signal information." Include "only the fields Claude needs to reason about its next step", because "Bloated responses waste context". Anthropic's [engineering post on tools](https://www.anthropic.com/engineering/writing-tools-for-agents) suggests "pagination, range selection, filtering, and/or truncation with sensible default parameter values" for any tool that can return a lot. It notes that Claude Code limits tool responses "to 25,000 tokens by default". In its example, a "concise" format used about a third of the tokens of a "detailed" one.

Think of a librarian at the desk. You ask for a bee book, and she hands you three good titles, not the whole card index.

**Errors are results too.** A tool can fail: a timeout, a rate limit, a record that does not exist. Do not crash the loop, and do not hide the failure. On Claude, send the error text as the result with `is_error: true`. The [Claude tutorial](https://platform.claude.com/docs/en/agents-and-tools/tool-use/build-a-tool-using-agent) explains why: "Claude reads the error and can retry with corrected input, ask the user for clarification, or explain the limitation." On OpenAI, the output is one string, and error codes are one format the docs list, so the error goes in that string. The [Gemini docs](https://ai.google.dev/gemini-api/docs/function-calling) list "Implement robust error handling" as a best practice.

**Write the error for the model.** The Claude docs: instead of a generic `"failed"`, "include what went wrong and what Claude should try next". Their example tells the model to retry after 60 seconds. The engineering post says errors should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks."

**Check the call before you run it.** Sometimes the call itself is bad: a required value is missing, or it has the wrong type. The Gemini docs say: "Validate function calls before executing." If the check fails, do not run the tool. Send back an error result that names the problem. The Claude docs show one: `Error: Missing required 'location' parameter`. They also say that for invalid or incomplete calls, "Claude will retry 2-3 times with corrections before apologizing to the user". Better descriptions and strict mode (chapter 2) prevent many of these calls.

## Worked example

### Step 1: the raw result

```text
call:    search_catalog(query="bees", audience="children")
result:  1,400 records x 60 fields
         marc_008=..., bib_uuid=7f2c..., item_barcode=..., created=...
```

The model has to read every field of every record to find three useful facts: the title, where the book is, and whether it is on the shelf.

### Step 2: the trimmed result

Give the tool a `branch` filter and a `page` parameter, with a default of 5 results. Return a few fields with meaningful ids:

```json
{
  "results": [
    {
      "record_id": "b2291047",
      "title": "The Bee Book",
      "branch": "riverside",
      "on_shelf": true
    },
    {
      "record_id": "b1873320",
      "title": "Busy Bees",
      "branch": "riverside",
      "on_shelf": false
    }
  ],
  "note": "Showing 5 of 214 matches at riverside. Pass page=2 for more, or a narrower query."
}
```

The `note` steers the model: it knows there is more, and how to get it.

### Step 3: the hard case, a failure

**The hard case is the catalogue server being down.** Before, the exception stopped the chat. Now the tool code catches it and returns an error result:

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01Ab",
  "is_error": true,
  "content": "The catalogue server did not answer within 10 seconds. Shelf status is unknown right now. Tell the reader, and offer to try again in a few minutes."
}
```

The model now tells the truth: it does not know. It does not invent "no copies" from an empty result.

### Step 4: an action with nothing to return

```text
Before:  cancel_hold(...)  ->  ""
After:   cancel_hold(...)  ->  "Hold H-5120 cancelled. The reader is no longer in the queue."
         or                ->  "Not cancelled: hold H-5120 belongs to another reader."
```

### Step 5: why it is better

- **Faster and more accurate.** Four fields per book instead of sixty, and five books instead of 1,400.
- **The chat survives failures.** An error is a result, so the model can explain it or try again.
- **Errors say what to do.** The model knows the cause and the next step.
- **No guessing about actions.** Every action reports success or the reason it failed.

## Common mistakes

1. **Raw internal fields in results.** Database column names and internal ids cost tokens and confuse the model. Fix: return the few fields the next step needs, with meaningful ids.
2. **A results message that breaks the format.** Text placed before the tool results, or a result that arrives later in the history, makes the Claude API return an error. Fix: put the results first, in the message right after the call.
3. **Running a call that is missing a value.** Your code guesses a default and does something the user never asked for. Fix: check the call first; if a value is missing, return an error that names the field and its format.

## Try it

Not graded. Write your answer down before you read the answer.

A recipe app has a `convert_units` tool. Rewrite each result so the model can act on it.

```text
A. convert_units(amount=2, from="cups", to="grams")   -> "E_UNIT"
B. convert_units(amount=-5, from="g", to="oz")        -> Traceback (most recent call last): File "conv.py"...
C. save_recipe(title="Pancakes")                      -> (nothing)
```

### Answer

- **A.** `is_error: true`, with "Cups to grams needs the ingredient, because a cup of flour and a cup of sugar weigh different amounts. Ask which ingredient it is."
- **B.** `is_error: true`, with "Amount must be above zero. You sent -5." A traceback helps a developer, not the model. Log it on your side instead.
- **C.** "Saved recipe 'Pancakes' with id r-881." or the reason it failed.

## Recap

- Every result carries the id of its call. On Claude, results come right after the call and before any text in the message.
- Keep results small and high-signal: few fields, meaningful ids, and paging or filters for big data. Always return something, even "success".
- Failures and bad calls become error results (on Claude, `is_error: true`) that say what went wrong and what to try next.

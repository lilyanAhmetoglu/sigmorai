## Goal

After this lesson you can:

- Write a tool definition: a clear name, a detailed description and an input schema.
- Use names, types and enums so that wrong calls are hard to make.
- Decide which values the model should fill and which your code should fill.

## The problem

The library assistant from chapter 1 now has a tool to place a hold on a book. A developer wrote it in five minutes:

```json
{
  "name": "hold",
  "description": "Puts a hold on a book.",
  "input_schema": {
    "type": "object",
    "properties": {
      "user": { "type": "string" },
      "book": { "type": "string" },
      "branch": { "type": "string" }
    },
    "required": ["user", "book", "branch"]
  }
}
```

The logs show three problems:

1. `book` gets the ISBN printed on the back cover. The hold system needs the catalogue record id, so the call fails.
2. `branch` gets `Riverside`, `riverside library` and `RIV`. Only one of them works.
3. The assistant asks readers for their library card number. The website already knows who is logged in.

## The idea

**The definition is a prompt.** Chapter 1 showed that the model never sees your code. It only sees the definition and the results. So everything from the prompting chapters applies: be specific, and remove guesses.

All three vendors use the same three core parts:

- a **name**, such as `get_order_status`;
- a **description** of what the tool does and when to use it;
- a **schema** for the inputs. Claude and OpenAI use JSON Schema (`input_schema` and `parameters`). Gemini's `parameters` uses "a subset of the OpenAPI schema" ([Gemini docs](https://ai.google.dev/gemini-api/docs/function-calling)).

**The description matters most.**

- The [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) ask for "extremely detailed" descriptions and call them "by far the most important" thing for tool performance. A good description covers the job of the tool, when to call it and when to skip it, the meaning of each parameter, and what the tool does not return. They suggest "at least 3–4 sentences for each tool description".
- The [OpenAI docs](https://developers.openai.com/api/docs/guides/function-calling) say: "Explicitly describe the purpose of the function and each parameter (and its format), and what the output represents."
- The OpenAI docs also give a test: "Pass the intern test." Could a new person use the function with only what you gave the model?

Think of a form at a post office. A box labelled only "Number" gets phone numbers, house numbers and parcel numbers. A box labelled "Parcel number (12 digits, on the yellow slip)" gets the right one.

**Names and types.**

- Anthropic's [engineering post on tools](https://www.anthropic.com/engineering/writing-tools-for-agents) says to name parameters so they cannot be misread: "instead of a parameter named `user`, try a parameter named `user_id`."
- The OpenAI docs: "Use enums and object structure to prevent invalid states." Their example is `toggle_light(on: bool, off: bool)`, which allows a call with both set to true.
- The Gemini docs say: "Use specific types (integer, string, enum)."

**Strict mode.** Without it, the model can send inputs that break your schema.

- The [Claude strict tool use page](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) says Claude "might return incompatible types". Example: a `passengers` field may arrive as `"two"` or `"2"` instead of `2`. Setting `strict: true` "guarantees Claude's tool inputs match your JSON Schema".
- The OpenAI docs say strict mode makes calls "reliably adhere to the function schema, instead of being best effort. We recommend always enabling strict mode." It needs `additionalProperties: false` and every field in `required`. To make a field optional, add `null` as a type.
- Both vendors support only part of JSON Schema in strict mode.

Strict mode checks the shape of the input. It does not check that a value is real: a well-formed id can still point to nothing.

**Let code fill what code knows.** The OpenAI docs: "Don't make the model fill arguments you already know." Their example: if you already have the `order_id`, define `submit_refund()` with no parameters and pass the id in your own code.

**Keep the list short.**

- The OpenAI docs: "Aim for fewer than 20 functions" at the start of a turn, "though this is just a soft suggestion".
- The Gemini docs: "Keep active set to 10-20 tools maximum."
- The Claude docs: "Consolidate related operations into fewer tools". Example: one tool with an `action` parameter instead of `create_pr`, `review_pr` and `merge_pr`.
- The OpenAI docs: "Combine functions that are always called in sequence."
- Prefix names by service. The Claude docs suggest service prefixes such as `github_list_prs`; OpenAI has namespaces such as `crm` and `billing`.

## Worked example

### Step 1: fix the name and description

`hold` says almost nothing. The new name says the service and the action: `catalog_place_hold`. The description answers the intern's questions:

```text
Places a hold on one catalogue record, so the reader is told when a
copy is ready to collect. Use it only after check_availability shows
no copy on the shelf at the reader's branch. Do not use it to renew a
loan. Returns the hold id and the reader's place in the queue. It does
not say when the copy will arrive.
```

### Step 2: fix the inputs

```json
{
  "name": "catalog_place_hold",
  "description": "Places a hold on one catalogue record ... (the text from step 1)",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "record_id": {
        "type": "string",
        "description": "The catalogue record id returned by check_availability, for example b2291047. Not the ISBN printed on the book."
      },
      "pickup_branch": {
        "type": "string",
        "enum": ["central", "riverside", "northgate"],
        "description": "The branch where the reader will collect the book."
      }
    },
    "required": ["record_id", "pickup_branch"],
    "additionalProperties": false
  }
}
```

**The hard case is the book id.** A reader holding a book sees an ISBN, and the model sees "book". Strict mode cannot fix this, because an ISBN is a valid string. Only the name `record_id`, the format example and the "not the ISBN" line tell the model which number to send.

### Step 3: remove what the code knows

`user` is gone. The website session knows the reader. Your code adds the reader id when it runs the call:

```text
model sends:   catalog_place_hold(record_id="b2291047", pickup_branch="riverside")
code adds:     reader id from the login session
code runs:     the hold, for that reader only
```

### Step 4: why it is better

- **The right id.** The parameter name, description and example point to one number.
- **No spelling games.** The enum gives three branch values, and strict mode enforces them.
- **No questions the website can answer.** The model never asks for the card number, and it cannot place a hold for someone else.
- **Clear limits.** The description says when not to use the tool and what it does not return.

## Common mistakes

1. **A one-line description.** "Gets data." leaves the model to guess when to call the tool. Fix: write 3–4 sentences: what, when, when not, and what comes back.
2. **Expecting strict mode to check values.** Strict mode guarantees the shape, not the facts. Fix: clear names and descriptions for the meaning, and a check in your code for the value.
3. **Many near-twin tools.** `get_hold`, `list_holds` and `hold_status` overlap, and the model picks at random. Fix: merge them into one tool, and prefix names by service.

## Try it

Not graded. Write your answer down before you read the answer.

A cinema app has this tool. Logged-in members book seats by chat. Find three problems and fix them.

```json
{
  "name": "book",
  "description": "Books seats.",
  "input_schema": {
    "type": "object",
    "properties": {
      "member": { "type": "string" },
      "show": { "type": "string" },
      "seats": { "type": "string" }
    },
    "required": ["member", "show", "seats"]
  }
}
```

### Answer

1. **Vague name and description.** Fix: `cinema_book_seats`, with 3–4 sentences: what it books, when to use it, when not (for example not for refunds), and what it returns.
2. **`member` is known from the login.** Fix: remove it, and add the member id in code.
3. **`seats` is free text.** It will get "two", "2" and "A4, A5". Fix: an `integer` count, or an array of seat codes with a format example like `F12`, and turn on strict mode.

Also rename `show` to `showing_id` and describe where the id comes from.

## Recap

- A tool definition is a prompt: a name, a detailed description and an input schema. The description does most of the work.
- Make wrong calls hard: clear parameter names, enums, specific types and strict mode. Strict mode checks shape, not truth.
- Let your code fill values it already knows, and keep the tool list short.

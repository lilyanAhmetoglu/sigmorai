## Goal

After this lesson you can:

- Order a prompt so that a long, stable part can be reused from the cache.
- Turn caching on and place the cache point on Claude, OpenAI and Gemini.
- Read the usage fields to prove a cache hit, and estimate what caching saves.

## The problem

A team runs a code-review bot. Each request sends three things: the team's coding standards (about 9,000 tokens), a short line about the pull request, and the diff to review. The bot reviews about 40 pull requests an hour.

The prompt starts like this: `PR #4812 by Dana, opened 10:02`. The coding standards come next, then the diff. The standards never change, but the team pays full input price for all 9,000 tokens on every request. They want to pay less for the part that repeats.

## The idea

When a model reads input, it computes internal states for every token. The [OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching) explain that prompt caching "preserves that state for a reusable **prefix**: the unchanged tokens at the beginning of a prompt." A later request with the same start can reuse that work.

Think of a bookmark in a long book. You can skip to the bookmark only if every page before it is exactly the same.

```text
request 1:  [standards ......... ] [PR line] [diff A]
request 2:  [standards ......... ] [PR line] [diff B]
             ^ same prefix: reused  ^ new: processed
```

The key word is **prefix**. Any change near the start breaks the match for all the text that follows.

- **The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching):** the cache covers `tools`, `system` and `messages`, "in that order", up to the block you mark. Hits "require 100% identical prompt segments".
- **The OpenAI docs:** "Cache reuse requires the entire rendered prefix to match." If your instructions contain "timestamps, user-specific content, or other dynamic content", the docs say to place them at the end.
- **The [Gemini docs](https://ai.google.dev/gemini-api/docs/caching):** "Try putting large and common contents at the beginning of your prompt".

The defaults differ:

- **Claude:** you opt in with `cache_control`. Automatic caching is one `cache_control` field at the top of the request. Or you mark up to 4 blocks yourself (explicit breakpoints).
- **OpenAI:** supported models cache on their own ("enabled by default"). On GPT-5.6 and later, you can also mark a block yourself (`prompt_cache_breakpoint`).
- **Gemini:** the Gemini docs say implicit caching is on "for all Gemini 2.5 and newer models". The docs add: "There is nothing you need to do".

Caching changes the price, not the answer. The Claude docs: the response "is identical to what you would get if prompt caching were not used."

## Worked example

The review bot uses Claude Sonnet 5.5. Let's make the standards cacheable step by step.

### Step 1: the weak layout

```text
system[0]  PR #4812 by Dana, opened 10:02      (changes every request)
system[1]  coding standards                    (~9,000 tokens, never changes)
messages   the diff                            (changes every request)
no cache_control
```

What goes wrong:

- Claude does not cache without `cache_control`, so every request pays full price.
- Even with caching on, the first block changes every time. Nothing after it can match.

### Step 2: stable first, changing last

```text
system[0]  coding standards                    (stable)
system[1]  PR #4812 by Dana, opened 10:02      (changes)
messages   the diff                            (changes)
```

The PR line moves below the standards. Now every request starts with the same 9,000 tokens.

### Step 3: mark the last stable block

```json
{
  "system": [
    {
      "type": "text",
      "text": "[coding standards, ~9,000 tokens]",
      "cache_control": { "type": "ephemeral" }
    },
    { "type": "text", "text": "PR #4812 by Dana, opened 10:02" }
  ],
  "messages": [{ "role": "user", "content": "[the diff]" }]
}
```

Why on the standards and not on the last block? The Claude docs: "Place the breakpoint on the last block that stays identical across requests." A mark on a changing block writes a new entry each time. Automatic caching falls into the same trap here: it places the cache point on the last cacheable block, which changes every request. So use an explicit mark.

### Step 4: prove it in the usage fields

Request 1 writes the cache. Requests 2, 3 and 4 should read it:

```text
request 1:  cache_creation_input_tokens=9,012  cache_read_input_tokens=0
request 2:  cache_creation_input_tokens=0      cache_read_input_tokens=9,012
request 3:  cache_creation_input_tokens=0      cache_read_input_tokens=9,012
```

On OpenAI, read `usage.input_tokens_details.cached_tokens` and `cache_write_tokens`. On Gemini, read `usage.total_cached_tokens`.

### Step 5: what it costs

On Claude, a 5-minute cache write is 1.25 times the base input price (the docs: "1.25 times the base input tokens price"). A read is normally 0.1 times, but the docs list exceptions: "Cache hits and refreshes on Claude Opus 5.5 and Claude Sonnet 5.5 are priced at 0.05x the base input price."

Ten reviews inside the cache lifetime, measured in "one full pass of the standards":

```text
no cache:                 10 x 1.00               = 10.00
Sonnet 5.5 (0.05 reads):  1.25 + 9 x 0.05         =  1.70
a 0.1x-read model:        1.25 + 9 x 0.10         =  2.15
```

The OpenAI docs do the same sum for GPT-5.6 and later at the 0.1 read rate: "one write and nine full reads cost 2.15×".

The default Claude lifetime is 5 minutes. The Claude docs: "The cache is refreshed for no additional cost each time the cached content is used." For longer gaps, Claude also has a 1-hour cache "at 2x the base input token price" for writes. On OpenAI models before GPT-5.6, `prompt_cache_retention` set to `24h` can keep entries "for up to 24 hours". At 40 reviews an hour, a request comes about every 90 seconds, so the 5-minute cache stays warm.

### Step 6: the hard case, a cheaper model

To save more, the team moves small diffs to Claude Haiku 4.5 and trims the standards to a 3,000-token summary. Now both usage fields show 0 on every request. There is no error.

The reason: each model has a minimum cacheable length. It is "4,096 tokens for Claude Haiku 4.5" and 512 tokens for Claude Sonnet 5.5. Shorter prompts "will be processed without caching, and no error is returned". Fix: check the minimum for the model before you trust caching. Here, either keep the full standards on Haiku 4.5 (over 4,096) or accept no caching for the short version.

### Why it is better

- **One stable prefix.** The 9,000 tokens are the same on every request, so they are read from the cache.
- **The mark sits on the last stable block.** Each request writes nothing new and reads the standards.
- **Proven, not assumed.** The usage fields show a write, then reads.

## Common mistakes

1. **Dynamic data at the top.** A date, a name or a request id in the first block breaks every match. Fix: move all changing parts below the stable content.
2. **Marking the newest block.** It changes every time, so you pay for writes and never read. Fix: put the mark on the final stable block.
3. **Trusting caching without checking.** A prompt under the model's minimum is simply not cached, with no error. Fix: read the cache fields in the response usage.

## Try it

Not graded. This Claude request runs 200 times a day for a translation tool. Find two problems.

```text
tools      12 tool definitions                  (~2,500 tokens, stable)
system[0]  Glossary for customer: ACME-DE       (changes per customer)
system[1]  translation rules                    (~6,000 tokens, stable)
messages   the text to translate                (changes)
cache_control on: messages (the text)
```

### Answer

1. **A changing block sits between stable ones.** The customer glossary is above the 6,000-token rules, so the rules can only be cached together with one customer's glossary. Fix: put the rules before the glossary.
2. **The mark is on the changing text.** Fix: mark the rules block, the last stable one. The tools come first in Claude's order (`tools`, then `system`), so they are part of that cached prefix.

## Recap

- Caching reuses the work for an identical prefix. Put stable content first and changing content last.
- Claude needs `cache_control` on the last stable block (or a top-level field). OpenAI (supported models) and Gemini 2.5+ cache on their own.
- Writes cost a little more and reads much less, but only above the model's minimum length. Check the usage fields to see the hit.

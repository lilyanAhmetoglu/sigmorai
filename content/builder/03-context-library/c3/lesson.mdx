You have chunks and vectors. Now a user asks a question. Retrieval is the step that picks which chunks reach the model. Pick badly and the model answers from the wrong pages, or from none.

## The basic loop

At question time, a simple RAG system does three things:

1. Turn the question into a vector. Gemini File Search: "When you make a query, it's also converted into an embedding."
2. Find the chunks whose vectors are closest.
3. Add the top chunks to the prompt and ask the model to answer.

OpenAI's Retrieval API does steps 1 and 2 for you: a `search` call on a vector store returns results "each with the relevant chunks, similarity scores, and file of origin". By default it returns at most 10 results; `max_num_results` raises that to 50.

## Where meaning search fails

Embeddings match meaning, but they can miss exact strings. Anthropic's example: a user searches a support database for "Error code TS-999". An embedding model "might find content about error codes in general, but could miss the exact" match.

The older fix is keyword search. Anthropic uses BM25, a ranking function that "uses lexical matching to find precise word or phrase matches". It is "particularly effective for queries that include unique identifiers or technical terms": part numbers, error codes, product names.

## Hybrid search: use both

Anthropic's recipe runs both searches and merges them:

1. Use BM25 to find top chunks by exact matches.
2. Use embeddings to find top chunks by meaning.
3. Combine and remove duplicates with rank fusion.
4. Add the top chunks to the prompt.

Its conclusion: "Embeddings+BM25 is better than embeddings on their own". In its tests, contextual embeddings plus contextual BM25 cut the top-20 retrieval failure rate by 49% (5.7% to 2.9%).

OpenAI exposes the same idea as settings. Its file search tool retrieves "through semantic and keyword search". In the Retrieval API, `ranking_options.hybrid_search` has two weights for reciprocal rank fusion: raise `embedding_weight` to favour meaning, or raise `text_weight` to favour shared words. At least one weight must be above zero.

## Narrow the search first

Two OpenAI settings help before ranking even starts.

- **Attribute filters** limit the search to files with certain labels, such as a region or a date range.
- **Query rewriting** (`rewrite_query=true`) turns a chatty question into a better search string. OpenAI's example: "I'd like to know the height of the main office building." becomes `primary office building height`.

OpenAI also offers a `score_threshold` from 0.0 to 1.0. A higher value keeps only more relevant chunks, "though it may exclude some potentially useful ones".

## Rerank the shortlist

Anthropic notes that with large knowledge bases, the first search often returns many chunks, "sometimes hundreds", of varying relevance. A reranker is a second model that scores each chunk against the question, so only the best ones reach the main model.

Anthropic's steps:

1. Retrieve the top candidates (it used the top 150).
2. Pass them, with the query, to a reranking model.
3. Keep the top-K by score (it used the top 20).
4. Send those to the model.

Voyage AI makes rerankers as well as embedding models. In the Claude docs, rerankers "take a query and a list of documents and return them ranked by relevance to the query."

In Anthropic's tests, adding reranking to contextual embeddings and BM25 cut the failure rate by 67% (5.7% to 1.9%). The cost is time: reranking "inevitably adds a small amount of latency". Reranking more chunks gives better results; fewer gives lower latency and cost.

## How many chunks to send

More chunks raise the chance that the answer is in the prompt. But Anthropic warns that "more information can be distracting for models". It tried 5, 10 and 20 chunks and found 20 performed best of these, while advising you to experiment. OpenAI makes the same trade from the other side: fewer results can reduce token usage and latency, "but may come at the cost of reduced answer quality."

## Hand the results to the model with sources

Retrieval is more useful when the user can check the answer. Claude, OpenAI and Gemini each document a way to link an answer back to the retrieved text.

- **Claude:** wrap each result in a `search_result` block with a `source`, a `title` and text `content`. With citations enabled, Claude cites them in its answer. The `source` can be "a URL, or an internal identifier such as `kb://article-1234`".
- **OpenAI:** the hosted `file_search` tool returns the model's message "along with the file citations".
- **Gemini:** File Search responses "may include citations that specify which parts of your uploaded documents were used to generate the answer."

Example: a support bot answers "Reset the router by holding the button for 10 seconds" and shows the cited source `kb://router-x200-manual`. A human can open it and check.

## Key points

- Retrieval embeds the question, finds the nearest chunks and adds the best ones to the prompt.
- Embeddings can miss exact strings like error codes. BM25 keyword search catches them; hybrid search uses both.
- OpenAI exposes hybrid weights, attribute filters, query rewriting and a score threshold.
- A reranker re-scores a large shortlist (Anthropic: 150) down to a small set (20). Better results, a little more latency.
- More chunks raise recall but can distract the model and cost more tokens. Test the number.
- Pass results with sources so the model can cite them: `search_result` blocks on Claude, file citations on OpenAI and Gemini.

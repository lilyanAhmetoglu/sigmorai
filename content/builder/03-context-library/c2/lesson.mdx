## Goal

After this lesson you can:

- Choose a chunk size, a chunk boundary and an overlap, and stay inside each vendor's limits.
- Spot a chunk that lost its context, and fix it with a short context line written by a model.
- Keep a code sample or table whole when you cut a document.

## The problem

A developer-tools company has 4 years of release notes: one long page per version, 60 versions in all. A support assistant answers questions from them with RAG.

A user asks: "In which version was the `--legacy-auth` flag removed?" The assistant finds this chunk:

```text
The --legacy-auth flag is removed. Use --token instead.
```

The chunk is right, but it never says which version it belongs to. The assistant guesses a version, and the guess is wrong.

A second user asks for the migration code from that release. The chunk with the code stops halfway through the example. The other half sits in the next chunk, which search does not return.

Both bugs come from one step: how the notes were cut into chunks.

## The idea

You do not embed a 40-page document as one vector. You cut it into **chunks** first. The [Anthropic Contextual Retrieval post](https://www.anthropic.com/engineering/contextual-retrieval) describes chunks as "usually no more than a few hundred tokens". Each chunk gets its own vector, and search returns chunks, not whole documents. So the chunk is the unit the model will see.

Think of cutting a cookbook into index cards. If one card holds half a recipe, the cook gets half a recipe.

The same post names three choices: "The choice of chunk size, chunk boundary, and chunk overlap can affect retrieval performance."

```text
size:     how many tokens per chunk
boundary: where a cut may fall (any token? only at a heading?)
overlap:  how many tokens two neighbour chunks share

|------ chunk 1 ------|
               |------ chunk 2 ------|
               ^^^^^^^ overlap
```

Managed vector stores cut files for you, with their own settings:

- **OpenAI vector stores** ([OpenAI docs](https://developers.openai.com/api/docs/guides/retrieval)): "By default, `max_chunk_size_tokens` is set to `800` and `chunk_overlap_tokens` is set to `400`." You can change it with `chunking_strategy`. The size must be "between 100 and 4096" tokens, inclusive. The overlap "should not exceed" half of it (`max_chunk_size_tokens / 2`).
- **Gemini File Search** ([Gemini docs](https://ai.google.dev/gemini-api/docs/file-search)): files are "automatically broken down into chunks". A `chunking_config` sets the most tokens per chunk and the most overlapping tokens.

A cut can also remove context. Anthropic's example is a chunk that says revenue grew by 3%, but that "doesn't specify which company it's referring to or the relevant time period". The fix in the post is **Contextual Retrieval**: a model reads the chunk together with its full document, then writes a short context. The context, "usually 50-100 tokens", is added in front of the chunk "before embedding it and before creating the BM25 index" (BM25 is keyword search; chapter 3 covers it). Writing these by hand would be "far too much work" for thousands of chunks, so a model does it.

There is also a second way. The [Claude docs](https://platform.claude.com/docs/en/build-with-claude/embeddings) list Voyage AI contextualized chunk models, such as `voyage-context-4`. They "produce chunk-level vectors that capture full document context without manual metadata augmentation". You call them with `contextualized_embed()`.

## Worked example

The team's first script cut the notes itself. Let's fix the chunking step by step, and move it to an OpenAI vector store.

### Step 1: the weak version

```python
chunks = [text[i:i + 1200] for i in range(0, len(text), 1200)]   # 1,200 characters, no overlap
```

What goes wrong:

- The cut can fall anywhere: inside a word, inside a code sample, inside a table.
- No overlap, so text near a cut is split between two chunks.
- Most chunks never name their version.

### Step 2: choose size, boundary and overlap

Release notes have clear headings (`## v4.2.0`, `### Breaking changes`). Split at headings first, and upload each section as its own file. Then let the vector store cut long sections, with settings inside its limits:

```text
chunking_strategy (type: static)
  max_chunk_size_tokens: 600
  chunk_overlap_tokens:  150
```

600 is inside 100–4096. 150 is less than half of 600 (300), so the overlap rule holds too. On Gemini File Search, the same idea goes in `chunking_config` (the docs' example sets 200 tokens per chunk and 20 overlapping tokens).

### Step 3: the hard case, a code sample on a cut

The migration example for `--legacy-auth` is 220 tokens long. It starts 100 tokens before a cut. With 150 tokens of overlap, it still does not fit in one chunk: the overlap is shorter than the example.

Overlap only saves text that is no longer than the overlap. Two fixes, best first:

1. **Never cut inside a code block or a table.** Keep each one whole, even if that chunk is a bit longer. A 220-token example fits easily in a 600-token chunk.
2. If you cannot control the cut, make the overlap at least as long as your longest example, and stay under the half-size rule.

### Step 4: add context to each chunk

The removed-flag chunk still has no version. Use a model to write a context line for every chunk. Anthropic's post shares its prompt:

```text
<document>
[the whole release note for one version]
</document>
Here is the chunk we want to situate within the whole document
<chunk>
[one chunk]
</chunk>
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else.
```

Before and after:

```text
before: The --legacy-auth flag is removed. Use --token instead.

after:  From the v4.2.0 release notes (March 2026), section Breaking changes.
        The --legacy-auth flag is removed. Use --token instead.
```

Now the word "v4.2.0" is in the chunk, so both meaning search and keyword search can match it, and the model can name the version.

### Step 5: keep it cheap

Every call sends the whole release note again, once per chunk. Anthropic's post uses prompt caching (chapter 4): load the document into the cache once, then send only the new chunk each time. With its stated assumptions (800-token chunks, 8k-token documents), the one-time cost was "$1.02 per million document tokens".

### Why it is better

- **Clean cuts.** Headings, code samples and tables stay whole.
- **Inside the limits.** Size and overlap follow the vendor's rules, so the upload is accepted.
- **Findable chunks.** Each chunk names its version. In Anthropic's tests, contextual embeddings cut the top-20 retrieval failure rate by 35% (5.7% to 3.7%).

You can also add labels that are not in the text. OpenAI files can have `attributes` (at most 16 keys) to filter on. Gemini File Search takes custom metadata, "a set of key-value pairs". Example: `product: cli` or `product: sdk`.

## Common mistakes

1. **Cutting by characters with no regard for structure.** Code and tables break in half. Fix: cut at headings and keep code blocks and tables whole.
2. **Trusting overlap to save anything.** Overlap only protects text shorter than the overlap. Fix: check your longest code sample or table against the overlap, or avoid cuts inside them.
3. **Adding one summary to every chunk.** Anthropic tried this kind of shared document summary and the gain was small. Fix: write a context that is specific to each chunk.

## Try it

Not graded. A team chunks a product manual. Find two problems before you read the answer.

```text
OpenAI vector store, chunking_strategy:
  max_chunk_size_tokens: 300
  chunk_overlap_tokens:  200

Sample chunk after upload:
  "Press and hold for five seconds until the light turns blue."
```

### Answer

1. **The overlap breaks the rule.** 200 is more than half of 300 (150). Fix: lower the overlap to 150 or less, or raise the chunk size.
2. **The chunk lost its context.** It does not say which product or which button. Fix: add a model-written context line per chunk, for example "From the Model T2 manual, section Pairing the remote." Or use a contextualized embedding model.

## Recap

- Chunks are the unit you retrieve. Size, boundary and overlap all change what search can find. Stay inside the vendor's limits (OpenAI: 100–4096 tokens, overlap at most half).
- Cut at structure. Keep code samples and tables whole; overlap only saves text shorter than the overlap.
- A chunk can lose the facts that make it findable. Add a short model-written context to each chunk (Contextual Retrieval), and use prompt caching to keep it cheap.

## Goal

After this lesson you can:

- Keep two lists of test jobs: regression jobs that must keep passing, and capability jobs that are still hard.
- Say which changes should trigger a test run, and treat a vendor's "move to the new model" note as one of them.
- Repeat jobs and work out how often a whole set of images comes out right.

## The problem

A wedding stationery shop makes watercolour monograms and invitation art with an image model. Six months ago the team tested the setup carefully, and it worked.

Since then, three things changed:

1. A designer added "gold foil look" to the style block in the prompt kit.
2. The vendor posted a note that a newer model is recommended.
3. The shop started selling sets of four matching cards.

Nobody re-ran the old tests after any of these. Then the complaints came: monograms with an "&" between two initials now often lose the "&". In the sets of four, at least one card often has a small flaw. A change that looked harmless broke a job that used to work.

This lesson shows how to catch that before a customer does.

## The idea

### Two kinds of test

The [Anthropic post on evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) splits evals into two kinds:

- **Capability evals** ask "What can this agent do well?" They "should start at a low pass rate", giving teams "a hill to climb".
- **Regression evals** ask "Does the agent still handle all the tasks it used to?" They "should have a nearly 100% pass rate". The post says "a decline in score signals that something is broken and needs to be improved."

A **regression** is when something that used to work stops working. The post adds that capability evals with high pass rates can "graduate" to become a regression suite.

For a creator: a capability job is a new, hard job, such as a monogram in a hand-lettered script. A regression job is one that works today and must keep working, such as the two initials with an "&".

A comparison: a regression list is like a pilot's pre-flight checklist. The plane flew yesterday. You still check the same things before every flight.

### Feed the suite with real failures

A **suite** is your full set of test jobs. The Anthropic post says to look at your bug tracker and support queue: "Converting user-reported failures into test cases ensures your suite reflects actual usage". The [OpenAI evaluation docs](https://developers.openai.com/api/docs/guides/evaluation-best-practices) say the same thing in other words: "grow the eval set over time".

Our habit: every customer complaint gets a question. Which test would have caught this? Then add it. A flaw you fixed once cannot come back unseen.

### Run it on every change

The OpenAI docs: "Set up continuous evaluation (CE) to run evals on every change, monitor your app to identify new cases of nondeterminism, and grow the eval set over time." **Nondeterminism** means the same input can give a different output.

Our list of changes that should trigger a run:

- a new model, or a new version of the one you use
- any edit to the prompt kit, style block or reference images
- a change to size, quality or filter settings
- a vendor update to a moderation or safety model

Vendors will tell you to move. The [Gemini API image docs](https://ai.google.dev/gemini-api/docs/image-generation) say of Nano Banana 2: "Recommended for all new projects to use Nano Banana 2.1." The [OpenAI image docs](https://developers.openai.com/api/docs/guides/image-generation) say: "For new integrations, use one of the GPT Image 2.5 models described above."

Our reading: these notes are a reason to run your suite. They are not proof that the new model is better for your jobs, and they say nothing about which of your jobs will still work.

The payoff, in the Anthropic post's words: when more powerful models come out, "teams without evals face weeks of testing while competitors with evals can quickly determine the model's strengths, tune their prompts, and upgrade in days."

### The same prompt, a different image

Image models vary from run to run, so one pass proves little. The Anthropic post gives a way to count this. **pass^k** "measures the probability that all k trials succeed". Its example: "If your agent has a 75% per-trial success rate and you run 3 trials, the probability of passing all three is (0.75)³ ≈ 42%." The post says this matters most "where users expect reliable behavior every time".

Its partner metric, **pass@k**, "measures the likelihood that an agent gets at least one correct solution in k attempts". The post: "pass@k for tools where one success matters, pass^k for agents where consistency is essential."

### Keep the suite alive

The Anthropic post warns: "An eval at 100% tracks regressions but provides no signal for improvement." That warning is about capability evals. Our reading: a regression list should sit near 100%, and that is its job. When your capability list is always at 100%, move those jobs to the regression list and write harder capability jobs. The post also says: "An eval suite is a living artifact that needs ongoing attention and clear ownership to remain useful."

### Keep your files

Tools change. The [OpenAI deprecations page](https://developers.openai.com/api/docs/deprecations) lists the Evals platform dates:

- "Oct 31, 2026": "Existing evals become read-only."
- "Nov 30, 2026": "The Evals dashboard and API are scheduled to shut down."

The page links a migration guide, "Moving from OpenAI Evals to Promptfoo". Our habit: keep test jobs, rubrics, anchor images and past results as files you own, so a tool can change and your suite stays.

## Worked example

### Step 1: the weak setup

```text
Tests:     run once, six months ago
Triggers:  none
Repeats:   one image per job
Complaints: fixed one by one, never added to tests
```

### Step 2: two lists

```text
REGRESSION (must stay near 100%)
  R-01  two initials with "&", serif
  R-02  three initials, script
  R-03  wreath around a monogram, sage green only
  ...   30 jobs from orders that worked, plus past complaints

CAPABILITY (expected to be hard)
  C-01  hand-lettered script with long names
  C-02  couple's pet in watercolour, matching the palette
  ...   8 jobs
```

### Step 3: triggers and owner

```text
Run both lists when: model, prompt kit, settings or filters change,
                     or a vendor posts a "move to" note.
Owner: one named designer. Review the lists every quarter.
```

### Step 4: the hard case

**The hard case is the set of four cards.** The team repeats job R-03 twenty times. The wreath comes out right in 19 of 20 runs: 95% per image.

Is that good enough for a set of four? Our maths, using pass^k:

```text
All 4 right: 0.95 x 0.95 x 0.95 x 0.95 = 0.8145, about 81%
At least one flawed card: about 19 sets in 100
```

Each card is right 95% of the time, yet about one set in five has a flaw. That matches the complaints. So the regression run must repeat each set job and report how often all repeats pass, not just one image.

### Step 5: why it is better

- **Every change triggers a run**, including the small "gold foil" edit.
- **Complaints become tests**, so the lost "&" cannot come back unseen.
- **Repeats show reliability**, the thing customers feel.
- **A named owner keeps the suite alive.**

## Common mistakes

1. **Mixing both lists into one score.** Gains on hard jobs hide a broken easy one. Fix: report regression and capability separately.
2. **Trusting a vendor's "recommended" note.** It is a trigger, not a test result. Fix: run your suite on the new model first.
3. **One run per job.** A lucky pass hides a flaky job. Fix: repeat jobs and report how often all repeats pass.

## Try it

Not graded. Write your answer down before you read the answer.

A designer asks the model for 3 draft monograms and picks the best one. Each draft is good 80% of the time. The draft is only for the designer, who will fix it by hand.

1. Which metric fits this job, pass@k or pass^k?
2. About how often is at least one of the 3 drafts good?

### Answer

1. **pass@k.** Only one good draft is needed. The Anthropic post says pass@k fits "where one success matters".
2. **About 99%.** Our maths: the chance that all 3 drafts are bad is 0.2 x 0.2 x 0.2 = 0.008. So at least one is good 1 - 0.008 = 0.992 of the time. Compare a set of cards that must all be right: there you need pass^k, and the number is much lower.

## Recap

- Keep two lists. The regression list should sit close to 100%, and a drop means something broke. Capability jobs start low; move them to regression when they stay at 100%.
- Turn every complaint into a test, run the suite on every change, and treat a vendor's "move to the new model" note as a trigger, not proof.
- Repeat jobs. pass^k is the chance all k tries succeed, so 95% per image is about 81% for a set of four. Keep your suite in files you own.

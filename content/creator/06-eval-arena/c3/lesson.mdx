## Goal

After this lesson you can:

- Choose what code, a model judge and a person should each check.
- Write a judge prompt for one rubric line, with a short reason and a way out.
- Check a judge against people before you trust it, and read where it goes wrong.

## The problem

A small team sells icon packs. Each week an image model makes about 400 icons. The rules: one object per icon, no stray letters, even line width. Checking 400 icons by hand takes a full day, so the team adds a **model judge**: a second model that looks at each icon and applies the rules.

They test the judge for one afternoon. It looks fine, so they switch it on.

A month later, buyers complain. About one icon in twenty has tiny letters near the edge, like a fake label. The judge passed almost all of them. Nobody had checked how often the judge was wrong, or what kind of mistakes it made.

A model judge is fast and never gets tired. It can also be wrong in a calm, confident way. This lesson shows how to check one before you trust it.

## The idea

### Three kinds of grader

A **grader** is whatever gives the score. The [Claude docs on evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests) compare three kinds:

- **Code-based grading:** "Fastest and most reliable, extremely scalable", but it "lacks nuance for more complex judgments".
- **Human grading:** "Most flexible and high quality, but slow and expensive. Avoid if possible."
- **LLM-based grading:** "Fast and flexible, scalable and suitable for complex judgment. Test to ensure reliability first then scale."

The [Anthropic post on evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) lists the weak points of model graders:

- "Non-deterministic"
- "More expensive than code"
- "Requires calibration with human graders for accuracy"

**Non-deterministic** means the same input can get a different grade on another run.

Our order: use code for what code can check (file type, size, transparency). Use a model judge for what needs eyes. Use people to check the judge.

A comparison: a model judge is like a new junior proofreader. Fast, useful, but you check a sample of their work before you stop looking.

### Three ways to judge

The [OpenAI evaluation docs](https://developers.openai.com/api/docs/guides/evaluation-best-practices) list these:

- **Pairwise comparison:** show two outputs and ask which is better on given criteria.
- **Single answer grading:** score one output on its own.
- **Reference-guided grading:** give the judge a "gold standard" answer to compare with.

They say: "Use pairwise comparison or pass/fail for more reliability", because "LLMs are better at discriminating between options". In plain words: "Does this icon contain any letters?" works better than "Rate this icon from 1 to 100".

The same docs say model judges are "cheaper to run and more scalable than human evaluation".

### Write the judge prompt like a rubric line

Tips from three sources:

- **One clear line.** The Claude docs: "Have detailed, clear rubrics". They also suggest a plain output, such as only "correct" or "incorrect".
- **Reason first.** The Claude docs say to use a grader "with thinking on, so that it reasons before it produces an evaluation score". The OpenAI docs agree: "reasoning before scoring improves eval performance".
- **A way out.** The Anthropic post says: "To avoid hallucinations, give the LLM a way out". Its example: the judge may return Unknown if it does not have enough information.
- **One judge per line.** The same post advises grading every dimension "with an isolated LLM-as-judge rather than using one to grade all dimensions".

### Known biases

The OpenAI docs list two challenges for a model judge: "Position bias (response order), verbosity bias (preferring longer responses)". For text, they say to "Control for response lengths". Images have no word count, so our reading is that verbosity bias may not carry over. Position bias does matter for images. Our test: show every pair twice, once in each order. If the judge keeps picking whichever came first, the order decides, not the image.

### Check the judge against people

The OpenAI docs: "Use human feedback to calibrate automated scoring." **Calibrate** means you compare the judge with people and adjust until they agree. And: "Once the LLM judge reaches a point where it's faster, cheaper, and consistently agrees with human annotations, scale up."

The [OpenAI graders page](https://developers.openai.com/api/docs/guides/graders) gives a method. Take answers that people have ranked from best to worst, and check that the model grader puts them in the same order. It also warns about "grader hacking": a model being trained can learn to exploit a model grader, so it scores high there "but score poorly on expert human evaluations".

The Anthropic post adds: "You won't know if your graders are working well unless you read the transcripts and grades from many trials." For you, the transcript is the judge's reason for each icon.

Our advice: count the two kinds of mistake apart. A judge can pass work a person failed (too lenient), or fail work a person passed (too strict). Both lower the same overall agreement, so one agreement number cannot tell you which one you have. For a quality gate, the lenient mistake usually costs more, because the bad work ships.

The same judge can grade the same image differently on another run. Our habit: run the judge two or three times on the same set. If a line's grades keep flipping, the wording is too loose. Tighten it or add an anchor image.

### A tool note

The OpenAI docs say OpenAI is deprecating graders as part of its evals workflows. The [deprecations page](https://developers.openai.com/api/docs/deprecations) gives two dates. "Oct 31, 2026": "Existing evals become read-only." "Nov 30, 2026": "The Evals dashboard and API are scheduled to shut down." The ideas in this lesson do not depend on one tool. Our habit: keep rubrics, anchors and human labels in files you own.

## Worked example

### Step 1: the weak judge

```text
Rate this icon from 1 to 100 for overall quality.
Reply with one number.
```

What goes wrong: three rules are mixed into one number. There is no reason to read, no way to say "I can't tell", and nobody knows which number means pass.

### Step 2: split the work

```text
Code:   PNG? transparent background? exactly 512x512?
Judge:  no stray letters | one object | even line width
People: check the judge on a labelled sample, then spot-check
```

### Step 3: one judge prompt per line

```text
Look at the icon. Question: does it contain any letters,
numbers or text-like marks? Check all four edges.
First, reason in one or two lines. After that, give exactly one of
PASS (no text), FAIL (text found) or UNKNOWN,
and one sentence that says where you looked.
```

Simplified. See the docs for the exact request shape.

### Step 4: the hard case

**The hard case is the UNKNOWN pile.** A person has already marked 40 icons on the "no stray letters" line. The judge from step 3 grades the same 40. The numbers are our example.

```text
PASS     26
FAIL      5
UNKNOWN   9
Total    40
```

The weak reading: "UNKNOWN means the judge found no letters, so count those 9 as passes." The better reading: UNKNOWN is the way out working as planned. The judge is saying "I can't tell", so a person decides those 9. Look at why the judge chose UNKNOWN: 7 of the 9 say there are thin marks along one edge. The person checks the 9 and finds stray letters on 4. Counting UNKNOWN as PASS would have shipped those 4 icons.

Then improve the line, not the count. Add one sentence to the prompt: "Thin marks along an edge that could be letters count as text." Run the same 40 again. Our habit: track how many icons land in UNKNOWN. If the pile stays big, the line needs an anchor image.

### Step 5: why it is better

- **Code does what code can do**, cheaply and the same way every time.
- **Each judge checks a single rule**, gives a reason, and may say UNKNOWN.
- **The judge was checked against a person's marks** before it was trusted, and its reasons were read, not only the counts.
- **UNKNOWN goes to a person**, never to PASS.

## Common mistakes

1. **Trusting the overall agreement.** A high overall agreement can hide a judge that lets bad work through. Fix: count each kind of mistake on its own.
2. **One judge for every line at once.** The lines blur into one mood. Fix: one judge call per line, each with pass, fail or unknown.
3. **Showing pairs in one fixed order.** The judge may favour first place. Fix: show each pair in both orders.

## Try it

Not graded. Write your answer down before you read the answer.

The icon team adds four new checks. For each one, choose code, a model judge or a person.

```text
A  The file is a PNG with a transparent background.
B  The icon shows exactly one object.
C  A new pack of religious holiday icons for a client in a
   country the team does not know well.
D  The file name follows the pattern pack-0001.png.
```

### Answer

1. **A: code.** A script reads the file type and the transparency. The Claude docs call code "Fastest and most reliable".
2. **B: a model judge.** It needs eyes, and it is a single yes-or-no rule. Calibrate it on icons a person has marked.
3. **C: a person.** It needs cultural judgment, and a mistake is costly. Human grading is slow, so keep it for cases like this and for calibration.
4. **D: code.** A simple pattern check. A model would be slower and less reliable.

## Recap

- Use code for what code can check, a model judge for what needs eyes, and people to calibrate the judge. The Claude docs say to test reliability first, then scale.
- Give each judge a single rubric line to check, let it reason first, and give it a way out such as UNKNOWN. Show pairs in both orders to test for position bias.
- Before you scale, compare the judge with people. Look at the kind of mistake, not only the overall agreement, and run the same set more than once.

## Goal

After this lesson you can:

- Write a role card for a helper agent: job, input, output, tools, boundaries and check.
- Give each role only the tools its job needs.
- Pick which role to test first on a cheaper, smaller model.

## The problem

An indie game studio needs 80 inventory icons: swords, bows, potions, keys and more. A lead agent plans the work. (An **agent** is a model that plans and uses tools on its own.) It hands parts of the job to helper agents. A helper that a lead agent starts is called a **subagent**.

The first try uses one short line per helper:

```text
Icon maker 1:  "Make the weapon icons."
Icon maker 2:  "Make the weapon icons."
Checker:       "Check the icons."      Tools: all tools
```

The result on Monday:

- Both icon makers drew a sword. Nobody drew the crossbow.
- The checker "fixed" three icons by redrawing them in a new style, and saved over the originals.
- Nobody can say what "checked" means for any icon.

The helpers were not lazy. Their briefs were empty. This lesson shows what a role brief needs.

## The idea

### A role is a brief, not a name

"Art director" on a slide means nothing to a model. A **role** is a written brief that says what to do, what to return and what to leave alone.

The [Anthropic post on its multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) describes how a lead agent should brief its helpers. Each subagent "needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."

The post also shows what happens without that. At first, the lead gave short orders like "research the semiconductor shortage". One helper explored the 2021 car chip crisis, while two others both studied 2025 supply chains. The post says that without detailed task descriptions, agents "duplicate work, leave gaps, or fail to find necessary information".

That is the sword and crossbow problem. Two helpers read one vague order, so they did the same part and skipped another.

### The role card

This template is ours, not a vendor format. The first four fields follow the Anthropic list. The last two are our addition.

| Field          | What it holds                                   |
| -------------- | ----------------------------------------------- |
| **Job**        | One sentence, one verb                          |
| **Input**      | What the role gets: files, item ids, style page |
| **Output**     | The exact shape of the answer, like a file name |
| **Tools**      | Only the tools this job needs                   |
| **Boundaries** | What it must not do or touch                    |
| **Check**      | Who or what looks at the output next            |

Our habit: if the job sentence needs "and", it is often two roles.

Our advice: do not plan on a helper asking for missing facts. Nothing makes a model stop and ask. Put the facts in the card.

### Keep each job narrow

The [OpenAI orchestration guide](https://developers.openai.com/api/docs/guides/agents/orchestration) says: "Give each specialist a narrow job." It also wants the handoff description (the short note that tells the model when to pick a specialist) to be "short and concrete". The [OpenAI Agents SDK docs on handoffs](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md) say to use that field "to hint when the model should pick that handoff".

The same guide warns against too many roles: "Start with one agent whenever you can." Splitting too early "creates more prompts, more traces, and more approval surfaces".

The [Claude Agent SDK docs](https://platform.claude.com/docs/en/agent-sdk/subagents) use two fields for each subagent:

- `description`: "Natural language description of when to use this agent"
- `prompt`: "The agent's system prompt defining its role and behavior"

So the description helps the main agent choose. The prompt holds the full brief.

Our example of the two fields for the file checker:

```text
description: Use to check icon files for size, transparency and file name.
prompt:      You check icon PNGs. For each item id, report PASS or FAIL
             with one reason. Never edit, move or redraw a file.
```

Simplified. See the docs for the exact request shape.

The description is short, because it only answers "when?". The prompt is longer, because it says how to do the job and what to leave alone. The docs say a tailored prompt can hold expertise "that would be unnecessary noise in the main agent's instructions."

### Give each role only the tools it needs

The Claude docs name tool restrictions as one benefit: subagents "can be limited to specific tools, reducing the risk of unintended actions." Their example is a reviewer with only read and search tools, so it can read files but never change them.

One detail matters: if you leave the `tools` field out, the subagent "inherits every" tool available to subagents. No list means all tools.

A comparison: a role's tool list is like the keys you hand a temp worker. You give the key to one room, not the whole building.

### Match the model to the job

A Claude subagent can run on a different model from the main agent. The `model` field accepts an alias such as `sonnet` or `haiku`, and `'inherit'` "uses the main model."

The [Anthropic post on building agents](https://www.anthropic.com/engineering/building-effective-agents) gives the same idea in its routing example: send "easy/common questions to smaller, cost-efficient models" and hard or unusual ones to more capable models.

Our reading for a studio: a role that checks plain facts (is the file 128 by 128 pixels? is the name on the list?) is easier than a role that makes judgment calls. Test the smaller model on the plain role first. Do not assume a creative role is easy, even when it looks short.

### Count roles, not items

80 icons do not need 80 agents. They are 80 **items** that pass through a few roles. The Anthropic research post says its early agents made errors like "spawning 50 subagents for simple queries".

## Worked example

### Step 1: the weak plan

The lead drafts a second plan for the 80 icons. It starts 80 helpers, one per icon. It also splits the makers by topic:

```text
Sword maker, Bow maker, Potion maker, Key maker
```

### Step 2: count roles, not items

80 icons are 80 items with the same job, the same tools and the same style page. That is one role that runs 80 times.

### Step 3: the hard case

**The hard case is the topic split.** The OpenAI guide says: "Split only when the next branch truly needs different instructions, tools, or policy." Put two of the makers side by side:

```text
              Sword maker        Potion maker
Instructions  same style page    same style page
Tools         image tool         image tool
Policy        same               same
```

Nothing differs, so it is one role: Icon maker. The topic goes in the Input field, as a list of item ids.

### Step 4: write the two fields (our example)

```text
description: Use to draw inventory icons from a list of item ids.
prompt:      You draw one 128x128 PNG icon for each item id you get.
             Follow the style page and the palette file. Name each file
             <item id>.png. Draw only the ids in your list.
```

Simplified. See the docs for the exact request shape.

### Step 5: why it is better

- **One role, many items.** The lead hands out id lists, not 80 briefs.
- **Fewer moving parts.** An early split, the OpenAI guide warns, "creates more prompts, more traces, and more approval surfaces".
- **A clear test for a new role.** It needs different instructions, tools or policy, not a new topic.

## Common mistakes

1. **One agent per item.** 80 icons become 80 briefs. Fix: one role per job, with a list of items.
2. **Splitting by topic.** A Sword maker and a Potion maker with the same brief are one role. Fix: split only when instructions, tools or policy differ.
3. **A job line with "and".** It hides two jobs. Fix: one verb per role.

## Try it

Not graded. Write your answer down before you read the answer.

A draft card says:

```text
Role:   Lore writer
Job:    Write each item description and translate it into French.
Tools:  none
```

1. Why is this card a warning sign?
2. Rewrite it as two roles.
3. Which role's output is the next role's input?

### Answer

1. **The job has two verbs: write and translate.** Writing and translating need different instructions, so they are two jobs.
2. **Two roles.** Lore writer: writes one English description per item id, returns plain text. Translator: turns each description into French, returns plain text. Neither role needs a tool.
3. **The Lore writer's.** Its English text is the Translator's Input field. Our habit: check the English text before it goes on, so a mistake is not translated too.

## Recap

- A role is a written brief. Each helper needs a goal, an answer format, advice on tools and sources, and clear limits. Without them, helpers repeat work and miss parts.
- Keep jobs narrow and tool lists small. Tool limits lower the chance of actions you did not want, and a missing tool list in the Claude SDK means every tool.
- Match the model to the role: try a smaller model on plain, rule-based roles, and count roles, not items.

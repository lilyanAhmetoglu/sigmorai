## Goal

After this lesson you can:

- Keep a team's facts in one record outside the chat, with one row per item and one writer per column.
- Pass files by name instead of pasting them through a chat.
- Restart a stopped run from the record, and keep secrets out of shared state.

## The problem

A small video team is making a 12-part online course. A lead agent plans the work. (An **agent** is a model that plans and uses tools on its own.) Helper agents write captions, find b-roll (extra background footage) and make thumbnails. A reviewer helper checks each lesson.

On Wednesday the team asks: "Which lessons are ready?" They get three answers:

- The lead agent says "8 of 12 done".
- The reviewer says lessons 4 and 9 failed.
- The caption helper says it never got the new script for lesson 6.

Then the lead agent's chat is closed by mistake. A new chat starts with nothing in it.

Nobody wrote the facts in one place. This lesson shows how to keep **shared state**: the facts the whole team reads and updates.

## The idea

### A model only knows what is in front of it

The [OpenAI Agents SDK docs on context](https://github.com/openai/openai-agents-python/blob/main/docs/context.md) (an SDK is a software kit for developers) split context into two kinds:

- context "available locally to your code"
- context "available to LLMs", which is "data the LLM sees when generating a response"

(An LLM, or large language model, is the model that reads and writes the text.) The docs say your own context object "is **not** sent to the LLM. It is purely a local object". The model sees only what you pass in.

The SDK's [sessions](https://github.com/openai/openai-agents-python/blob/main/docs/sessions/index.md) help with one thing. They "maintain conversation history across multiple agent runs". That is a chat log. It is not a list of what is done.

The [Claude Agent SDK docs](https://platform.claude.com/docs/en/agent-sdk/subagents) show the same limit for helpers. A fresh **subagent** (a helper agent started by a main agent) does not receive "The parent's conversation history or tool results".

Even a long chat has a ceiling. A model's **context window** is the most text it can hold at once. It is measured in **tokens**, small pieces of text. In the [Anthropic research system](https://www.anthropic.com/engineering/multi-agent-research-system), the lead agent saved its plan to memory, "since if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan."

So the rule is simple: **write down what matters, outside the chat.**

### The tracker

This template is ours. One row per item. The row id is the same id you use everywhere else, including in a batch.

| Column    | Example (made up)              | Who writes it   |
| --------- | ------------------------------ | --------------- |
| `id`      | `course-l06`                   | Lead            |
| Script    | approved, `l06-script-v2.md`   | Person          |
| Captions  | done, `l06-captions.srt`       | Caption maker   |
| Thumbnail | done, `l06-thumb.png`          | Thumbnail maker |
| Review    | FAIL, audio drops at 03:12     | Reviewer        |
| Notes     | lead: re-record planned Friday | Anyone, signed  |
| Sign-off  | waiting for Ana                | Person          |

### One writer per column

Many roles read the tracker. Trouble starts when two roles write the same cell.

The OpenAI docs show that shared, changing data is normal in one run. Your context object is for "your own mutable app state and dependencies". And nested agent-as-tool runs "do not get an isolated copy of your app state by default." In plain words: helpers in one run can touch the same data.

So we set the rule ourselves: **each column has one writer.** The reviewer writes Review. The caption maker writes Captions. If the lead disagrees with a review, it writes a signed line in Notes. It never changes the Review cell. Reading other columns is fine. Writing them is not.

### Pass file names, not pasted files

When helpers pass whole outputs through the lead's chat, details get lost. The Anthropic research post calls this the "game of telephone". Its fix has two parts:

- Helpers "store their work in external systems, then pass lightweight references back to the coordinator."
- This "prevents information loss during multi-stage processing and reduces token overhead from copying large outputs through conversation history."

A comparison: you send a colleague the link to a shared folder, not a photo of every page.

For the course: the thumbnail maker saves `l06-thumb.png` in the project folder and writes the name in the tracker. The reviewer opens the file from the folder.

### Facts that never change

Some facts are the same for all 12 lessons: the brand fonts, the intro music, the review rubric. Our advice: keep them in one read-only folder, a brand kit. Every role reads it. No role edits it. If a brand rule changes, a person changes it, and the lead marks the affected rows to redo.

### Restart from the record

The Anthropic post says that in long agent runs, "we can't just restart from the beginning: restarts are expensive and frustrating for users." Its team built systems that pick up at the point where the agent was when an error happened, and use "regular checkpoints".

The tracker is your checkpoint. A new lead reads it and carries on with the unfinished rows. With no tracker, you start again at lesson 1 and pay twice.

### Keep secrets out

The OpenAI docs warn: "Avoid putting secrets in `RunContextWrapper.context` if you intend to persist or transmit serialized state." That line is about their SDK. Our advice: treat any shared record the same way. Many roles and people read it, and it is kept. A password or upload key never goes in it. Give the one role that needs access its own limited key.

## Worked example

### Step 1: the change

On day 3 the client changes the brand font. Lessons 1 to 6 already have thumbnails. Lessons 7 to 12 do not.

### Step 2: the weak fix

The lead tells every helper in chat: "New font from now on."

The message lives in one chat. A helper started later never sees it. And nothing says which old thumbnails used the old font.

### Step 3: the better fix (our method)

A person updates the read-only brand kit and names it kit v2. The tracker gets one more column, written by the thumbnail maker:

```text
id          Thumbnail        Kit used
course-l05  l05-thumb.png    v1
course-l06  l06-thumb.png    v1
course-l07  -                -
```

### Step 4: the hard case

**The hard case is lesson 6.** It was started under v1 and saved after the change. The chat cannot say which font it has. The Kit used cell can, because the maker writes the version it read when it started. The lead marks every row with Kit used = v1 to redo, lesson 6 included.

### Step 5: why it is better

- **One place for the rule.** The change lives in the kit, and every role reads the kit.
- **A visible trail.** The tracker shows which items used the old rule.
- **Less rework.** Only the affected rows are redone.

## Common mistakes

1. **Announcing a rule change in a chat.** A helper started later never sees it. Fix: change the kit, version it, and record the version each item used.
2. **Free-text status.** "Mostly fine, see chat" tells the next role nothing. Fix: write a state (done, FAIL, waiting) and one reason.
3. **Letting helpers edit the brand kit.** One "improvement" changes every later item. Fix: keep the kit read-only; a person changes it.

## Try it

Not graded. Write your answer down before you read the answer.

Where does each fact belong: the **tracker**, the **read-only brand kit**, or **both**?

1. The rule "thumbnail text at least 60 px high".
2. "course-l08: captions done".
3. "The brand kit changed to v2 on day 3."

### Answer

1. **Brand kit.** It is the same for every lesson, and no role should change it.
2. **Tracker**, in the Captions column, written by the caption maker.
3. **Both.** The kit gets the new version, and each tracker row records the version it used.

## Recap

- A model knows only what is in front of it. Chat logs and sessions are history, not a record of what is done. Keep a tracker outside the chat.
- One row per item, one writer per column. Pass file names, not pasted files, and keep fixed rules in a read-only kit.
- The tracker is your checkpoint for a restart. Secrets never go in shared state.

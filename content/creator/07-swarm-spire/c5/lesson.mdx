## Why it matters

Your batch finished overnight. The producer says "all done". The checker says six ads failed. The visual maker says it never saw the new tagline. Who is right?

Nobody can say, because nobody wrote the facts in one place. A model does not remember your project. It knows only what is put in front of it right now. **Shared state** is the set of facts the whole team reads and updates: the brief, the approved copy, the status of each ad and where each file lives. This lesson shows how to keep it.

## A chat is not a project record

OpenAI's SDK docs split "context" into two kinds: context "available locally to your code", and context "available to LLMs", which is "data the LLM sees when generating a response". They add that your own context object "is not sent to the LLM." The model sees only what you pass in.

Sessions help with one thing. The SDK's session memory keeps "conversation history across multiple agent runs". That is a chat log. It is not a status board.

Claude's subagents show the same limit. A fresh subagent does not receive "the parent's conversation history or tool results". And even a long-running lead has a ceiling: in Anthropic's research system the lead saved its plan to memory, because if the context window "exceeds 200,000 tokens it will be truncated and it is important to retain the plan."

So the rule for a studio is simple: **write down what matters, outside the chat.**

## The status sheet

This template is ours. One row per item, and the row id is the same id you gave the request in the batch (Chapter 4).

| Column      | Example (made up)            | Who writes it |
| ----------- | ---------------------------- | ------------- |
| `id`        | `tea-de-9x16`                | Producer      |
| Copy        | approved, file `tea-de.txt`  | Localiser     |
| Image       | made, file `tea-de-9x16.png` | Visual maker  |
| Check       | FAIL, line 3                 | Checker       |
| Cost so far | $0.42                        | Producer      |
| Sign-off    | waiting for Mia              | Person        |

Look at the last column. A person's name in the sheet is how you know who still has to say yes.

## One writer for each column

Several roles read the same sheet. Two roles writing to the same cell is how "all done" and "six failed" both end up true.

OpenAI's docs show that shared, changing data is normal in a multi-agent run. Your context object holds "your own mutable app state", and every agent and tool in a run uses the same type of context. Nested agent-as-tool runs "do not get an isolated copy of your app state by default."

So we set the rule ourselves: **each column has one writer.** The checker writes "Check". The visual maker writes "Image". Nobody edits another role's column. If the producer disagrees with the checker, it adds a note. It does not overwrite the result.

## Pass links, not copies

Do the roles pass whole images through the producer's chat? Anthropic calls the loss of detail "the 'game of telephone'". Its fix: subagents "store their work in external systems, then pass lightweight references back to the coordinator." It says this "prevents information loss during multi-stage processing and reduces token overhead from copying large outputs through conversation history."

For a studio, the visual maker saves `tea-de-9x16.png` in the project folder. It tells the producer the file name. The checker opens the file from the folder. The image never has to travel through a chat.

## Inputs that never change

Some facts are the same for all fifty ads: the brand rules, the approved master, the rubric. Keep them in one read-only place, such as a brand kit folder. Brand kits were covered in Context Library. Every role reads from there. No role edits it. If the brand rules change, a person changes them, and the producer starts the affected items again.

## Resume from the record

Anthropic says that in long agent runs, "we can't just restart from the beginning: restarts are expensive and frustrating for users." Its systems "resume from where the agent was", and use "regular checkpoints".

Your status sheet is the studio's checkpoint. If the producer's chat is lost, a new one reads the sheet and carries on with the rows that are not done. With no sheet, you start again from item one, and you pay twice.

## Keep secrets out

OpenAI's docs warn: "Avoid putting secrets in `RunContextWrapper.context` if you intend to persist or transmit serialized state." That advice is about its SDK, but the idea is ours too. A shared sheet is read by many roles and people. Do not put a client's password in it. Give the one role that needs access a limited key, as Agent Citadel taught.

## What this means for your work

- **Do not rely on chat memory.** Write facts in a status sheet.
- **Use the same id in the batch and the sheet.**
- **Give every column one writer.**
- **Pass file names, not pasted files.**
- **Keep brand rules and the rubric in a read-only place.**
- **Never store passwords in shared state.**

## Goal

After this lesson you can:

- Write a budget table for a multi-agent job, with dated prices and a reserve, and add it up correctly.
- Set caps at three levels: each item, each batch and the whole run.
- Find the money limit in your agent tool, and write an effort rule into the brief.

## The problem

An audio studio is launching a 10-episode audio drama. For every episode, it needs a short written blurb and a square cover image. A lead agent runs the job and starts helper agents. (An **agent** is a model that plans and uses tools on its own.)

The producer says: "We have $15 for the whole season." The first test run looks like this:

- The lead agent started 9 helpers for one blurb.
- Each cover was tried 6 or 7 times, because nothing said when to stop.
- The bill for one episode was more than the season budget.

Nobody had written a number down before the run. This lesson shows how to plan the cost first, and how to put brakes on the run.

## The idea

### Helpers use more tokens

A **token** is a small piece of text. Models charge by the token. The [Anthropic post on its research system](https://www.anthropic.com/engineering/multi-agent-research-system) shares its own numbers: "In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats."

The post's conclusion: multi-agent systems need "tasks where the value of the task is high enough to pay for the increased performance."

Those are the post's own figures, not a rule for audio studios. Our reading: the direction is what matters. Every extra helper adds its own prompts and its own model calls.

### The budget table

This method is ours. Write one row for each kind of spend. Each row is **items × tries × price per try**.

Three rules make the table honest:

- **Count tries, not keepers.** If each cover gets 3 tries, you pay for 3 images, and you check 3 images.
- **Add an agent line.** The lead agent's own run costs money, and it is the line that moves most.
- **Add a reserve on top of the sum.** Write the percent down.

### Real prices, with dates

Take the price per try from the live pricing page, and write the date next to it. On 2026-10-11:

- [Google's pricing page](https://ai.google.dev/gemini-api/docs/pricing) lists Nano Banana 2.1 at "$0.0336 per 1K image" on Standard and "$0.0168 per 1K image" on Batch.
- [OpenAI's pricing page](https://developers.openai.com/api/docs/pricing) lists GPT Image 2.5 image output at $30.00 per 1M tokens on Standard and $15.00 on Batch.
- The [Claude batch docs](https://platform.claude.com/docs/en/build-with-claude/batch-processing) say: "All usage is charged at 50% of the standard API prices."

Prices change. The method does not.

### Why a reserve

The Claude batch docs also say: "Because of high throughput and concurrent processing, batches may go slightly over your Workspace's configured spend limit." So an account limit is not a wall for a batch. A reserve keeps a small overrun inside the client's number.

### Caps at three levels

Our view: one cap is not enough.

1. **Each item:** a maximum number of tries.
2. **Each batch:** a small test first, then the rest.
3. **The whole run:** a money limit that ends the work.

Tools differ here. In the [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/subagents) (an SDK is a software kit for developers), the docs say Claude "decides on its own when to spawn a subagent and how many to spawn". (A **subagent** is a helper agent started by another agent.) A subagent can start its own, "so one prompt can grow into a tree of agents." The docs list three caps:

- Depth: default "`3` layers of subagents below your main agent".
- Concurrency: default "`20` subagents running at once". This counts helpers, not money.
- Spend: default "No limit". You set it with `max_budget_usd` in Python or `maxBudgetUsd` in TypeScript.

At the spend cap, the SDK does three things:

- It "refuses to spawn more subagents".
- It "stops background subagents that are still running".
- It "ends the query with the `error_max_budget_usd` result subtype."

The docs add that "On earlier releases, some of these limits are missing or default differently", so check your version.

The [OpenAI Agents SDK](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md) has a different brake. The runner works in a loop: "We call the LLM for the current agent, with the current input." Then: "If we exceed the `max_turns` passed, we raise a `MaxTurnsExceeded` exception." (An exception is an error that stops the run.) It counts turns of that loop, not money. Neither SDK knows your client's budget.

Our advice: ask your tool's owner, "What is the money limit, and who set it?" If the answer is "none", the cap is you.

### Put an effort rule in the brief

The Anthropic research post says: "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts." Its examples:

- "Simple fact-finding requires just 1 agent with 3-10 tool calls"
- "direct comparisons might need 2-4 subagents with 10-15 calls each"
- "complex research might use more than 10 subagents with clearly divided responsibilities"

The post says these rules help "prevent overinvestment in simple queries". Write the same kind of rule into your lead agent's brief.

### Cheaper where it is easy

The [Anthropic post on building agents](https://www.anthropic.com/engineering/building-effective-agents) describes routing "easy/common questions to smaller, cost-efficient models". Our reading: use a smaller model for plain checks, keep the strong one for judgment, and test the cheap one first.

## Worked example

### Step 1: the weak line

```text
Covers   10 covers x "about 5 cents"   = $0.50
```

No page, no date, no tries, no mode.

### Step 2: price it from the page (2026-10-11)

Our plan: 3 tries per cover, so 30 images.

```text
Nano Banana 2.1, 1K, Standard   30 x $0.0336 = $1.008, about $1.01
Nano Banana 2.1, 1K, Batch      30 x $0.0168 = $0.504, about $0.50
```

### Step 3: the hard case

**The hard case is the second vendor.** OpenAI's pricing page lists GPT Image 2.5 image output at $30.00 per 1M tokens (Standard) and $15.00 (Batch). That is a price per token, not per image. The page says: "For image generation cost estimates, use the calculator in the image generation guide." Do not guess. Use the calculator, and write its number and the date.

### Step 4: who watches this line?

The Claude Agent SDK docs say the spend cap "Counts the call's own spend, subagent requests included". Our reading: a cover batch sent through another API is not in that count. So write down who watches it: a person or a script.

### Step 5: why it is better

- **Each price has a page and a date.**
- **Tries are in the count.**
- **A per-token price is not turned into a guess.**
- **Every line has someone watching it.**

## Common mistakes

1. **Prices with no date.** Fix: write the page and the date next to every price.
2. **Turning a per-token price into a guess.** Fix: use the vendor's calculator.
3. **Forgetting the lead agent's own run.** Fix: add an agent line; it is the line that moves most.

## Try it

Not graded. Write your answer down before you read the answer.

The studio wants 200 cover variations for a poster contest, using Nano Banana 2.1 at 1K. Use the prices listed above from 2026-10-11.

1. What do 200 images cost on Standard?
2. What do they cost on Batch?
3. What must you write next to these numbers in the budget?

### Answer

1. **$6.72.** Our maths: 200 × $0.0336 = $6.72.
2. **$3.36.** Our maths: 200 × $0.0168 = $3.36. That is half the Standard price.
3. **The date and the page.** Prices change, so write "Google pricing page, 2026-10-11" next to them, and check the page again before the run.

## Recap

- Plan the money before the run: items × tries × price for every line, an agent line, and a written reserve. Add it up yourself.
- Cap each item, each batch and the whole run. The Claude Agent SDK has no spend limit by default, and OpenAI's `max_turns` counts turns of the agent loop, not money.
- Agents are poor at sizing their own effort, so write scaling rules into the brief, and use smaller models for plain checks.

## Goal

After this lesson you can:

- Read a job's status and say which jobs have a file ready, which are still working, and which ended badly.
- Plan delivery times from the vendors' own time ranges.
- Choose between checking jobs again and again (polling) and being told when they finish (a webhook).

## The problem

A florist wants five short video clips for Mother's Day. Your studio submits them on Thursday evening. On Friday morning, the producer opens the job list, sees no red errors, and writes to the client: "All five clips are done, you'll have them at 10:00."

At 09:30 the editor finds only two video files. One job is still waiting in a queue. One ended with a failure. One was cancelled by a teammate. The producer read "finished" as "successful", and "no error" as "done".

Video takes minutes, not seconds. So the vendors treat it as a **job**, not an instant answer. This lesson shows how to read a job.

## The idea

### A job is a ticket

Think of a dry cleaner. You hand in the coat, you get a ticket, and you come back later. Slow generation works the same way:

```text
1. submit   -->  2. get an id (no file yet)
                        |
                        v
                 3. check the id until it is finished
                        |
                        v
                 4. if it succeeded, pick up the result
```

The vendors say it like this:

- **Google (Veo).** The [Veo docs](https://ai.google.dev/gemini-api/docs/veo) say a request "starts a long-running job and immediately returns an `operation` object". You check it until its `done` field is true.
- **Runway.** The [Runway primer](https://docs.dev.runwayml.com/ai-context.md) says that, with few exceptions, the request that starts the work does not give you the output. You get a task id. Then you check `GET /v1/tasks/{id}`.
- **OpenAI.** [Background mode](https://developers.openai.com/api/docs/guides/background) is for long text and reasoning tasks, not video. It uses the same idea: it starts the task "asynchronously", and you check the response object over time.

Checking again and again is called **polling**. The Runway primer says to poll "with backoff rather than a tight loop". Backoff means you wait longer between checks as time goes on. A tight loop asks many times a second, which only floods the service with requests.

### Reading the status

A Runway task has six states:

| Status      | What it means                                           | File ready? |
| ----------- | ------------------------------------------------------- | ----------- |
| `PENDING`   | waiting to start                                        | no          |
| `THROTTLED` | waiting behind your rate limit; it will start by itself | no          |
| `RUNNING`   | being made now                                          | no          |
| `SUCCEEDED` | finished well                                           | **yes**     |
| `FAILED`    | finished badly; has `failure` and `failureCode` fields  | no          |
| `CANCELLED` | stopped before the end                                  | no          |

The primer is clear on three points:

- "Only `SUCCEEDED` carries an `output` array." No other state has a file.
- `FAILED` has two fields: `failure` is text for people, `failureCode` is for software.
- A `THROTTLED` task is fine. It is queued behind your rate limit and "will proceed on its own".

One more word: **terminal**. The OpenAI docs say that when a background job leaves the `queued` or `in_progress` state, it has reached a "final (terminal)" state. Terminal means finished. It does not mean successful. In Runway terms, `SUCCEEDED`, `FAILED` and `CANCELLED` are all finished, and only one of them gives you a file.

### How long is "a while"?

Use the vendors' numbers, not a guess:

| Job                          | What the docs say                                                      |
| ---------------------------- | ---------------------------------------------------------------------- |
| Veo video                    | latency "Min: 11 seconds; Max: 6 minutes (during peak hours)"          |
| OpenAI image, complex prompt | "may take up to 2 minutes"                                             |
| Runway generation            | "anywhere from seconds to minutes depending on the model and duration" |
| Gemini image batch           | higher rate limits, but a "turnaround of up to 24 hours"               |

The Veo docs also say: "the higher the resolution, the higher the latency will be." So a job that is still running after a few minutes is often normal. And a batch is for work that can wait a day, not for a meeting tomorrow morning.

### Poll, or be told

Polling is simple. The other way is a **webhook**: the vendor sends a message to your system when the job ends. The [OpenAI webhooks docs](https://developers.openai.com/api/docs/guides/webhooks) list events such as "a batch completes" or "a background response is generated". Three details:

- Your system should answer fast with a success code (`2xx`). Slow work happens later.
- If it does not answer, OpenAI tries again "for up to 72 hours with exponential backoff".
- The OpenAI docs say it "may deliver duplicate" copies of one event. The `webhook-id` header lets you spot the copy and ignore it. Two messages with one `webhook-id` are one event, not two jobs.

### Stopping a job

The Runway primer says `DELETE /v1/tasks/{id}` "cancels an in-progress task". The OpenAI background-mode docs show how to cancel a response that is still running. Cancel only what you really do not need.

## Worked example

### Step 1: the weak report

The producer's Friday note:

```text
Florist clips: all 5 done, no errors. Delivery 10:00.
```

### Step 2: read each job

```text
clip-1  Runway  SUCCEEDED   -> file ready, download it now
clip-2  Runway  SUCCEEDED   -> file ready, download it now
clip-3  Runway  THROTTLED   -> not an error; waiting for the rate limit
clip-4  Runway  FAILED      -> read "failure" and "failureCode"
clip-5  Runway  CANCELLED   -> stopped by a teammate; no file
```

### Step 3: the hard case

The hard case is clip-3. It looks stuck, and a teammate wants to delete it and submit it again. But `THROTTLED` only means waiting. The task is in the queue and will start by itself. A new copy would wait behind the same rate limit, so resubmitting gains nothing and wastes the place it already has. The right move is to leave it and keep checking with backoff.

Clip-4 is different. It ended. Waiting will not change it. Read the failure fields, then decide.

### Step 4: the good report

```text
Florist clips, Friday 08:15
  Ready now:   clip-1, clip-2 (downloaded to /florist/final/)
  In queue:    clip-3 (THROTTLED, will run on its own)
  Failed:      clip-4 (reason in failureCode; fix and resubmit)
  Cancelled:   clip-5 (resubmit if still wanted)
  New promise: 2 clips at 10:00, the rest by 14:00
```

### Step 5: why it is better

- **"Finished" and "successful" are kept apart.** Only `SUCCEEDED` jobs count as files.
- **The queue is respected.** The throttled clip is left alone.
- **The promise uses real numbers.** The new time leaves room for queues, a rerun and a review.

## Common mistakes

1. **Counting finished jobs as delivered files.** Fix: count only the jobs whose status says success, and check that the file is saved.
2. **Cancelling a throttled job.** Fix: leave it in the queue. It runs by itself when your limit allows.
3. **Treating two webhook messages as two jobs.** Fix: compare the `webhook-id`. If it is the same, it is one event delivered twice.

## Try it

Not graded. Write your answer down before you read the answer.

A teammate builds a small checker for 300 overnight Veo clips. It asks "is it done?" for every clip, every half second, all night. In the morning, a client meeting at 09:00 needs ten of those clips.

Name two problems with this plan.

### Answer

1. **A tight loop.** Asking every half second floods the service. Fix: wait longer between checks (backoff), or use a webhook, so the system is told when each job ends.
2. **Must-have clips are mixed into the big overnight run.** Each Veo clip can take up to 6 minutes at peak hours. Fix: run the ten meeting clips first, as their own jobs, and leave time to review them.

## Recap

- Slow generation is a job: submit, get an id, check it, then pick up the result. "Submitted" is not "done".
- Finished (terminal) can mean success, failure or cancelled. Only a successful job has a file. `THROTTLED` is a queue, not an error.
- Plan with the vendors' time ranges. Check with backoff, or let a webhook tell you, and treat a repeated `webhook-id` as one event.

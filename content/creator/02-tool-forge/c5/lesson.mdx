## Goal

After this lesson you can:

- Sort a failed request into one of three groups: change the request, wait and retry, or fix the account.
- Plan a safe retry: growing pauses, a little randomness, and a limit on tries and time.
- Check what a failure costs before you retry many jobs at once.

## The problem

A podcast network makes 60 episode covers and 12 short promo clips in one night. In the morning, 9 jobs have failed. A developer writes a script: "retry every failed job, every 2 seconds, until it works". He also wraps it around the vendor's own client library.

By lunch, nothing new has worked. Some jobs failed the same way again and again. One vendor account is close to suspension for too many blocked requests. The team paid credits for some failures twice. And the request count is much higher than anyone planned.

Retrying is not a fix. It is one of three different answers. This lesson shows how to pick the right one.

## The idea

### Three groups of failures

Think of a letter that comes back from the post office. If the address is wrong, sending it again changes nothing: you fix the address. If the post office was closed, you try again tomorrow. If you had no stamp, you buy a stamp first.

```text
failure
  |-- the request is wrong   -> CHANGE the request, then send   (no plain retry)
  |-- the service is busy    -> WAIT, then send again slowly    (retry is fine)
  |-- the account is blocked -> FIX credits, limits or the key  (no retry until fixed)
```

This sorting is ours, not a vendor rule. The vendor docs say which errors go where.

### Group 1: change the request

These failures come from your prompt, your input or a setting.

- **OpenAI.** The [image docs](https://developers.openai.com/api/docs/guides/image-generation) say some failures are "user-correctable" with `error.type = "image_generation_user_error"`, for example `moderation_blocked`. They say: "Don't automatically retry these errors without modifying the prompt or input images."
- **Runway moderation.** The [task failures page](https://docs.dev.runwayml.com/errors/task-failures) says a `SAFETY.INPUT.*` code means an input was rejected, and: "You should not retry these generations." The last part of the code is only a hint. `SAFETY.INPUT.TEXT` points to the prompt text, but the page says to "treat these as diagnostic messages only".
- **Runway bad inputs.** `ASSET.INVALID` is "often" about "the dimensions, duration, or other properties" of your file.
- **Plain 400 errors.** The [Runway error table](https://docs.dev.runwayml.com/errors/errors) marks `400` as not safe to retry. The [Gemini troubleshooting page](https://ai.google.dev/gemini-api/docs/troubleshooting) says: "Do not retry on client errors (like `400`, `402`, or `403`)". The [Claude docs](https://platform.claude.com/docs/en/api/errors) call a 400 a problem "with the format or content of your request".

One Runway code sits in between: `INTERNAL.BAD_OUTPUT.01`. The name sounds like a server problem, but the common causes are in your request:

- "Logos, watermarks, or overlaid text in input media"
- a prompt with explicit requests to generate text
- a prompt that asks for a media prompt to be written, instead of giving one

The page says you "may retry" these, and they "may succeed if corrections were made". So: fix first, then retry.

### Group 2: wait, then retry

These failures mean the service is busy for a short time.

- **OpenAI** ([rate limits](https://developers.openai.com/api/docs/guides/rate-limits)): for a `429` or a `503`, "Follow `Retry-After` when it's present". That header tells you how many seconds to wait.
- **Gemini**: retry errors such as `429 RESOURCE_EXHAUSTED` and `503 UNAVAILABLE`.
- **Claude**: `529` means "The API is temporarily overloaded."
- **Runway**: `429`, `502`, `503` and `504` may be retried. For `THIRD_PARTY.UNAVAILABLE`, you "may wait and retry".

How to wait:

- **Backoff.** Wait a little, then longer after each failure. The Gemini page gives an example: 1 second, then "2s, 4s, 8s".
- **Jitter.** Add a small random delay, so that many apps do not hit the service in the same second. The Runway docs say: "add a random delay of up to 50%".
- **A cap.** The OpenAI docs say: "Limit both the number of attempts and the total time spent retrying."

Fast retries make things worse. The OpenAI docs warn: "unsuccessful requests contribute to your per-minute limit, so continuously resending a request won't work."

### Group 3: fix the account

The status number is not enough. Read the code too. A `429` can mean "busy" or "no money".

- **OpenAI** ([error codes](https://developers.openai.com/api/docs/guides/error-codes)): the code `credit_balance_exhausted` on a `429` means no prepaid credits are left. The page says: "Retrying billing, spend, or quota errors won't restore API access." Top up the credits, or raise the limit, before you send again.
- **Claude**: a `429` from a monthly spend cap "has no `retry-after` header and keeps failing until access resumes".
- **Runway**: `401` means "The provided API key is not valid." Not safe to retry.

### Does a failure cost money?

Check this before any bulk retry. The rules differ:

- **Runway**: "Moderated generations have the same credit cost as successful generations." And for `SAFETY.INPUT.*`, "credits are not refunded". Too many moderated requests can get your account suspended.
- **Veo 3.1**: the [Veo docs](https://ai.google.dev/gemini-api/docs/veo) say it sometimes blocks a video because of the audio, and "You will not be charged if your video is blocked from generating."

So retrying a blocked prompt on Runway pays again for the same rejection.

### Retries may already be on

Client libraries (SDKs) often retry for you:

- The Claude docs: the SDK retries transient failures "twice by default".
- The OpenAI docs: each official SDK "automatically retries eligible `429` and `503` responses".
- The Gemini docs: the official SDKs include "automatic retry logic with exponential backoff by default".

If you add your own loop around them, the tries multiply. The OpenAI docs say to "disable SDK retries or account for them" in your limits, "so nested retry loops don't multiply requests". Example: 3 SDK tries inside 5 tries of your own can send 15 requests for one job.

## Worked example

### Step 1: the weak plan

```text
For every failed job:
  retry every 2 seconds until it works
  (inside the SDK, which also retries)
```

### Step 2: sort the 9 failures

```text
cover-07  OpenAI image  image_generation_user_error / moderation_blocked
cover-19  Runway        FAILED  SAFETY.INPUT.IMAGE
cover-33  Runway        FAILED  ASSET.INVALID
promo-02  Runway        FAILED  INTERNAL.BAD_OUTPUT.01
                        (prompt: "write a prompt for a neon studio scene")
promo-05  Runway        HTTP 503
promo-08  Gemini        429 RESOURCE_EXHAUSTED
promo-09  Claude        529 overloaded_error   (script writing step)
cover-41  OpenAI        429 organization_spend_limit_exceeded
promo-11  Runway        FAILED  THIRD_PARTY.UNAVAILABLE
```

```text
CHANGE   cover-07  rewrite the prompt or change the input image
         cover-19  replace the input image; do not resend as is
         cover-33  fix the file size, length or shape
         promo-02  give the scene prompt directly, then retry
WAIT     promo-05, promo-08, promo-09, promo-11
         backoff + jitter, max 4 tries or 10 minutes
FIX      cover-41  raise the spend limit or add credits first
```

### Step 3: the hard case

**The hard case is promo-02.** Its code starts with `INTERNAL`, so the developer put it in "wait". But the Runway docs list "write a prompt for..." requests as a common cause. A plain retry repeats the same mistake. Fix the prompt first. Then a retry is allowed and may work.

### Step 4: the good plan

```text
1. Sort first. Never retry a CHANGE or FIX job unchanged.
2. WAIT jobs: follow Retry-After if present; else 1s, 2s, 4s, 8s
   plus a random extra of up to 50%. Stop after 4 tries or 10 min.
3. Our loop only, with SDK retries off (or counted in the cap).
4. Before resending Runway jobs, remember: moderated jobs cost credits.
```

### Step 5: why it is better

- **Each failure gets the right answer.** Nothing is sent again unchanged when the request was the problem.
- **The load stays low.** Backoff, jitter and a cap stop a flood of requests.
- **No hidden multiplier.** One retry loop, with a known maximum.
- **Money is checked.** Blocked prompts are fixed before they are paid for again.

## Common mistakes

1. **Retrying a rejected prompt as is.** It fails again, and on some services it costs again. Fix: change the prompt or input first.
2. **Reading only the status number.** A `429` can mean "too fast" or "no credits". Fix: read the error code and message too.
3. **Stacking your own loop on the SDK's loop.** Requests multiply. Fix: turn one loop off, or count both in one limit.

## Try it

Not graded. Write your answer down before you read the answer.

Put each failure in a group (change, wait or fix), and say the next step:

```text
a) Gemini 400, bad syntax in the request body
b) Claude 529 overloaded_error
c) Runway 401
d) Runway FAILED INTERNAL.BAD_OUTPUT.01, the input poster has a big title text on it
```

### Answer

- **a) Change.** A 400 is a client error. Fix the request body, then send it.
- **b) Wait.** The API is temporarily overloaded. Send again after growing pauses, with jitter, and stop after a few tries.
- **c) Fix.** The API key is not valid. Replace the key. Retrying will not help.
- **d) Change, then retry.** Overlaid text in the input is a common cause. Use a version without the title, then retry.

## Recap

- Sort first: change the request, wait, or fix the account. Read the error code, not only the number.
- Retry only busy errors. Use growing pauses and jitter, and set a maximum for tries and for time. Fast resending counts against your limit.
- Check the cost of failures, and check what the SDK already retries, so loops do not multiply.

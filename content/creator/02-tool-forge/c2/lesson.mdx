## Goal

After this lesson you can:

- Explain who runs a tool: the model only asks, and your app or the vendor does the work.
- Write tool names and descriptions that lead the model to the right tool with the right values.
- Decide which tools need a person to approve each call, and which can run freely.

## The problem

A stationery shop adds a chat assistant to its website. Couples use it to design wedding invitations. The assistant has three tools: one makes a card design, one changes it, and one orders the printed cards.

In the first week:

- A couple asked for "a card with our names". The card came back in landscape. They wanted portrait. Nobody asked them.
- A couple loved a design and said "make the gold a bit softer". The assistant made a brand new card. The approved design was gone from the screen.
- One couple typed "looks great!" and the assistant placed a print order for 150 cards.

The model is not broken. The tools were designed badly. This lesson shows how tools work in a chat, so you can design them well.

## The idea

### The model asks, something else does the work

A **tool** is a small service the assistant can call: make an image, save a file, send an order. All three vendors describe the same loop:

- The [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) say the model looks at what the user asked and at the tool's description, then decides whether to call it. It returns a structured call. For your own tools, "your application executes" it.
- The [OpenAI docs](https://developers.openai.com/api/docs/guides/function-calling) describe the same steps: the model returns a tool call, your app runs the code, and you send the output back.
- The [Gemini docs](https://ai.google.dev/gemini-api/docs/function-calling) are the clearest: "The model _doesn't_ execute the function itself."

```text
user  -->  model: "call make_card(style=..., shape=...)"
                         |
                         v
           your app (or the vendor) runs it
                         |
                         v
           result goes back --> model answers the user
```

Some tools are run by the vendor. The Claude docs call them **server tools**, which Anthropic runs on its own side. OpenAI calls them **built-in tools**, and image generation is one. Either way, the model still only asks. Your app runs your own tools. The vendor runs its built-in or server tools.

### Names and descriptions steer the choice

The model reads each tool's name and description to choose. So the description is a brief for the model, like a brief for a freelancer.

- The Gemini docs: "Be clear and specific." Use descriptive names without spaces.
- The OpenAI docs: "Write clear and detailed function names, parameter descriptions, and instructions."

Two tools with fuzzy descriptions, like "makes a card" and "does card stuff", leave the model to guess which one fits. It may call a tool at the wrong moment, or never call it at all.

### Missing values get guessed

What if a tool needs a value the user never gave? The Claude docs give an example with a weather tool and no city. The model "might guess values" that nobody gave it. The docs add: "This behavior is not guaranteed". So you cannot rely on the model to ask. Put it in the design: the description says the value must come from the user, and the assistant asks when it is missing.

### Make or change

The image tool in OpenAI's Responses API can make a new image or edit one already in the chat. Its `action` setting decides: `auto` lets the model choose, `generate` or `edit` forces one. The docs say: "If not specified, the default is `auto`." Other tools work the same way: with the default `tool_choice` of `auto`, the model decides on each turn whether to call a tool at all (Claude and OpenAI docs).

### Check the call, then guard the risky ones

A tool call is a request, not a promise that the request is sensible. The Gemini docs list validation as a best practice: check each function call before you run it. Your app checks the values against what is allowed before it runs anything.

Then sort tools by what a wrong call does. This split is our rule, not a vendor rule:

- **Make tools** create drafts: make, change, resize. A wrong call wastes a minute. Let them run.
- **Send tools** reach the outside world: order, email, publish, pay. A wrong call costs money or reaches a customer. Put a person in front of every call.

### Tools cost tokens on every turn

Every request carries the full tool list. The Claude docs say the `tools` parameter adds input tokens: the tool names, their descriptions and their schemas. The OpenAI docs say function definitions "are billed as input tokens". More tools with longer descriptions means a higher cost for every turn, even turns where no tool is called.

## Worked example

### Step 1: the weak tool list

```text
make_card     "Makes a card."
              inputs: prompt, shape (required)
edit          "Card stuff."
              inputs: request
order_prints  "Orders the cards."
              inputs: quantity
```

What goes wrong:

- `shape` is required, but nothing says it must come from the couple. The model guessed landscape.
- `edit` has a vague name and a vague description, so the model could not tell it apart from `make_card`.
- `order_prints` runs as soon as the model calls it. "Looks great!" was enough.

### Step 2: rewrite the names and descriptions

```text
make_card      "Creates a NEW invitation design from scratch. Use only
                when the couple asks for a new design. Ask the couple
                for the shape (portrait or landscape) if they have not
                said it. Never choose the shape yourself."
               inputs: prompt, shape: portrait | landscape (required)

change_card    "Changes the design the couple is looking at now. Use
                for every small change: colours, fonts, wording."
               inputs: instruction
```

### Step 3: the hard case

The hard case is the print order. Good descriptions are not enough here. Even a perfect description cannot stop the model from reading "looks great!" as "order now". The call has a real cost: 150 printed cards.

```text
order_prints   "Prepares a print order for the approved design.
                The order is NOT sent until the couple confirms
                on the order screen."
               inputs: design_id, quantity
App rule:      the app checks design_id exists and quantity is
               between 10 and 500, then shows a confirm button.
               Only a click by the couple sends the order.
```

### Step 4: why it is better

- **Who runs what is clear.** The model asks. The app checks the values, then runs `make_card` and `change_card` freely.
- **The right tool gets picked.** "New design" and "change the current design" are now different in name and in description.
- **No guessed shape.** The description tells the model to ask.
- **The send tool has a person in front of it.** The model can prepare an order. Only a person can send it.
- **Short list.** Three tools, not ten, so each turn costs fewer input tokens.

## Common mistakes

1. **Thinking the model runs the tool.** Then nobody owns the checks. Fix: your app (or the vendor, for built-in tools) runs it, so your app validates every call first.
2. **Two tools with blurry descriptions.** The model picks the wrong one. Fix: say what each tool is for and when to use it, in plain words.
3. **The same approval rule for every tool.** Approving every draft slows the work. Approving nothing lets a bad order out. Fix: run make tools freely and put a person before every send tool.

## Try it

Not graded. Write your answer down before you read the answer.

A podcast studio gives its assistant these tools:

```text
make_cover      "Image tool."               inputs: prompt, size (required)
upload_episode  "Uploads the episode to all podcast apps."
                                             inputs: file, title
```

Find two problems and fix each one.

### Answer

1. **`make_cover` has a vague description, and `size` can be guessed.** Fix: "Creates a NEW square cover image. Ask the host for the size if they have not given it."
2. **`upload_episode` is a send tool with no person in front of it.** It publishes to the world. Fix: the app shows the title and file, and the host clicks to confirm.

## Recap

- The model only asks for a tool call. Your app runs your tools. The vendor runs its built-in or server tools. Your app checks each call before it runs.
- Names and descriptions steer the choice. Make them specific, and say which values must come from the user, or the model may guess.
- Let make tools run, put a person before send tools, and keep the tool list short: definitions cost input tokens on every turn.

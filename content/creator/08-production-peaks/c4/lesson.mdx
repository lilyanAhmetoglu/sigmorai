## Goal

After this lesson you can:

- Name the meters a vendor uses to limit you, and say where each limit lives.
- Tell a rate-limit error apart from a spend cap and an overload.
- Write a retry plan that waits when waiting helps, and stops when it does not.

## The problem

Driftwood is an animation studio. One client job uses three APIs (services your tools call): a Claude model writes panel descriptions, a Gemini model makes still frames, and an OpenAI model writes captions.

Before the job starts, the lead writes one rule for the money errors of all three:

```text
If an error mentions spend or a usage limit: stop the whole job.
```

The rule sounds careful. But the vendors do not use the word "spend" the same way. On one of them, this rule stops the job for an error that clears in minutes.

## The idea

### A limit is a set of meters

A **rate limit** is a cap on how much you can send in a stretch of time. Every vendor uses several meters at once.

| Meter | Counts                   | Named in the docs of   |
| ----- | ------------------------ | ---------------------- |
| RPM   | requests per minute      | OpenAI, Claude, Gemini |
| TPM   | tokens per minute        | OpenAI, Gemini         |
| ITPM  | input tokens per minute  | Claude                 |
| OTPM  | output tokens per minute | Claude                 |
| RPD   | requests per day         | OpenAI, Gemini         |
| IPM   | images per minute        | OpenAI, Gemini         |

A token is a small piece of text, roughly part of a word.

- The [Gemini docs](https://ai.google.dev/gemini-api/docs/rate-limits) say: "Your usage is evaluated against each limit, and exceeding any of them will trigger a rate limit error."
- The [OpenAI docs](https://developers.openai.com/api/docs/guides/rate-limits) say limits can be hit "depending on what occurs first".
- The Gemini docs add that limits are "more restricted for experimental and preview models". Gemini counts IPM only for models that can make images.

A comparison: a car has a speed limit, a fuel tank and a driving-hours rule. Any one of them can stop the trip.

### Where a limit lives

- **OpenAI:** limits are set "at the organization level and at the project level, not user level".
- **Claude:** the [Claude docs](https://platform.claude.com/docs/en/api/rate-limits) say limits apply to the organization, and you may set your own limits for workspaces.
- **Gemini:** "Rate limits are applied per project, not per API key." Requests-per-day quotas (fixed daily allowances) "reset at midnight Pacific time".

For tests, the [OpenAI production guide](https://developers.openai.com/api/docs/guides/production-best-practices) suggests a staging project (a test copy) apart from the live one, so you can "set custom rate and spend limits per project".

### Pace and ramp

The Claude docs describe a token bucket:

- Capacity "is continuously replenished up to your maximum limit, rather than being reset at fixed intervals".
- A rate of 60 requests per minute "might be enforced as 1 request per second".
- So "Short bursts of requests can exceed the limit".

Limits also watch how fast traffic grows:

- **OpenAI:** a `slow_down` error "can occur even when your traffic is within its requests-per-minute and tokens-per-minute limits". Once traffic reaches 1 million input tokens per minute, raise it "by no more than 50% every 15 minutes".
- **Claude:** a sharp rise can trip an acceleration limit. The docs say: "ramp up your traffic gradually and maintain consistent usage patterns."

### Money stops traffic too

- **OpenAI** has two controls. A spend alert "Sends a notification; API traffic continues". With a hard spend limit, "Affected API requests return a `429` error". A `429` is the status code vendors return for a rate-limit error.
- **Claude** has a monthly spend cap (the most an organization may spend on the API in a month) per tier. A tier is a level that rises as you use and pay more. At the cap, the [Claude errors page](https://platform.claude.com/docs/en/api/errors) says the `429` "has no `retry-after` header and keeps failing until access resumes". The rate-limits page adds that its `error_code` is `enforced_spend_limit_reached`. A lower spend limit you set yourself returns a `400` error instead.
- **Gemini** has spend-based limits over a rolling 10-minute window. If you hit one, you get a `429 RESOURCE_EXHAUSTED` error, and the docs say "Wait and retry after a short period."

### Which errors are worth a retry

A **retry** sends the same request again. **Backoff** means you wait a little longer after each failed try. **Jitter** is a small random extra wait, so many scripts do not retry at the same second. A **header** is an extra line of data on a reply. An **SDK** is the vendor's code library.

- **A rate-limit `429`** usually says when to try again. The Claude API sends `retry-after`. The OpenAI docs say to treat `Retry-After` as a minimum, "and add a small random delay".
- **No header?** The OpenAI docs say: "fall back to exponential backoff with jitter. Limit both the number of attempts and the total time spent retrying."
- **An overload** is about the vendor's traffic, not your limit: `529` on Claude, `503` with `server_is_overloaded` on OpenAI.
- **An error that needs a person:** the OpenAI docs say: "Don't retry quota, billing, or other errors that require you to take action."

Two more facts matter for scripts:

- The Claude SDK already "retries transient failures", "twice by default, honoring the `retry-after` header when present".
- The OpenAI docs warn that "unsuccessful requests contribute to your per-minute limit, so continuously resending a request won't work".

## Worked example

### Step 1: the weak rule

```text
If an error mentions spend or a usage limit: stop the whole job.
```

### Step 2: list each vendor's money errors

Our table, built from the pages above:

```text
Vendor  What comes back                            What the docs say
Claude  429 rate_limit_error, no retry-after,      monthly spend cap: keeps failing
        error_code enforced_spend_limit_reached    until access resumes
Claude  400 "You have reached your specified       your own limit: raise or remove it
        API usage limits"                          to get access back sooner
OpenAI  429 at a hard spend limit                  affected requests return 429
Gemini  429 RESOURCE_EXHAUSTED, spend-based        rolling 10-minute window:
                                                   "Wait and retry after a short period."
```

### Step 3: the hard case

**The hard case is the Gemini row.** It is a spend limit, so the weak rule stops the job. But the limit is counted over a rolling 10-minute window. The Gemini docs say to wait and retry after a short period, and to reduce the rate of expensive requests. Stopping the whole job here loses hours for a pause of minutes.

### Step 4: the better rule

```text
Claude 429 + enforced_spend_limit_reached   stop the job, tell the lead
Claude 400 "specified API usage limits"     stop; the lead decides whether to raise it
Gemini 429 RESOURCE_EXHAUSTED (spend)       pause a few minutes, slow the expensive
                                            requests, retry; tell the lead if it repeats
Every failed call                           log the request ID
```

Our note: the OpenAI rate-limits page does not show how a hard-limit `429` differs from a rate-limit `429`. Read OpenAI's spend-limits guide before you write that row.

### Step 5: why it is better

- **Each row comes from that vendor's page.** The same word gets different actions.
- **A wait where the docs say wait.** The Gemini pause costs minutes, not the day.
- **A stop where only a person can help.** The Claude cap and your own limit go to the lead.

## Common mistakes

1. **Copying one vendor's error rule to another.** "Spend" means a monthly cap on Claude and a 10-minute window on Gemini. Fix: write each row from that vendor's page.
2. **Sizing a big job on a preview model.** The Gemini docs say limits are "more restricted for experimental and preview models". Fix: check the limits for the exact model first.
3. **Not logging request IDs.** For a Claude `500` that persists, the Claude docs say to "contact support with the request ID". Fix: log the request ID of every failed call.

## Try it

Not graded. Write your answer down before you read the answer.

In Driftwood's job, 4,500 of the 5,000 input tokens in every request are the same style guide. A teammate turns on prompt caching, so the model stores that part and reuses it.

The Claude docs say: "For most Claude models, only uncached input tokens count toward your ITPM rate limits."

1. After the cache is written, about how many input tokens per request count toward ITPM?
2. Does the first request, the one that writes the cache, count in full?
3. Is this true for every Claude model?

### Answer

1. **Our maths: about 500.** Only the uncached part counts.
2. **Yes.** The docs say tokens being written to the cache count toward ITPM.
3. **No.** The docs name Claude Haiku 3.5 (retired, except on Google Cloud) as a model that also counts cached reads (`cache_read_input_tokens`) toward ITPM. Check the page for your model.

## Recap

- A limit is several meters at once, set per organization or project. Any one meter can stop you.
- Rate limits and overloads are worth a wait and a retry: follow the header, add jitter, cap tries and total time.
- Some errors need a person, not a retry: a Claude spend-cap `429` has no `retry-after` and keeps failing. Read the error body, not only the code.

## Goal

After this lesson you can:

- Write an incident plan row with a trigger, a first action and a named owner.
- Put "stop the harm" before "find the cause", and say when the order of a key change flips.
- Keep a watch list of the exact models you use, and turn each vendor's shutdown date into your own switch-by date.

## The problem

Kiln is a small studio that makes short product videos for online shops. Three AI tools run its business:

- a video pipeline on the Gemini API
- a caption script on the Claude API
- a "mood board" web tool where clients type ideas and get images from an OpenAI model

The studio's whole incident plan is one line in the team wiki. Its list of tools is one more line:

```text
If anything breaks, post in #general. Whoever sees it, fixes it.
Tools: Veo, Claude, OpenAI images.
```

An **incident** is something going wrong in production (the live work clients see), while the clock runs. On Monday, October 5, 2026, a client asks: "Will your video pipeline still work for our campaign at the end of the month?" Nobody at Kiln can answer.

## The idea

### Five steps for any incident

This frame is ours, not a vendor's.

```text
1 Spot     how will we hear about it?
2 Contain  stop the harm: pause, revoke, switch off
3 Fix      replace the asset, the key or the tool
4 Tell     who must know, and who tells them
5 Learn    change the plan so it is less likely next time
```

Contain comes before fix. Pausing a bad ad takes a minute. Finding why it went wrong can take a day, and the harm keeps going while you look. A comparison: in a kitchen fire you turn off the gas first. You find out who left the pan on later.

Each row of the plan has a trigger, a first action, a next step and one named owner. An example row (ours):

```text
Trigger: a limit stops the pipeline | First: pause new orders, tell clients
Then: find the meter that ran out    | Owner: Theo
```

### Spot: plan how you will hear

The [Gemini safety guidance](https://ai.google.dev/gemini-api/docs/safety-guidance) says: "No matter how much you test and mitigate, you can never guarantee perfection, so plan upfront how you'll spot and deal with problems that arise." It suggests a monitored channel where users can share feedback.

The [OpenAI safety guide](https://developers.openai.com/api/docs/guides/safety-best-practices) says users should have an easy way to report problems, such as a listed email address. That method "should be monitored by a human and responded to as appropriate". Our reading: if no one has the job of reading it, nobody really watches it.

### Contain: a leaked key

An API key is the password your tools use to call a vendor. The OpenAI safety guide says: "If you believe an API key has been exposed, misused, or otherwise compromised, revoke it promptly and replace it with a new key."

The [OpenAI production guide](https://developers.openai.com/api/docs/guides/production-best-practices) also describes the normal, calm change of a key, called **rotation**: "Before a key expires, create a replacement, update your applications to use it, and revoke the old key once you've verified that the replacement works."

```text
Normal rotation:  new key -> update apps -> revoke old
Leak:             revoke old now -> new key -> update apps
```

In a leak the harm is live, so the slow order is the wrong one. Afterwards, the production guide says key usage can be monitored on the Usage page once tracking is on. It also says to keep keys out of code and public repositories.

### Trace: who did it?

If the public can use your tool, one bad user can cause trouble for your whole account. The OpenAI safety guide recommends **safety identifiers**: a string that uniquely identifies each user, sent with each request. They give "a stable way to trace activity back to an individual end user". The guide says: "Hash the username or email address in order to avoid sending us any identifying information." A hash turns text into a scrambled code that cannot easily be turned back.

### Tools that go away

Vendors retire models. A **deprecation** is the notice that a model will go. The **shutdown** or **retirement** is the day it stops. The notice is different for each vendor:

- **OpenAI** ([deprecations page](https://developers.openai.com/api/docs/deprecations)): generally available models get "At least 6 months"; specialized variants "At least 3 months". Preview models "may be retired with much shorter notice, such as 2 weeks".
- **Claude** ([model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)): "at least 60 days' notice before model retirement for publicly released models". "Requests to retired models will fail." The table calls its dates "Tentative retirement date". The docs suggest testing newer models "well before the retirement date". The Usage page in the Claude Console can export a CSV "broken down by API key and model".
- **Gemini** ([deprecations](https://ai.google.dev/gemini-api/docs/deprecations)): the shutdown dates in its table are "the _earliest possible dates_" a model might be retired. Google says it will tell users the exact date with advance notice. Once a model is shut down, "the endpoint is no longer available".

A real example from the OpenAI page: on March 24, 2026, developers were told that the Videos API and the Sora 2 models would be removed on September 24, 2026. The table lists no replacement. After that date the calls fail.

## Worked example

### Step 1: the weak list

```text
Tools: Veo, Claude, OpenAI images.
```

A product name is not a model. A vendor's deprecation table lists exact model IDs, so this list cannot be checked against it.

### Step 2: find the exact model IDs

Theo, the owner of the tools, reads the model ID in each script. For Claude, Theo also exports the usage CSV from the Console, to catch any old script still running. The result:

```text
Tool           Vendor   Exact model ID
Video          Gemini   veo-3.1-generate-preview
Captions       Claude   claude-sonnet-4-5-20250929
Mood board     OpenAI   gpt-image-1.5
```

### Step 3: look up each ID on its vendor's page

From the three live pages, on October 5:

```text
veo-3.1-generate-preview     shutdown October 22, 2026   replacement gemini-omni-1.1-flash
claude-sonnet-4-5-20250929   deprecated September 30, 2026; tentative retirement November 30, 2026
gpt-image-1.5                shutdown Dec 1, 2026        replacement gpt-image-2.5-sunburst
                                                         or gpt-image-2.5-flare
```

### Step 4: the hard case

**The hard case is the video pipeline.** Its row has three problems at once:

- **The date is the earliest possible one.** The Gemini page says the exact date will be announced later. It could move later, but Kiln cannot plan on that.
- **It is close.** October 22 is 17 days after October 5. The client's campaign runs at the end of the month, after that date.
- **The replacement is a different model.** Our reading: prompts and settings tuned for Veo may not give the same look on `gemini-omni-1.1-flash`. Kiln needs time to test.

So Theo treats October 22 as the real deadline, not as a guess. Our rule: switch one week before the vendor's date. For video that is October 15. Theo runs five past orders through the replacement this week, compares them with the approved files, and tells the client the plan today.

### Step 5: the better watch list

```text
Model ID                     Vendor date   Our switch-by   Owner
veo-3.1-generate-preview     Oct 22        Oct 15          Theo
claude-sonnet-4-5-20250929   Nov 30        Nov 23          Dana
gpt-image-1.5                Dec 1         Nov 24          Dana

Check: all three vendor pages on the first Monday of each month, and
whenever a script gets a new model ID. Owner: Theo
```

### Step 6: why it is better

- **Exact IDs.** Each row can be checked against a vendor table.
- **Our date, not theirs.** The switch-by date leaves a week to fix surprises.
- **Words read carefully.** "Earliest possible" and "tentative" mean the date may move, so Kiln plans for the first date.
- **A name on every row.** The client gets an answer the same day.

## Common mistakes

1. **Listing products, not model IDs.** "Veo" or "Claude" does not match any row in a deprecation table. Fix: write down the exact ID each script calls.
2. **Reading "earliest possible" as "probably later".** The Gemini date is the first day it may stop. Fix: plan to switch before it.
3. **Testing the replacement in the last week.** Then there is no time to fix a bad result. Fix: set a switch-by date with a buffer, and test before it.

## Try it

Not graded. Write your answer down before you read the answer.

Kiln adds a free "try it" button to the mood board. Visitors can make three images without logging in, so there is no username or email to hash.

1. Can Kiln still send a safety identifier for these visitors? What would it send?
2. Must Kiln send safety identifiers at all?

### Answer

1. **Yes: a session ID.** The OpenAI safety guide says: "If you offer a preview of your product to non-logged in users, you can send a session ID instead." A session ID is a code for one visit.
2. **No, but it is wise.** The guide says safety identifiers "are recommended for products where individual users interact with a model, but they are not required". Without them, one visitor's misuse is harder to trace.

## Recap

- Write the plan before launch: one row per trigger, with a first action that stops the harm and a named owner.
- In a leak, revoke the key first and replace it after. The calm order (new key, update, then revoke) is for normal rotation.
- Keep a list of exact model IDs. OpenAI previews may get about 2 weeks' notice, Claude gives at least 60 days, and Gemini lists the earliest possible shutdown dates. Switch before the date, not on it.

## Goal

After this lesson you can:

- Move one token change from the token file to every design file, in a fixed order.
- Publish a Figma or Penpot library change with a version and a clear note.
- Set up a coding agent so it can read the token file but not change it.

## The problem

A language-learning app changes one colour. The designer edits it in Figma. A developer edits the CSS. An AI agent, asked to "tidy the colours", edits the token file. Three people changed one thing in three places, and now there are three values.

A token change needs an **owner** and one **path**: one person decides, one file changes, and every tool gets the change in the same order (our terms).

## The idea

### One owner, small changes

Our advice: write down who owns the token file. Changes go through a **pull request** (a proposed change that others review before it is merged). Everyone else, people and agents, asks the owner.

The DTCG format helps keep changes small:

- **Change the alias, not every use.** The [DTCG spec](https://www.designtokens.org/tr/2025.10/format/) says that in a design tool, "changes to the value of a token being referenced by aliases SHOULD be reflected wherever those aliases are being used." So a new value can be a one-line edit.
- **Retire before you remove.** `$deprecated` marks "a token as deprecated, and optionally explain the reason". One reason the spec lists: "Removing the token now may break existing support".

### Publish a Figma library

A **library** is a file whose components, styles and variables other files can use. The [Figma publish page](https://help.figma.com/hc/en-us/articles/360025508373-Publish-a-library) says: "When you first create a style, component, or variable in a file, it is only accessible from that file. To make it available in other files, you need to publish it as a library."

Check the plan first. Publishing is "Available on all paid plans" and "Requires a Full seat with edit access to the library's source file".

After a change in the library file, "those changes will only appear in the current file until you publish them." Three details matter:

- **A note each time.** "Every time you publish updates to a library, you'll be prompted to add a description." Figma shows it "when accepting updates from a library, as well as in the file's version history."
- **Keep drafts out.** "Hide when publishing" keeps a component, style or variable out of the library.
- **The badge.** After a publish, people who use the library see "a blue badge on the library icon". "They can then review and accept the updates."

### Accept an update

The [Figma accept page](https://help.figma.com/hc/en-us/articles/360039234193-Review-and-accept-library-updates) adds one more case: the blue badge also shows "if you have made updates to a library resource that need to be published". By default, a review shows a "Side by side view of the change", with an Overlay view as the other option. Then you "Click Update next to an individual asset, or Update all to apply all updates."

### Help the code side

The [Figma variables page](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections) has two settings for developers:

- **Code syntax.** A code name for a variable. "You can create one name per platform, including Web, Android, and iOS." It shows in code snippets in Dev Mode, Figma's view for developers.
- **Description.** "Add a description to explain how the variable should be used."

### Penpot shared libraries

The [Penpot libraries page](https://help.penpot.app/user-guide/design-systems/libraries/) says you can "publish any regular file as a shared library". Other files "in the same team" can then connect to it.

Tokens need one more step. **Import tokens** copies a connected library's tokens into the current file. Penpot says this "is separate from connecting the library for components, colors and typographies". It also warns: "Importing tokens from a library replaces all tokens, sets and themes in the current file. Export your tokens first (from the Tokens tab → Tools → Export) if you need to keep a backup."

### Lock the token file for agents

A rules file guides an agent; it does not stop it. Both coding agents have settings that block edits.

**Claude Code.** The [Claude Code permissions docs](https://code.claude.com/docs/en/permissions) say: "Deny rules prevent Claude Code from using the specified tool." They name the fix for files: "add an `Edit` deny rule for paths no tool may change". And "`Edit` rules apply to all built-in tools that edit files." You can "check permission settings into version control to share them with every developer". One limit: deny rules do not cover "a Python or Node script that opens files itself". For that, the docs point to the **sandbox**, a walled-off area that limits what every command can touch.

**Codex.** The [Codex permissions docs](https://learn.chatgpt.com/docs/permissions) have permission profiles. They are in beta: "Permission profiles are under active development and may change." A path set to `read` "Allows commands to read files and list directories under the path. Commands cannot create, modify, rename, or delete files there." One catch: if `sandbox_mode` "appears in any loaded config file", Codex "uses those older sandbox settings instead".

Our advice: the agent may read the tokens and propose a change in a pull request. The owner makes the edit.

## Worked example

The app's token owner gets a request: links are hard to see, so make them darker.

### Step 1: the smallest edit

Links use an alias, so the change is one line:

```diff
  "link": {
-   "$value": "{color.palette.blue-500}"
+   "$value": "{color.palette.blue-700}"
  }
```

No screen and no component file changes. Every use of `link` follows the alias.

### Step 2: a version number

Our rule for the token file:

```text
value change, or a new token   ->  minor   2.3.0 -> 2.4.0
removed or renamed token       ->  major   2.4.0 -> 3.0.0
```

This is a value change, so the file goes from 2.3.0 to 2.4.0.

### Step 3: import into the library file

The owner imports the file into the Figma library file. The variable `color/role/link` now points at `blue-700`.

### Step 4: the hard case

**The hard case is a draft.** The same library file has a new variable, `color/role/promo`, still being tested for a sale banner. If the owner publishes now, the draft goes out too, and other teams may start to use it.

So, before publishing, the owner right-clicks `color/role/promo` in the library modal and picks **Hide when publishing**. Only the link change goes out.

### Step 5: publish with a note

```text
tokens 2.4.0
- color/role/link: now points at blue-700 (was blue-500).
  Why: links were hard to see on light cards.
- No names changed. Code syntax stays: --color-link.
- Please accept this update this week.
```

Figma shows this note to each team when they review the update, and keeps it in the version history.

### Why it is better

- **One line changed**, in one file, by one owner.
- **The version is on record**, so anyone can tell which tokens a screen or an agent used.
- **Drafts stay home.** Only finished work reaches other teams.

## Common mistakes

1. **A quick local fix.** A designer makes a new variable in their own file to fix a colour. It is "only accessible from that file". Fix: ask the owner to change the library.
2. **One big publish with the note "updates".** Nobody knows what changed or why. Fix: one topic per publish, and a note with the version, the change and the reason.
3. **No version in the agent's task.** The agent may use an old copy of the tokens. Fix: name the token version in the task.

## Try it

Not graded. Write your answer down before you read the answer.

A token owner has three changes in the library file:

```text
a. space/md: 16 -> 20 (finished)
b. color/role/success: a new token (finished)
c. color/role/beta-tag: a new token (still being tested)
```

1. Using our rule, what is the new version after 5.1.0?
2. What happens to change c?
3. Write the publish note.

### Answer

1. **5.2.0.** Change a is a value change and change b is a new token. Both are minor.
2. **Hide when publishing.** It stays in the library file, but other files do not get it yet.
3. One way to write it:

```text
tokens 5.2.0
- space/md: 16 -> 20. Why: more room between cards.
- color/role/success: new, for success messages.
- No names changed.
```

Your words can differ. Check that the note has the version, each change and a reason.

## Recap

- One owner, one path: change the token file in a pull request, change aliases, and retire tokens with `$deprecated` before you remove them.
- In Figma, a change stays in the library file until you publish it, with a note; other files then review and accept it. In Penpot, Import tokens replaces the file's tokens, so export a backup first.
- Lock the token file for agents with a Claude Code `Edit` deny rule or a Codex `read` path. A rule only guides.

## Goal

After this lesson you can:

- Name the rules file each coding agent reads: `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex.
- Write design rules that an agent can follow and a person can check.
- Keep a rules file short, split rules by folder, and know what a rules file cannot do.

## The problem

A design team works with an AI coding agent. Every day someone types the same reminders in chat: "Put new screens in the screens folder." "Every image needs alt text." The agent follows them in that session. The next day, in a new session, it has forgotten. A new teammate never typed them at all.

The fix is a **rules file**: a plain text file the agent loads each time a session starts. You write the design do's and don'ts once, and every session and every teammate gets them.

## The idea

### Three vendors, one idea

**Figma.** The [Figma rules page](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/) is for its MCP server (a plug that lets an agent read Figma data).

- It suggests "project-level instructions to help guide the AI toward consistent, high-quality output".
- It calls them the "unwritten rules" that experienced developers "would want to pass on to a new junior hire".
- The page does not pick the file: "check your IDE or MCP client's documentation for how to structure rules." (An IDE is a code editor.)

**Anthropic.** The [Claude Code memory docs](https://code.claude.com/docs/en/memory) say Claude "reads them at the start of every session". A project file sits at `./CLAUDE.md` or `./.claude/CLAUDE.md`, and it is "shared with your team through version control" (the shared history of the code).

**OpenAI.** The [Codex AGENTS.md docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md) say: "Codex reads AGENTS.md files before doing any work." There is a global file in your Codex home folder. Then Codex walks from the project root "down to your current working directory", reading the files on the way.

| Tool        | Project rules file                       | Size note from the docs                                            |
| ----------- | ---------------------------------------- | ------------------------------------------------------------------ |
| Claude Code | `CLAUDE.md` (can also read `AGENTS.md`)  | "target under 200 lines per CLAUDE.md file"                        |
| Codex       | `AGENTS.md` (`AGENTS.override.md` first) | stops adding files at `project_doc_max_bytes`, "32 KiB by default" |
| Figma MCP   | whatever your agent reads                | gives example rules                                                |

### How Codex joins its files

The Codex docs say: "Codex concatenates files from the root down, joining them with blank lines." (Concatenate means join end to end.) Then: "Files closer to your current directory override earlier guidance because they appear later in the combined prompt."

### When Claude Code reads AGENTS.md

The Claude docs say: "By default, Claude reads `AGENTS.md` only when you have no `CLAUDE.md` in your working directory or above it." With both files, Claude reads "Your `CLAUDE.md` files only".

The docs name a fix: "add a `CLAUDE.md` next to your `AGENTS.md` that imports it". A CLAUDE.md can pull in another file with `@path/to/import`. So a team can keep its rules in `AGENTS.md` and put the line `@AGENTS.md` in `CLAUDE.md`. One file, two agents.

### What goes in

Figma's list of unwritten rules is a good start:

- "Which layout primitives to use"
- "Where component files belong"
- "How components should be named"
- "What should never be hardcoded"

Three more sample rules from the page:

- "Follow WCAG requirements for accessibility" (WCAG is the W3C's set of web accessibility rules).
- A "Required flow". Step 1: "Run get_design_context first to fetch the structured representation for the exact node(s)." Only after `get_design_context` and `get_screenshot` does the agent start to build.
- "When conflicts arise, prefer design‑system tokens and adjust spacing or sizes minimally to match visuals."

### Write rules a person can check

The Claude docs ask for instructions "concrete enough to verify". Their examples:

- "Use 2-space indentation" instead of "Format code properly"
- "API handlers live in `src/api/handlers/`" instead of "Keep files organized"

Our reading: a good rule names a file, a folder, a component or a value. Then anyone can look at the result and say yes or no.

### Keep it short, one truth per rule

- **Size.** The Claude docs: "Longer files consume more context and reduce adherence." (Adherence means how well the agent follows it.)
- **Rules for one folder.** Claude Code has `.claude/rules/` files with a `paths` field. They "only apply when Claude is working with files matching the specified patterns".
- **No contradictions.** The Claude docs: "if two instructions contradict each other, Claude may pick one arbitrarily." So pick the one true rule and remove the other line.

### A rule is not a lock

The Claude docs say Claude treats these files "as context, not enforced configuration". To block an action "regardless of what Claude decides", the docs point to a **PreToolUse hook**: a script that runs before a tool call and can stop it.

Our advice: use rules to guide, and checks to prove. A **lint check** is a script that scans the code and fails on a rule break.

## Worked example

A design lead has a 600-line brand guide. It has the brand story, mood words, logo rules for print, chart rules and coding rules. The team uses Claude Code only.

### Step 1: the weak start

The lead pastes the whole guide into `CLAUDE.md`:

```text
CLAUDE.md  (600 lines)
  Our story: we started in a garage in 2019 ...
  Our voice is warm, playful, never cold ...
  Logo clear space on print: 2x the height of the "o" ...
  Charts: bars use the chart palette, never more than 6 colours ...
  New screens go in src/screens/ ...
```

The Claude docs target under 200 lines, and longer files "reduce adherence". Most of these lines are not rules for code.

### Step 2: sort every line

We sort each line into one of three boxes (our method):

```text
Every task      rules for any code the agent writes
One folder      rules for one part of the code only
Not a rule      story, mood, print-only rules: keep in the guide
```

The story and the print logo rules leave the file. They stay in the brand guide, where people read them.

### Step 3: write the root file

```markdown
# Design rules

- New screens go in `src/screens/<ScreenName>/`.
- Component files use PascalCase names, like `PriceTag.tsx`.
- Build UI from components in `src/ui/`. Ask before you add a new component.
- Every image has alt text. Decorative images use `alt=""`.
- Icons come from `src/icons/`. Do not add an icon package.
- Run `bun run test` before you say a task is done.
```

Each line names a folder, a file name pattern, a command or a thing you can see. A reviewer can say yes or no for each one.

### Step 4: the hard case

**The hard case is the chart rules.** They are real rules, and they matter. But they apply only to code in `src/charts/`. In the root file, they cost space in every session, also when the agent works on a login screen.

So they go in a path-scoped rule (our file name):

```markdown
---
paths:
  - 'src/charts/**'
---

# Chart rules

- Bars use the colours in `src/charts/palette.ts`, in order.
- A chart has at most 6 colours. Group the rest as "Other".
- Every chart has a text summary under it.
```

This file is `.claude/rules/charts.md`. It loads only when Claude works on files that match `src/charts/**`.

### Step 5: why it is better

- **Short root file.** Six lines that apply to every task, far under 200.
- **Rules where they matter.** Chart rules load only for chart code.
- **Every line is checkable.** No mood words that nobody can verify.

## Common mistakes

1. **Pasting the brand story into the rules file.** The agent cannot act on "warm and playful". Fix: keep only rules for the code, and leave the story in the guide.
2. **Rules that live in chat.** They are gone in the next session. Fix: if you type a reminder twice, add it to the rules file.
3. **Never reviewing the file.** Old rules point at folders that moved. Fix: review the rules file each time the design system changes.

## Try it

Not graded. Write your answer down before you read the answer.

A team uses Claude Code. Sort these lines from its guide into **every task**, **one folder** or **not a rule**:

```text
a. Our brand feels like a sunny morning.
b. Forms live in src/forms/ and use the Field component.
c. Email templates in src/email/ use tables for layout.
d. Every button has a visible text label.
e. The print logo is never smaller than 20 mm.
```

Then say where the email rule should live.

### Answer

- **Every task:** b and d. They apply to any screen and you can check them.
- **One folder:** c. It applies only to `src/email/`.
- **Not a rule:** a (a mood) and e (print only).

The email rule goes in a file like `.claude/rules/email.md`, with `paths` set to `src/email/**`. Then it loads only for email code. Your file name can differ. Check that each kept line can be answered with yes or no.

## Recap

- Claude Code reads `CLAUDE.md`, and Codex reads `AGENTS.md`. Codex joins its files from the root down, and a CLAUDE.md can import AGENTS.md with `@AGENTS.md`.
- Write rules that name a file, folder, component or command, so a person can check them. Keep the root file short and move folder rules into scoped files.
- A rules file guides; it does not enforce. Remove contradictions, and use a hook or a lint check when you need a guarantee.

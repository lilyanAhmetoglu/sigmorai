## Goal

After this lesson you can:

- Say the contrast lines in WCAG 1.4.3, and the exceptions to them.
- Work out a contrast ratio with the W3C formula, step by step.
- Build a contrast check where a script decides and an AI model only helps.

## The problem

A recipe app adds a yellow "Tip" box with grey text inside. A designer asks an AI model: "Is this readable?" The model looks at a screenshot and says yes. A week later, a user writes in: the tips are hard to read on a phone in the sun.

Contrast is a number, not an opinion. This lesson shows the rule, the formula, and a check that a script runs, not a model.

## The idea

### The rule: WCAG 1.4.3

**WCAG** is the W3C's set of rules for accessible web content. Rule 1.4.3 is called "Contrast (Minimum) (Level AA)". Level AA is one of WCAG's levels. The page notes a stricter line for level AAA: "The contrast ratio of 7:1 was chosen for level AAA". The [W3C page](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) gives its goal in five words: "Text can be seen by more people."

The rule says text needs "a contrast ratio of at least 4.5:1". **Contrast ratio** compares how light two colours are. 1:1 is no difference, and 21:1 is black on white.

There are three exceptions:

- **Large text.** "Large-scale text and images of large-scale text have a contrast ratio of at least 3:1". Large means "18 point text or 14 point bold text". In screen pixels, 14pt and 18pt "are equivalent to approximately 18.5px and 24px".
- **Incidental text.** Text in "an inactive user interface component", text that is "pure decoration", text "not visible to anyone", or text in "a picture that contains significant other visual content" has "no contrast requirement".
- **Logos.** "Text that is part of a logo or brand name has no contrast requirement."

The logo exception is small. The W3C says: "Beyond logos and logotypes, text that has insufficient contrast due to corporate identity or brand guidelines is not exempted from the requirements of this criterion."

The rule covers "placeholder text" (the grey hint in an empty field). It also covers text "shown when a pointer is hovering over an object or when an object has keyboard focus". Charts, graphs and diagrams fall under a different rule, "Success Criterion 1.4.11 Non-Text Contrast".

### The formula

The W3C defines the contrast ratio as:

```text
(L1 + 0.05) / (L2 + 0.05)
L1 = relative luminance of the lighter colour
L2 = relative luminance of the darker colour
```

**Relative luminance** is how bright a colour is, "normalized to 0 for darkest black and 1 for lightest white". For sRGB (the standard colour space for screens), the W3C gives these steps:

1. Split the hex code into red, green and blue, and divide each by 255.
2. Convert each channel: if it is 0.04045 or less, divide by 12.92. Else use `((c + 0.055) / 1.055) ^ 2.4`.
3. Add them up: `L = 0.2126 * R + 0.7152 * G + 0.0722 * B`.

"Contrast ratios can range from 1 to 21".

### Three notes for a checker

- **No rounding.** The lines are "threshold values", and "the computed values should not be rounded (e.g., 4.499:1 would not meet the 4.5:1 threshold)."
- **Use the defined colours.** Check "the foreground and background colors obtained from the user agent, or the underlying markup and stylesheets, rather than the text as presented on screen." (The user agent is the browser.) Our reading: in a design system, that means the token values.
- **Check pairs that meet.** Check "color pairs specified in the content that an author would expect to appear adjacent". It is also "a failure if no background color is specified when the text color is specified".

### Why a model should not decide

Both vendors warn about reading images:

- The [Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision): Claude "might hallucinate or make mistakes when interpreting low-quality, rotated, or very small images under 200 pixels." And: "Always carefully review and verify Claude's image interpretations, especially for high-stakes use cases."
- The [OpenAI vision docs](https://developers.openai.com/api/docs/guides/images-vision): "Vision models can make mistakes." A model "may struggle to understand graphs or text where colors or styles—like solid, dashed, or dotted lines—vary." Also, "Images may be resized before analysis".

A screenshot has a second problem: the W3C asks for the defined colours, not "the text as presented on screen". So even a perfect reading of a screenshot measures the wrong thing (our reading).

Our advice: a model can list the colour pairs and suggest fixes. A script with the formula gives the verdict.

## Worked example

The recipe app's tokens:

```text
text/tip      #6b6b6b   grey text inside the Tip box
bg/tip        #f2d58f   yellow Tip box
bg/page       #ffffff   white page around the box
```

The tip text is body text, so the line is 4.5:1.

### Step 1: luminance of the grey

`#6b6b6b` has red, green and blue all equal to `6b`, which is 107.

```text
107 / 255                      = 0.4196
0.4196 > 0.04045, so:
((0.4196 + 0.055) / 1.055)^2.4 = 0.147
R = G = B = 0.147, so L        = 0.147
```

When all three channels are the same, L equals the channel value, because the three weights add up to 1.

### Step 2: luminance of the yellow

`#f2d58f` has three different channels, so each one gets its own step 2, then the weights:

```text
channel   hex   /255     converted
red       f2    0.9490   0.8879
green     d5    0.8353   0.6654
blue      8f    0.5608   0.2747

L = 0.2126 * 0.8879 + 0.7152 * 0.6654 + 0.0722 * 0.2747 = 0.6845
```

(Our sums. The numbers are rounded here only to fit the page. A script keeps every digit.)

### Step 3: the ratio

The yellow is lighter, so it is L1.

```text
(0.6845 + 0.05) / (0.147 + 0.05) = 0.7345 / 0.197 = 3.73
```

3.73 is under 4.5. The tip text fails.

### Step 4: the hard case

**The hard case is the background.** The designer's first check put the grey on the white page: 5.33:1, a pass. But the tip text never sits on the white page. It sits on the yellow box. The W3C asks for the pairs "an author would expect to appear adjacent", and here that is grey on yellow.

So the pairs file lists the real neighbours:

```text
pair                       text size   needs
text/tip  on  bg/tip       body        4.5
text/body on  bg/page      body        4.5
```

### Step 5: the fix, checked by the script

A model suggests a darker grey, `#4d4d4d`. The script, not the model, checks it: `#4d4d4d` on `#f2d58f` is 5.91:1. Pass.

Why this is better:

- **The verdict comes from the formula**, using token values, not a screenshot.
- **The pairs are the real neighbours**, so the check tests what users see.
- **The model still helps**: it found the pairs and proposed the fix.

## Common mistakes

1. **Checking only the resting state.** Placeholder text and text on hover or focus count too. Fix: add those states as rows in the pairs file.
2. **Using the text lines for icons and charts.** Those fall under 1.4.11, a different rule. Fix: check text with 1.4.3, and non-text parts with 1.4.11.
3. **Dividing the wrong way.** Darker over lighter gives a number under 1. Fix: always put the lighter colour on top, so the result is between 1 and 21.

## Try it

Not graded. Write your answer down before you read the answer.

A search field has a light grey background (L = 0.9). Its placeholder text has L = 0.2. When a user types, the text turns black (L = 0).

1. Work out the ratio for the placeholder text.
2. Work out the ratio for the typed text.
3. Does the placeholder need a check at all?

### Answer

1. `(0.9 + 0.05) / (0.2 + 0.05) = 0.95 / 0.25 = 3.8`. Under 4.5 for body text: it fails.
2. `(0.9 + 0.05) / (0 + 0.05) = 0.95 / 0.05 = 19`. A pass.
3. **Yes.** The W3C says the rule covers placeholder text. Add it as its own row in the pairs file, then pick a darker grey and run the script again.

## Recap

- WCAG 1.4.3: 4.5:1 for text, 3:1 for large text. Only incidental and logo text are exempt, and brand guidelines are not an excuse.
- The ratio is `(L1 + 0.05) / (L2 + 0.05)`, from the defined colours, with no rounding. Check the pairs that really sit next to each other.
- Models can misread images. Let a model list pairs and suggest fixes, and let a script give the verdict.

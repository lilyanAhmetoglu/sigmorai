## Goal

After this lesson you can:

- Place a person's sign-off at the right points in a creative chain, and design the card that person signs.
- Explain how an approval pauses a run, how long it can wait, and how to send a reason with a "no".
- Put the approval on the tool that causes the side effect, and know which tools a vendor's default policy covers.

## The problem

A wedding photo studio uses an agent chain. One agent picks and edits 300 photos and makes a 60-second highlight film. Then it hands the job to a delivery agent. The delivery agent has two tools: one emails the gallery link to the couple, and one posts the film on the studio's public page.

Last month three things went wrong:

1. The approval message said only "Gallery ready. Send?" The owner tapped yes on a phone. The gallery still held 40 unedited test shots.
2. The owner was at another wedding all weekend. The team got tired of waiting, so they set the agent to "approve by itself after 2 hours". A film went public before the couple had seen it.
3. The only check was on the first agent's input. The delivery agent's posting tool had no check at all.

The studio had a reviewer model, a rubric and a person. It still shipped mistakes. The sign-off was in the wrong place and showed the wrong things.

## The idea

### A check is not a signature

A reviewer model can pass every rubric line. That is evidence. It is not permission. When work goes to a client or to the public, a named person who can answer for it must say yes. Our rule: **reviewers check, people sign.**

Two sources point the same way:

- The [Anthropic engineering post on agents](https://www.anthropic.com/engineering/building-effective-agents) says agents can "pause for human feedback at checkpoints or when encountering blockers".
- The [Gemini agents docs](https://ai.google.dev/gemini-api/docs/agents) say to "Always verify outputs" before you deploy them, "especially for tasks that modify data or interact with external systems".

The Gemini docs also list managed agents as a **Public Preview**, and ask you to review the agent's actions and outputs before you rely on them in sensitive work.

### Where sign-off sits

The [OpenAI guardrails docs](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) say human approval fits when you must pause "before side effects like cancellations, edits, shell commands, or sensitive MCP actions". A side effect is a change in the outside world: an email that is sent, a post that is live.

Our habit: three sign-off points in a creative chain.

```text
1 BEFORE THE SPEND   approve the plan before expensive renders
2 AT A STOP          a stop rule ended the loop without a pass
3 BEFORE THE SEND    approve the exact file before it leaves
```

### What the person must see

A sign-off is only as good as the card the person signs. This part is ours.

A weak card says only "Ready. Approve?" The person must take the agent at its word.

A strong card shows the evidence:

- the actual file (a player or a preview), not a summary of it
- each rubric line and its result from the last round
- where it goes: the address, the account, the exact caption
- money spent against the budget, and rounds used
- any stop rule that fired

If the card cannot show the file, the person is not signing the file.

### How the pause works

Both vendors treat an approval as a pause that can last a long time.

**OpenAI Agents SDK.** The [guardrails docs](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) list the steps:

1. The run records an approval interruption "instead of executing the tool".
2. The result returns the interruptions and a state you can resume.
3. Your app approves or rejects each one.
4. You "resume the same run" from that state, not a new one.

For a slow reviewer the docs say: "If the review might take time, serialize `state`, store it, and resume later. That's still the same run."

The [SDK human-in-the-loop docs](https://github.com/openai/openai-agents-python/blob/main/docs/human_in_the_loop.md) add one more useful fact. This works even when the tool belongs to an agent reached through a handoff. The approval still shows up on the outer run.

**Claude Managed Agents (beta).** The [Claude permission policies docs](https://platform.claude.com/docs/en/managed-agents/permission-policies) describe a similar pause:

- A tool set to `always_ask` makes the session pause "and wait for your approval before executing".
- While it is paused, "The session waits indefinitely for a response."

Your app then sends a `user.tool_confirmation` event with `"allow"` or `"deny"` for each blocked call.

So a person who is away does not break anything. The job waits. Our advice: a missing answer is never a yes. Do not add a timer that approves by itself. If a wait is too long, send a reminder or pass the card to a second person.

### Say why when you say no

A plain "no" teaches the agent nothing. Both vendors let you add a reason.

- **OpenAI.** By default, a rejected call sends the SDK's standard rejection text back into the run. You can pass `rejection_message=...` to `state.reject(...)` for one call, or set a run-wide `tool_error_formatter`.
- **Claude.** Add a `deny_message` to the denial. The docs say the agent then "receives a tool result saying the call was rejected, including your `deny_message`".

Our habit: write the reason as an instruction. Not "no", but "Do not send yet. Remove the test shots from the gallery, then ask again."

### Put the approval on the tool

The OpenAI guardrails docs warn that agent-level checks "don't run everywhere":

- An input guardrail checks only the first agent of the chain.
- An output guardrail checks only the agent that gives the final answer.
- A tool guardrail checks only the function tools it is attached to.

Their advice for checks around every custom tool call: "Put validation next to the tool that creates the side effect."

Our reading: a line in the prompt like "always ask before posting" only asks the model nicely. It is not a lock. Put the approval on the tool itself.

### What Claude's policies cover

The Claude docs list three policies: `always_allow`, `always_ask`, and `auto`, where the server judges each call. Defaults differ by toolset:

- The built-in agent toolset defaults to `always_allow`.
- MCP toolsets default to `always_ask`. The docs say this "ensures that new tools added to an MCP server do not execute in your application without approval".

One kind of tool is outside all of this. The docs say: "Custom tools are executed by your application and controlled by you, so they are not governed by permission policies." If your own app runs the tool, your own app must ask the person.

## Worked example

### Step 1: the weak set-up

```text
Chain:     editor agent -> hands off to delivery agent
Tools:     send_gallery_email (custom; the studio app runs it)
           post_film (from a social MCP server)
Checks:    one input guardrail on the editor agent
Card:      "Gallery ready. Send?"  [Yes] [No]
Waiting:   auto-approve after 2 hours
```

### Step 2: find what each check really covers

```text
Input guardrail on editor   -> runs for the first agent only.
                               Never sees the delivery agent.
post_film (MCP)             -> on Claude, MCP default is always_ask.
                               It will pause. Good.
send_gallery_email (custom) -> no Claude policy covers it.
                               Nothing asks a person. GAP.
Auto-approve after 2 hours  -> a missing answer becomes a yes. GAP.
```

### Step 3: the hard case

**The hard case is the email tool.** The team saw `always_ask` on the MCP posting tool and thought: "Good, the platform asks before every action." For `post_film` that is true, because MCP toolsets default to `always_ask`.

But `send_gallery_email` is a custom tool. The studio's own app runs it. As the quote above says, permission policies do not apply to such tools. So no platform setting will ever pause it. The studio's app must stop before it sends, show the card, and wait for a person.

The same is true on OpenAI, in a different way. The input check sits on the first agent, and the email is sent by the second agent after a handoff. Set approval on the tool itself (a `needs_approval` tool), and the pause appears on the outer run, wherever the tool sits in the chain.

### Step 4: the better set-up

```text
Sign-off 1  plan: photo list + film storyboard, before export
Sign-off 2  any stop rule fires -> card to the owner
Sign-off 3  before send_gallery_email AND before post_film

Card:  gallery preview (all 300 photos, scrollable)
       film player
       rubric: lines 1-5, pass/fail
       to: couple's email address / studio page + caption
       cost: $18 of $25, rounds: 2 of 4

Approval:  on the tools themselves
           post_film: MCP, always_ask (keep the default)
           send_gallery_email: the studio app pauses and asks
Waiting:   no auto-approve; reminder after 12 hours;
           second approver after 24 hours
On "no":   deny_message with one clear instruction
```

### Step 5: why it is better

- **The person signs what ships.** The 40 test shots are visible on the card.
- **No silent yes.** A long wait sends reminders, not posts.
- **Every side effect is covered.** Each tool that sends or posts has its own approval, wherever it sits in the chain.
- **A "no" helps.** The agent gets an instruction it can act on.

## Common mistakes

1. **A card with no file on it.** The person signs the agent's summary. Fix: show the file, the rubric results and the destination.
2. **Trusting a platform default for a custom tool.** Tools your own app runs are outside Claude's permission policies. Fix: build the approval into your app for those tools.
3. **Checking the first agent only.** Input guardrails never see later agents. Fix: put the approval next to the tool with the side effect.

## Try it

Not graded. Write your answer down before you read the answer.

A design studio has an OpenAI Agents SDK chain. A triage agent hands work to a print agent. The print agent has a tool `order_prints` that spends money at a print shop. The team says:

```text
a  "Our input guardrail on the triage agent covers it."
b  "If the boss rejects, the agent just sees 'rejected'.
    That is fine."
c  "The boss takes two days to answer. We must restart
    the run each time."
```

What is right or wrong in each line?

### Answer

- **a: wrong.** An input guardrail checks the triage agent only. Mark `order_prints` with `needs_approval=True`. The pause then shows on the outer run, even after the handoff.
- **b: weak.** By default the run gets standard rejection text. Pass a `rejection_message` that says what to change, such as "Order 20, not 200."
- **c: wrong.** Save the state, store it, and resume later. The docs say it is still the same run.

## Recap

- A reviewer gives evidence. A named person signs: before the spend, at a stop, and before the send. The card shows the real file, the rubric results, where it goes and the cost.
- Approvals can wait. OpenAI resumes the same run from saved state; Claude's `always_ask` session waits with no time limit. A missing answer is never a yes, and a "no" should carry a reason.
- Put the approval on the tool with the side effect. Agent-level checks miss later agents, and a custom tool run by your own app gets no Claude policy at all.

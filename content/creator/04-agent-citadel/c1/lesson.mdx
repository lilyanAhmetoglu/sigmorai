## Goal

After this lesson you can:

- Tell a workflow from an agent, and say who picks the next step in each one.
- Place a creative job on a ladder: one call, a workflow, or an agent.
- Explain why the number of loops in an agent run, and so its cost, is unknown at the start.

## The problem

An illustrator makes picture books for small publishers. A publisher sends a new job: a 12-page book about a fox who is afraid of rain. The publisher has approved the text and one style sheet (colours, line weight, how the fox looks).

The illustrator reads about AI agents and writes this plan:

> One agent does the whole book. It reads the text, decides the style, draws all 12 pages, checks them, fixes what it does not like, and exports a print file. I just wait for the result.

The plan sounds modern. It has three hidden problems:

1. Some parts of the job never change. The export is the same every time. Nobody needs a model to decide it.
2. Some parts are already decided. The style sheet is approved, so "decide the style" is work the agent should not do.
3. Nobody knows how long the agent will run, or what it will cost. The plan has no number at all.

This lesson gives you a way to split a job like this. Each part goes to the simplest tool that can do it.

## The idea

### Two kinds of chain

The [Anthropic engineering post on agents](https://www.anthropic.com/engineering/building-effective-agents) calls both kinds "agentic systems", but it draws one clear line between them:

- A **workflow** is a system where models and tools run on paths that were written in code beforehand. The post calls them "predefined code paths". A person chose the steps.
- An **agent** is a system where the model chooses. In the post's words, agents are systems where LLMs "dynamically direct their own processes and tool usage".

So the key question is simple: **who picks the next step?** In a workflow, your code does. In an agent, the model does.

A small comparison helps. A workflow is a recipe card: step 1, step 2, step 3, the same each time. An agent is a cook who tastes the soup and decides what to add next.

The post is from December 2024. A note at the top says much of the tooling it describes "has changed since December 2024". The two definitions are still the useful part.

### The agent loop

The [OpenAI agents docs](https://developers.openai.com/api/docs/guides/agents) describe agents as systems that "can plan and complete tasks using tools, work with other agents, and maintain context across steps".

The [OpenAI Agents SDK docs](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md) describe the loop. Our short version:

```text
1. call the model with the current input
2. look at what the model returned:
   - a final answer (text, no tool calls)  -> stop, return it
   - a handoff to another agent            -> switch agent, go to 1
   - one or more tool calls                -> run them, add the
                                              results, go to 1
```

For a picture, one image can take several trips. The model asks for an image. Your app runs the image tool. The image comes back. The model looks and asks for a new version. Then it looks again and gives its answer. That is three model calls for one picture.

Two things follow from this loop:

- **Every trip costs something.** Each trip is a model call, and model calls use tokens. The tool call may cost money too.
- **The model sets the number of trips.** You do not know the count when you press start. A long run is how the loop works. It is not, by itself, a bug.

### How big the spread can be

The [Gemini agents docs](https://ai.google.dev/gemini-api/docs/agents) put a number on this for Google's managed agents. Their pricing is pay-as-you-go, "based on Gemini model tokens and tool usage". The docs say: "A single interaction can trigger multiple reasoning loops, typically consuming 100k to 3M tokens."

The top of that range is 30 times the bottom. So there is no "normal" number of loops you can budget for. The same docs list managed agents as a **Public Preview**, so these details may change.

### The ladder

The Anthropic post gives the main advice: "we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all."

It explains the trade. Agentic systems "often trade latency and cost for better task performance". And for many applications, one well-built model call "is usually enough".

So think of three steps on a ladder:

```text
3  agent      the model picks the steps    open-ended work
2  workflow   fixed steps, in code         known, repeated work
1  one call   one prompt, one result       many jobs end here
```

Start at the bottom. Climb only when the step below fails.

### When an agent fits

The Anthropic post says agents fit "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path".

It also names the price: "The autonomous nature of agents means higher costs, and the potential for compounding errors." Its advice is to test agents a lot in sandboxed environments, with the right guardrails.

Our reading: if a job repeats with the same steps, a model that "chooses" the steps only adds risk. There is nothing to choose.

## Worked example

### Step 1: the weak plan

```text
ONE AGENT, whole book:
  read text -> decide style -> draw 12 pages -> self-check
  -> fix -> export print PDF
  limits: none
```

What goes wrong:

- The style is already approved. If the agent "decides" it again, page 1 may not match the style sheet.
- The export has fixed settings. A model gains nothing by choosing them.
- There is no limit. The run could be 20 trips or 200.

### Step 2: split the job into parts

Write each part on its own line. Then ask one question for each: **can I write the steps before the job starts?**

```text
PART                         STEPS KNOWN?   WHY
A  export a print PDF        yes            same settings every book
B  one cover sketch for      yes            one prompt, approved style
   the sales sheet
C  12 page illustrations     yes            one page = one prompt + check
D  find a new idea for the   no             the publisher wants
   back cover: "surprise us"                 options, not a set answer
```

### Step 3: put each part on the ladder

```text
A  export          -> workflow (fixed code, no model choice)
B  cover sketch    -> one call, then a person looks
C  12 pages        -> workflow: for each page, one image call,
                      one check, the same steps 12 times
D  back cover      -> maybe an agent: try ideas, look, drop
                      weak ones. Set a limit first.
```

### Step 4: the hard case

**The hard case is part C, the 12 pages.** It looks like agent work. There are many images, each one needs a check, and some will need a second try. It feels "open-ended".

But read the steps again. For every page you can write them down before you start: take the page text, make one image in the approved style, check it, redo it once if the check fails. The path is the same for page 1 and page 12. That is a workflow with a small repeat inside it. Your code holds the steps. The model only draws.

Why this matters: a workflow is easy to predict. You know there are 12 pages and at most 2 image calls per page. So you can say "no more than 24 image calls" before the job starts. An agent gives you no such number.

Only part D has no path you can write down. Nobody knows how many ideas the agent will try. That is the one place where an agent may earn its cost.

### Step 5: the better plan

```text
A  export:      a script with fixed print settings
B  cover:       one image call with the approved prompt;
                the illustrator looks at it
C  pages 1-12:  a workflow; each page gets 1 image call,
                1 check, and at most 1 redo
D  back cover:  an agent, with a cap on tries and a
                person who picks the final idea
```

### Step 6: why it is better

- **Each part uses the lowest step that works.** Only one part pays the agent price.
- **Most of the cost is known.** Parts A, B and C have a fixed number of calls.
- **The approved style stays approved.** No model gets to "decide" it again.
- **The open part has a limit.** The plan says how the agent run will end before it starts.

## Common mistakes

1. **Using an agent because the job is big.** Size is not the test. Fix: ask if you can write the steps first. If you can, build a workflow.
2. **Budgeting for a "normal" number of loops.** The model decides the count, and the spread is wide. Fix: set a hard cap on tries or money before the run.
3. **Thinking only the image tool costs money.** Every trip round the loop is also a model call that uses tokens. Fix: count model calls and tool calls when you plan.

## Try it

Not graded. Write your answer down before you read the answer.

A small music label asks you to plan three jobs for a new single:

```text
1  For every new episode, put its title on the same approved
   card template and save a PNG and a JPG.
2  The singer wants "a strange, dreamy visual idea" for a
   tour poster. No idea is chosen yet.
3  A teammate plans the agent in job 2 like this: "The docs
   say 100k to 3M tokens per interaction. Our budget is
   100k, the low end. That is enough."
```

For jobs 1 and 2, pick a step on the ladder. For line 3, say what is wrong with the teammate's idea.

### Answer

1. **Workflow.** The card and the two file types are the same for every episode. The steps are known, so fixed code does it. A model choosing them adds nothing.
2. **Maybe an agent, with limits.** Nobody can write the steps for "find a strange idea". The model must try, look and choose. Try one call first. If that is not enough, use an agent with a cap.
3. **The low end is not a budget.** The top of that range is 30 times the bottom, and the model chooses how many trips to take. A run can pass 100k easily. Set a hard cap on tries or money, and plan for the high end.

## Recap

- A workflow follows steps written in code. An agent lets the model pick the next step and the tools.
- Start with the simplest thing: one call, then a workflow, then an agent. Many jobs never need an agent.
- In an agent loop, the trip count is the model's choice. Each trip costs tokens, so the cost is unknown until you set a limit.
